# Task Progress Registry

## Authority

所有模型、执行者和会话共用活动 Spec 的 `tasks.md`。在顶部维护 `Execution Progress`，
完整列出所有可执行单元，包括设计收口、实现、迁移、补救、检查、正式验收和交付。
每行包含稳定 ID、详细说明链接、状态、依赖、证据/剩余项、更新时间；按依赖排序。
父任务保留其验收，子任务详情可在同文件或链接契约；不要复制契约，也不要另建模型专用进度表。

## Generation and Regeneration

每次生成或修订 tasks.md 都必须包含该表，不能只在用户指定某个模型时启用。
使用 `.specify/templates/tasks-template.md` 的字段顺序：
`Unit / Details | Status | Depends | Evidence / Remaining | Updated`。
若模板被 preset/override 替代，生成者仍应补齐此标准。
单层任务直接用 T001；只有确需拆分时才使用 T001-A 等子任务 ID。
逐行链接可执行详情：成果、阅读入口、修改范围、步骤、验收；同文件和契约链接均可。
重新生成先读取旧表，保留 ID、状态、证据和 checkpoint；仅重新打开实际受影响的单元。
生成后核对任务/子任务覆盖、唯一 ID、依赖存在且无环、详情与证据链接、状态和父任务勾选。
缺少进度行不能视为任务未开始或已完成；先补齐真实状态再交付。

## Progress Timestamp

`Updated`必须使用`YYYY-MM-DD HH:mm ±HH:MM`，例如`2026-09-12 16:22 -05:00`；
从实际系统时钟取得时间，精确到分钟并保留UTC offset。项目约定时区时先转换到该时区，不能硬编码夏令时offset。
它表示该行最后一次实际修改（状态、依赖、证据或剩余项）的记录时间，不是开始/完成时间或验收执行时间。
只刷新发生变化的行；重排、读取、格式化其他行或提交文件，不应顺带刷新整表时间。
新Current Checkpoint和批次结果的事件时间也精确到分钟并带offset；Date创建日期字段可仍仅保留日期。
跨机器保留事件来源时区或统一转换到项目时区；不把合并时间覆盖为另一机器的执行时间。
历史只有日期时保留原记录并说明精确时间UNKNOWN，不用00:00、文件mtime或提交时间冒充事件时间。
首次升级旧表可用本次格式迁移时间作为Updated，但必须明确这是元数据修订时间，并保留旧日期来源，不能据此重算历史耗时。

## Status

### Strict Serial Completion Mode

用户要求逐项完成、上一项完成才开始下一项时，在plan/tasks标明`STRICT_SERIAL`。
本模式优先于默认批内静态通过后继续、异步独立派发及测试暂缓规则：

1. 先按实现、接口、设计、构建及验收依赖拓扑排序，再按实际执行顺序列正文和进度表。
   前置必须出现在前面；禁止前向依赖、循环和未知ID。只有依赖顺序正确后才分story/phase，不能为分组打乱顺序。
2. 每个顶层任务是一个完整可验收工作单元；反例/实现/静态复审/受影响构建/回归/适用动态验证/证据在本项闭合。
   必须共同构建验收、无法各自完成的成员合为同一任务的内部步骤，不列成多个必须先后DONE的任务。
3. 下一项以紧邻前项DONE为硬门；PARTIAL、BLOCKED、STATIC_PASS/TESTS_DEFERRED均不能解锁。
   不生成[P]或并行示例；在当前项解决设计/诊断缺口，不能跳到后项回填前置。
4. 独立最终系统验收可以置末，但不得接收前项自身必需的验收欠账，更不能靠缩减原验收制造局部DONE。
   明确unit/batch与feature系统出口，保留原需求、C++证明和真实实验义务；不得承诺未来实验绝不会暴露缺陷。
5. 修订现有清单保留历史证据；未执行任务可经显式旧→新映射重编号，已执行稳定ID优先保留并另列执行序号。
   同步plan/contracts/traceability/active引用，不重命名历史证据来伪造新结论。
6. 失败停在当前项；后续发现前项回归时，重开最早受影响项并暂停后项，修复/验证受影响闭包。
   这是显式失败恢复，不是正常调度；更新证据失效范围，不默许无序跳转。

生成后检查正文顺序=进度表顺序，每项依赖仅引用较早项、包含紧邻前项；检查验收步骤不存在等待后项的反向依赖。
结构校验不能代替语义审查，也不构成产品DONE。普通模式保留原批次/并发规则，不自动修改冻结旧Spec。
仓库提供时运行`python3 skills/speckit-code-design/scripts/verify-serial-tasks.py <tasks.md>`；
维护该检查器时运行`--self-test`，并独立审查实际任务验收是否偷偷等待后项，脚本不声称能自动判断语义。
该检查器只接受单层顶层任务表，遇可执行子ID明确拒绝；不可分步骤写在本项内部，不截断子ID冒充父依赖。

使用 NOT_STARTED、READY、IN_PROGRESS、PARTIAL、BLOCKED、DONE。
READY 需要依赖和阶段门禁满足；PARTIAL 只说明部分成果，不代表可以跳过依赖。
批内小任务静态通过而测试待执行，记录 PARTIAL 与 `STATIC_PASS / TESTS_DEFERRED / Batch ID`；只有明确定义的实现依赖可据此继续，验收依赖仍需实际通过。批末测试证据逐项映射成员，完整单元验收后才 DONE；不把证据标记新增为状态枚举。
DONE 需要完整单元验收及持久证据；源码存在、语法检查、单项测试或结构检查不能替代完整验收。
父任务只有全部子任务 DONE 且父任务验收满足后才勾选，正式资格验收保持独立。
迁移旧计划时说明状态来源和未核实边界，不推算虚假的完成百分比。

## Update Protocol

1. 开始工作前读取进度表、当前 checkpoint 和前置证据，选择已授权且门禁满足的单元。
2. 新发现的工作先补稳定 ID、依赖和详细执行定义，再登记进度行；不只留在聊天或临时 TODO。
3. 开始执行时更新 IN_PROGRESS；每个单元成功、失败或阻塞后更新状态、证据、剩余验收和分钟级Updated，遵循Progress Timestamp。
4. 证据记录实际源码基线、相关未提交改动、命令和结果；没有运行的检查明确 NOT_RUN。
5. 提交和最终回复前核对表、代码与证据；并发修改时读取最新文件，仅更新自己负责的行。
6. 新修改使原证据失效时重新打开受影响单元，保留历史证据；范围取消需同步 Spec/plan，不能冒充 DONE。

这是执行者的持续维护协议，不是无人运行时自动监控源码的后台服务。
生成任务时检查每个父任务都有执行单元；执行时检查卡片与进度行一一对应、依赖有效，
DONE 有证据且父任务没有提前勾选。新 Spec 沿用此规则，不自动回填冻结的旧 Spec。
