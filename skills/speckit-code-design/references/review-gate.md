# Design Readiness Review

## Core Goal And Necessity Review

在补齐设计或追加任务前，先用当前用户决定界定核心成果、完成边界、明确排除项及独立
验收；旧 Spec 的措辞和任务清单不能覆盖后续决定。若决定存在实质冲突，指出受影响的
范围和证据，不能自行选择更大或更小的目标。

对每项需求、设计机制、任务和实验条件检查两件事：

- **必要性**：删掉它，哪个核心成果、强制约束或必要验收会失败？给出具体依赖或失败
  因果。只说“更完整”“更通用”“以后有用”或引用它自己的 FR 编号不能证明必要。
  必需前置可以间接支撑成果，但应说明为何现有支持不能满足；不要求每项前置都单独
  产生用户可见功能。
- **最小性与顺序**：已有 API、部署路径或仍适用的资格证据能否复用？有没有更小改动
  达到相同出口？任务是否有真实依赖、明确 owner、失败/清理路径和独立判据？先闭合
  能回答目标的最小端到端路径，再做由测量或已批准主张确实需要的扩展。

特别检查：无当前消费者的通用化、平行实现/构建部署路径、重复模型导出或实验、同一
行为的机械任务拆分、重复文档与报告，以及扩大模型/拓扑/故障矩阵却不回答新问题。
这些是检查线索，不是自动判错；风险不同、候选改变或验收合同不同可能使额外工作必要。

在已有 findings/coverage 记录内附简短处置，不新增 task、报告层级或审批门：

| Item / location | Goal or necessary prerequisite | Disposition | Evidence and smallest sufficient action |
| --- | --- | --- | --- |
| [FR / mechanism / task / experiment] | [成果、约束或因果依赖] | keep / reuse / merge / remove / defer | [源码、仍适用证据或缺口；替代路径及影响] |

只列实际发现及关键依赖；无删减建议时明确说明已检查，并说明必要性依据。`defer` 指移出
当前 Spec 的建议，不自动生成新 Spec、backlog 或任务。`reuse` 要核对版本、配置、候选和
验收范围，不能用旧 PASS 覆盖新行为。未知必要性保持 unverified，不因缺证据直接删掉。
结论给出最小剩余依赖顺序、必要验收和明确移出的工作；覆盖率高、任务全打勾或结构清晰
都不能替代“目标值得做且任务必要”的判断。

审计只提出处置建议；只有当前授权包含修改时才落实。保留已批准行为、信任与授权、
兼容迁移、资源边界、取消/清理及必要负例/真实验收；不能通过降级它们制造精简或 PASS。

## Call-Chain Design Review

设计和审计以一条具体业务动作的真实调用链为主线，不按孤立文件或 API 清单推断闭环。
复用已有 FLOW/契约，在同一设计或审计记录内按执行顺序说明：生产入口与有效配置
→ 实际 caller/owner → 被调实现或远端接收方 → 结果消费者 → 可观察结果及资源释放。
受影响的分支单独注明；不为无关路径展开全仓库调用图或新增报告层级。

逐跳核实并解释以下细节，不能只列函数名或写“接入、转发、处理完成”：

- **可达性**：准确的文件/符号、调用或注册位置、触发条件、默认工厂/配置分支及真实
  实现实例来源。每条边需有调用点、注册/dispatch 或协议生产/消费的源码依据；同名字段、
  图上相邻节点或已有函数定义不能证明实际接线。源码位置绑定受审 baseline。
- **数据传递**：caller 的哪个值成为哪个实参，谁生产、转换、校验和消费；说明关键
  identity/request/attempt/epoch/digest、单位、默认值、缺失和错误的语义（按适用性）。
  返回值/事件由谁接收、如何影响下一步，不能追到内部 helper 就结束。
- **状态和副作用**：进入条件、guard、校验/授权与副作用先后、状态写入/发布/提交点、
  后置不变量和下一步触发者。指出权威状态 owner、重复调用的效果和幂等边界。
- **异步与跨进程边**：区分同步返回、入队、回调、远端执行和完成通知；核对线程/事件
  循环、捕获对象寿命、注册/取消及终态。对跨节点步骤连接发布→检索→验证→接收方
  状态转换，不能用一根本地函数调用箭头掩盖消息与依赖准入。
- **失败与恢复**：在关键跳点说明错误如何传播到消费者，谁负责超时、取消、有限重试、
  部分副作用回收，以及晚到/重复事件如何被拒绝或处理。只展开影响本次设计的反例。

对改动给出同一条链的现状、目标和最小 delta；节点/边标明 existing、planned 或
unverified。planned 边写清拟新增的调用/注册/消息契约，不能给它伪造现有源码位置。
将必要负例和独立 oracle 绑定到链上的触发点、观测点与预期结果，说明其能发现哪种
断链或错误顺序；静态手推不冒充已执行验证。

审计结论必须解释至少一条受影响主链及决定设计成立的分支，指出首个断点、影响到的
调用方/结果、最小修正和未核实的边。没有缺陷时也应交代实际核实的链及其边界。
实现就绪不能建立在关键接线、输入来源、状态 owner 或失败收尾尚不明确的链上；
仅让相关范围保持 DRAFT/BLOCK，其他独立范围继续。具体信息填入已有 FLOW 表，
图只作导航，不能替代逐跳解释。普通局部变量和无关算法细节不需逐行设计。

## Design Checks

检查实际设计能否让接手者实施并验证，按影响范围使用以下问题：
- 每项实现任务的Design binding是否实质覆盖类/文件delta、前后关键签名、字段owner、调用/失败流程与PO，而非只有公开API清单或几个实施动词？
- 用户成果、FR/SC、任务和 PO 是否对应；是否存在无目的机制或机械任务拆分？
- 实现任务是否有产品代码变更，或对具名生产 C++ target 的行为验证？是否误把 API/Design/PDF/evidence 更新拆成独立文档任务？仅当接口、可观察行为或安全契约变化时，文档是否并入对应实现任务？
- 如果代码前仍有未决契约，它是否真实阻塞 API/wire/身份授权/owner 边界，且核查范围、证据和实现依赖方都明确？能并入所属实现任务的，不应保留单独文档阶段。
- 是否已在同一实现审查中做过最小化检查，去除未请求的抽象、依赖、文件、重复逻辑和无关重构，同时完整保留行为、安全、C++ 验证及验收门？
- 类/方法/重要字段的职责、输入来源、失败、寿命、并发、调用方式和注释是否明确？
- 是否按上述 Call-Chain Design Review 逐跳核实实际边并说明关键细节，而不是仅列符号或图？
- 共享机制是否复用，模型/业务逻辑是否留在正确层；旧调用方如何迁移与退出？
- 具体改动范围、前置条件与关键未知是否明确；局部实现选择是否仍有合理空间？
- 验收是否通过真实生产路径与独立判据发现错误，包括必要负例和真实运行？
- 每个逻辑批次是否有稳定、可独立观察的出口，且已列出生产调用方、测试/harness
  oracle、构建注册和 source closure；闭合批次是否会及时验证而不继续吸收无关职责？
- 批次结果是否能分别说明静态发现、编译/链接漏检、运行/测试漏检和可比的构建耗时？
- 文档是否引用唯一契约，避免复制规则、重复报告或测试门槛？

只报告实际问题、位置、影响和处置。DRAFT / BLOCK / READY_FOR_IMPLEMENTATION
仅描述受审范围的设计状态；结构脚本 PASS 不能代替语义审查或产品验收。
能在授权范围内解决的问题直接处理，不为普通设计选择反复请求批准。
