# Design Readiness Review

检查实际设计能否让接手者实施并验证，按影响范围使用以下问题：
- 每项实现任务的Design binding是否实质覆盖类/文件delta、前后关键签名、字段owner、调用/失败流程与PO，而非只有公开API清单或几个实施动词？
- 用户成果、FR/SC、任务和 PO 是否对应；是否存在无目的机制或机械任务拆分？
- 实现任务是否有产品代码变更，或对具名生产 C++ target 的行为验证？是否误把 API/Design/PDF/evidence 更新拆成独立文档任务？仅当接口、可观察行为或安全契约变化时，文档是否并入对应实现任务？
- 如果代码前仍有未决契约，它是否真实阻塞 API/wire/身份授权/owner 边界，且核查范围、证据和实现依赖方都明确？能并入所属实现任务的，不应保留单独文档阶段。
- 是否已在同一实现审查中做过最小化检查，去除未请求的抽象、依赖、文件、重复逻辑和无关重构，同时完整保留行为、安全、C++ 验证及验收门？
- 类/方法/重要字段的职责、输入来源、失败、寿命、并发、调用方式和注释是否明确？
- 共享机制是否复用，模型/业务逻辑是否留在正确层；旧调用方如何迁移与退出？
- 具体改动范围、前置条件与关键未知是否明确；局部实现选择是否仍有合理空间？
- 验收是否通过真实生产路径与独立判据发现错误，包括必要负例和真实运行？
- 每个逻辑批次是否有稳定、可独立观察的出口，且已列出生产调用方、测试/harness
  oracle、构建注册和 source closure；闭合批次是否会及时验证而不继续吸收无关职责？
- 批次结果是否能分别说明静态发现、编译/链接漏检、运行/测试漏检和可比的构建耗时？
- 文档是否引用唯一契约，避免复制规则、重复报告或测试门槛？

只报告实际问题、位置、影响和处置。DRAFT / BLOCK / READY_FOR_IMPLEMENTATION
