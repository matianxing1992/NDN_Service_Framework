## Data-plane result and failure boundary

Stage 0 fetched and verified completely:

```text
bytes: 18,530,194,174
segments: 2,438,184
retransmittedBytes: 0
fetchMs: 259,730.11
```

Stage 0 then loaded its shard on `cuda:0` successfully:

```text
cacheHit: false
diskCacheHit: false
fetch_ms: 259,730.11
load_ms: 88,959.63
cpuFallback: false
```

Stage 1 failed before model loading or CUDA execution after only 630,800 bytes
and 84 segments:

```text
errorType: ArtifactApiError
error: INTERNAL_ERROR: artifact backend failed (RuntimeError): adaptive
segmented fetch failed ... retry budget exhausted after timeout
```

Stage 2 continued fetching independently after the Stage 1 failure. The
request did not produce a complete generation response in the retained
evidence. Stage 2 eventually completed, but only after the Stage 1 failure
released enough Repo service:

```text
bytes: 19,274,718,182
segments: 2,536,148
retransmittedBytes: 92,615
fetchMs: 681,551.86
```

Stage 1 never reached model loading, and no complete distributed generation
response was produced. Therefore this smoke is a Repo/concurrent-fetch failure,
not a Qwen/CUDA inference result.

The failure also exposed a concrete transport defect in the artifact client:
each large-object fetch used an initial window of 8, a maximum window of 128,
a persistence fan-out of 32, a 10-second Interest lifetime, and only five
retries. Three simultaneous shard pulls could therefore occupy the shared
NFD/Repo service with up to 96 pending Interests while a slower shard repeatedly
timed out. The repair changes the default artifact profile to a bounded
4/16/16 window/backlog, a 30-second Interest lifetime, and eight retries, with
bounded environment overrides. The progress-driven total deadline remains
authoritative.

## Interpretation

The first cold request confirms the intended lifecycle separation: request and
ACK/planning/Selection are one durable invocation, while preparation and Repo
fetch are data-plane work. It also exposes a current Repo limitation: three
large concurrent pulls from one Repo node are not fair. Stage 0 occupied the
effective fetch service; Stage 1/2 progressed only very slowly and Stage 1
exhausted its adaptive retry budget. The next validation is to rerun the same
immutable smoke with the bounded fetch profile and verify that all three shards
complete before model loading. This is not a reason to reopen NDNSF collaboration
for every generated token.
