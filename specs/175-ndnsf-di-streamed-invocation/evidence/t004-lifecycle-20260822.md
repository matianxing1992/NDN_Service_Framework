# T004 Lifecycle and Existing-Request Attachment Evidence

Date: 2026-08-22  
Branch: `Experimental`

## Scope

T004 closes the shared lifecycle primitive and its attachment to an already
existing user `PendingCall` or provider pending request key. It does not claim
event publication, exact-Interest consumption, public streaming APIs, ONNX
generation, MiniNDN, SIF, TigerCluster, or performance qualification; those
remain in T005-T028.

The implementation now provides one `StreamInvocationLifecycle` owner with one
`StreamTerminalAuthority`, one user view, and one provider view. Repeated
attachment to the same request context returns the same owner. A deferred
collaboration is accepted only when the existing user call is already marked
deferred; attachment never allocates a request ID or publishes a second
Request. Provider pending cleanup fences an active streamed owner before
releasing its map entry, so expiry cannot silently abandon an active attempt.

The attachment case verifies ordinary and deferred user calls, duplicate
attachment identity, mode mismatch rejection, provider-side owner identity,
shared user/provider terminal authority, and cleanup fencing. The lifecycle
suite covers valid/invalid transitions, duplicate terminal claims, cancellation
races, callback failure, fencing, and bounded queue high-water/deadline
behavior. T004 is therefore implemented and executed; G1 remains blocked until
T005-T007 add transport, delivery, and authorization integration.
