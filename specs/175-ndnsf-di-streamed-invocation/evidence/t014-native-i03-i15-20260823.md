## Subject and correction

Both cases use the production C++ `BeginCollaboration` Request/ACK/plan/
Selection path, `NativeProviderHandler`, the request-scoped epoch coordinator,
the checked-in four-role stateful ONNX fixture, authenticated epoch-specific
DATA_V1 activation/token-feedback objects, the Core bounded stream writer, and
one final-role End/Response owner.

The first I03 draft exposed a false-green condition: the final Provider
returned the exact Response while two intermediate Providers later failed
waiting for activation epoch 8. The qualified implementation fixes this by
carrying a bounded terminal marker from final-role feedback to Stage0 and then
along the existing activation chain. Each upstream role verifies and forwards
the marker without running a ninth ONNX transition. The test gate now requires
all four epoch coordinators to terminate cleanly and fails on any native
Provider exception; a final Response alone cannot pass.

Normal activation and terminal-control bundles have different encoded sizes,
so activation `expectedBytes` is unset. The authenticated DATA_V1 manifest is
the exact byte-count authority, while the sealed capability still bounds bytes
and segments.

I15 uses the same production harness and token oracle but rotates the signed
role-to-Provider mapping. It explicitly verifies that every role differs from
the canonical Provider identity map before accepting the result.
