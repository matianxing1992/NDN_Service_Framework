# B190-06 — Normal Repo r24 log-volume boundary

## Status

`PARTIAL` / `NOT_CLOSED`

## First boundary

The fresh normal Repo run `direct-int8-prep-r24` passed command preflight, MiniNDN/NFD
startup, ACK collection, Selection, placement-bound fetch, and both Provider
`RUNNER_READY` boundaries. It then entered real C++ execution. It was stopped by the
operator after the two Provider logs grew to approximately `0.93 GB` while the root
filesystem had only `2.6 GB` free. The first 512 dependency-fetch events on each Provider
were observed; no ORT/model/protocol error was observed before the stop. The outer Python
wait was interrupted, so the run is not a qualification result.

The cause is in `examples/DI_NativeProviderExecutable.cpp`: every execution-evidence
observer callback serialized the complete `nodeProviderAssignments` list for both
`NDNSF_DI_EXECUTION_EVIDENCE_UPDATE` and `NDNSF_DI_EXECUTION_EVIDENCE_OBSERVED`, even
when the profile and execution state had not changed. The large ORT evidence record is
useful once, but repeating it per token is not required for the C++ execution contract
and can exhaust the host disk.

## Changed gate

Keep the in-memory `ExecutionEvidence` and one full `OBSERVED` record for each meaningful
profile/completion transition. Emit a compact per-epoch `UPDATE` summary containing the
request/provider/runner/status/count fields, without node assignments or profile JSON.
The gate is successful only if the affected C++ target builds, the focused evidence-line
regression passes, and a fresh normal Repo run keeps Provider logs bounded while still
recording ACK, Selection, both runner stages, terminal/EOS, multi-turn KV reuse, and
cleanup. r24 is preserved and not counted as PASS.

A follow-up r25 verified the compact evidence behavior in the real path: both Providers
entered execution, and their logs stayed around `6.6 MB` each while emitting more than
200 compact updates. It was then stopped when the run-scoped encrypted Repo reached about
`734 MB` and host free space fell below the configured `4 GB` guard. The source ONNX file
was confirmed to be a read-only hardlink to the existing immutable source inode, so it was
not an additional physical model copy. The r24/r25 transient encrypted staging was removed
after preserving their logs/configuration/raw evidence; the remaining issue is SIGTERM
cleanup of child processes and run-scoped staging, not model loading.

The launcher now routes SIGTERM through its existing `finally` cleanup path. A focused
Python regression covers this signal bridge; a new run is required to verify process and
encrypted-Repo cleanup in the actual MiniNDN path.
