T003 的原生实现和静态 gate 已完成，但本批不能闭合。`DI_NativeRequester`
现在支持 `turns[]`，在一次 `Runtime → User.prepare → PreparedModel → Conversation`

和 oracle log view；默认 profile 为三轮。

## T003 cache/lease/resident-runner static review (2026-09-22)

本轮只做只读静态审查，没有新增生产代码或 Changed gate。审查入口为 Provider 的
`runnerPreparationFactory`，并沿着 `ProviderArtifactCache::acquireWithRunner()`、
`tryLoadNativeCanonicalOnnxRoleFromCache()`、cold assembly worker 返回和 runner spec
生命周期核对失败/清理顺序。

- `ProviderArtifactKey` 使用 source/root/manifest/initializer/graph、role、`offerDigest`、
  recipe/backend/device/precision/quantization/layout/profile、protection epoch 以及
  grant/provider identity；没有 request id、attempt 或 mutable runner state。不同 Selection
  的 offer digest 变化会产生不同 key，但不能说明 key 被瞬态 request identity 污染。
- normal protected Repo 在没有 `cacheCompatibilitySourceDir` 时，
  `tryLoadNativeCanonicalOnnxRoleFromCache()` 明确返回 miss，以保留 grant-bound encrypted
  semantics。只有 plaintext fixture 或显式 compatibility diagnostic 才进入 recipe-addressed
  assembled-cache；这正是当前 protected material reuse 尚未冻结的安全边界，不属于 T003 可静默
  放宽的修复项。
- cache entry 发布前复制 metadata-only runner template，并清空 `path`/`lifetime`；cache
  不保存第二份 resident model bytes。move-only `ProviderArtifactLease` 的 release callback
  负责 active pin/entry cleanup，Provider 再把 lease 绑定到实际 runner 使用周期。
- assembly worker 返回后，父进程 scrub canonical source/material；protected plaintext 使用
  `NativePlaintextBufferGuard` 和 staging lease。静态上没有发现 idle cache 或异常路径遗漏第二份
  model buffer 的证据；这不等价于承诺 allocator 会立即把 RSS 归还给内核。

因此 H1（cache key 被 request/attempt 污染）和 H2（idle cache 持有第二份模型）被当前代码
反证；H3（assembly 临时对象未释放）没有得到静态支持。结合 run-54/run-57/run-58 的
Provider-0 resident runner 与 Provider-1 assembly/session 重叠，当前剩余边界归类为 H4：两个
resident ORT session/runner 的工作集重叠。没有 terminal、三轮 requester state、C++ oracle 或
qualification PASS；T003 仍 `PARTIAL`，T004 仍 `NOT_STARTED`。后续只能在 T006/T007 的
受控 protected material reuse/resident-session 设计明确后实施并验证，不能在 T003 直接移除
protected cache miss gate。
