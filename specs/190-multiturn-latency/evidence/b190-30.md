## Status

## First boundary and repair

本轮全链路静态复审发现同步 `User::prepare()` 已把
`repositorySourceProvider->lookupPrepared(...)` 接入 `PreparationSpec`，但
`User::prepareAsync()` 在构造同一 `PreparationSpec` 后没有接入该 port。新
Runtime 的异步入口因此会跳过已提交 receipt 查询，继续走 source load 和
prepare-time publication，违反 CD-08 的 query-before-store 入口一致性。

修复只在 `Runtime.cpp` 的异步入口补上与同步入口完全相同的 bounded、deadline-
aware lookup closure；没有改变 Repo identity、publication、授权或 wire 契约。
回归夹具同时把同一个 `RepoSourceProvider` 注入 source provider 和 artifact
publisher，确保第二个 fresh Runtime 的异步调用确实以已提交 receipt 为命中边界。

首次定向运行暴露的是夹具边界：只注入 source provider 时 publication 仍走
Core mock，不能用 Repo `publicationCalls` 证明命中。该失败说明保存在
`.codex-tmp/spec190-b190-30-async-lookup-r1/fixture-boundary.txt`，修正夹具后
才计生产修复结果。

## Changed gate

`fresh Runtime → User::prepareAsync() → lookupPrepared hit → no second Repo
publication/ingest`。

第一轮同步准备产生 `publicationCalls=1`、`missIngests=1`；关闭 Runtime 后以
同一固定 Repo 根创建新的 Runtime，异步准备完成后仍为
`publicationCalls=1`、`missIngests=1`。当前 `ModelPreparationCache` 在 receipt
命中后仍执行一次有界 source read 以重建并校验 native catalog；本 gate 不把这次
本地/Repo 校验读取错误宣称为零字节，也不把它等同于重复 publication 或重新分层。
