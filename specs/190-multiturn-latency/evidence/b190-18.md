# B190-18 Core-owned durable reference recovery gate

## Status

`ADVANCE` / T006 remains `PARTIAL`; T007 remains locked.

## Boundary and root cause

B190-17 proved that a committed Repo ciphertext can be looked up and registered
for Core segment serving, but its lookup still depended on the process-local
`HybridMessageCrypto` state. After a User restart, the Repo object survived
while the opaque key/reference state was not recoverable. A Repo ciphertext
alone therefore could not be treated as a protected hit.

## Implemented scope

`ServiceUser` now owns a small durable, non-secret reference record outside the
Repo ciphertext store. The record is keyed by the stable publication identity
and binds the service, encrypted data name, plaintext digest/size, policy and
protection epochs, opaque key-reference id/version, ciphertext manifest digest,
and serving locator. The store uses an explicit directory
(`NDNSF_DURABLE_KEY_REFERENCE_DIR`, with a user-state fallback), owner-only
permissions, a lock, atomic replacement, strict field validation, and
fail-closed corruption/trailing-data handling.

The durable publish path now performs the following order:

1. look up the Repo durable object and the Core-owned reference;
2. validate current content identity, policy/protection epochs, manifest,
   locator, source ownership and first-range readability;
3. on a valid hit, register the existing range source without key generation,
   encryption, or a second `commitFile`;
4. on a miss, perform the existing cold publish;
5. persist the reference only after Repo commit/read-back, local serving-owner
   registration and expiry scheduling have succeeded.

If the reference is removed or structurally invalid, the existing ciphertext is
not reported as a hit and the path returns
`DURABLE_LOOKUP_METADATA_MISMATCH`.

## Static review and five lanes

The production path was checked with CodeGraph before source inspection. The
independent read-only review-agent pass used the `a0768c74` baseline and the
explicit ServiceUser/test diff. It confirmed the commit/read-back and serving
owner ordering, but returned `BLOCK` for T006 closure.

- `static`: PASS for this atomic ordering/validation scope; review remains
  `BLOCK` for complete T006.
- `compile-link`: PASS for the affected target.
- `runtime-test`: PASS for the named C++ selector and full target suite.
- `unobserved`: real OS process restart, actual wrapped-key/decrypt serving,
  current grant/Selection/placement rebinding, revoke invalidation, Provider
  or assembled hit, precise missing-object fetch, and Qwen/MiniNDN remain
  unobserved.
- `migration`: the normal protected assembler miss is unchanged; no sanitizer
  claim is made because ASan/UBSan remains deferred.

The review also identified two follow-up design risks: the reference is
structurally validated but not independently authenticated/owner-bound, and
policy revoke currently invalidates Hybrid crypto state without invalidating
these durable records. These are not silently counted as fixed here.

## Closure decision

This is a real Changed gate for Core-owned durable reference recovery and
fail-closed missing-reference behavior. It advances T006 but does not satisfy
the full protected-material reuse contract. The next atomic gate must bind
durable reuse to current authorization/Selection/placement and explicit revoke
invalidation before any Provider/assembled hot-hit or T007 resident-session
work begins.
