# B190-15 / T006 stable protected identity and Repo recovery static audit

**Status**: `PARTIAL` / `OPEN_FOR_NEXT_BATCH`
**Updated**: 2026-09-23
**Scope**: inspect the next production boundary after B190-14; no production
code, protected cache miss gate, or Qwen/MiniNDN run was changed.

## First production boundary

B190-14 closes only the authenticated in-process key-reference handoff. The
next boundary is durable identity and owner recovery, not a directory rename:

1. `prepareNativeCanonicalOnnxRole` currently writes protected ciphertext below
   `protected/<role>/<rootPath.filename()>`. `rootPath` is request/staging
   state, so the resulting directory is not stable across runs or processes.
2. `NativeAssemblyArtifactDirectoryOwner` and the Provider cleanup guard retain
   ownership of that directory. Cache eviction/destruction therefore removes
   the only protected ciphertext instead of treating it as a durable object.
   `markNativeArtifactStagingLease` also exposes the protected directory to
   stale staging cleanup.
3. `tryLoadNativeCanonicalOnnxRoleFromCache` deliberately returns a miss for
   normal protected projections. Its existing `assembled/<role>/<recipe>`
   branch is plaintext/compatibility behavior and cannot be enabled for
   protected ciphertext without a key-aware header/manifest check and a
   Provider-side decrypt-to-staging step.
4. `ProviderArtifactKey` still uses `provider|grantName|grantDigest` as its
   protected identity. A legitimate new grant therefore misses even when the
   B190-14 reference tuple is unchanged; replacing it requires the verified
   reference digest to be available before cache acquisition.
5. Core encrypted large-data publication still allocates
   `identity/service/requestId/objectId/version` names and calls the legacy
   transient `commitFile` overload. `LargeDataPublishResult` has no durable
   key-reference or encryption-manifest identity, while `HybridMessageCrypto`
   keeps wrapped send keys in process memory. Repo transparency cannot repair
   this owner/recovery gap by itself.

## Owner-correct next gate

The next atomic implementation must be Core/Repo metadata and recovery:

- extend the durable commit/receipt contract with the already-authenticated
  opaque key-reference identity, protection epoch, encryption-manifest digest
  and serving locator; keep the legacy transient overload unchanged;
- make `ServiceUser` create or recover that metadata and re-register serving
  before returning a durable hit; Repo stores bytes and metadata but never
  unwraps or invents a key;
- add C++ positive/negative cases for same identity, wrong key/epoch,
  corrupted manifest, old boot/KV and active-lease cleanup.

Only after this gate is compile-linked and tested should the protected assembler
use a stable path such as a recipe/reference identity and should
`ProviderArtifactKey` stop using request/grant-instance identity. The protected
miss remains mandatory until then.
