## First boundary

首个控制性缺口在 protected durable identity/serving owner，而不是
`tryLoadNativeCanonicalOnnxRoleFromCache` 的单个条件：

1. `NativeCanonicalOnnxAssembler.cpp::tryLoadNativeCanonicalOnnxRoleFromCache`
   对非 `plaintext-v1` 且非显式 compatibility source 的路径强制 miss。这是
   当前安全门，不能直接删除。
2. `RepoEncryptedLargeDataStore::Source::~Source()` 无条件调用
   `RepoCore::removeIfCurrent`。因此保留目录不能构成 durable Repo hit。
3. `ServiceUser` 的 protected large-data publication 将 wrapped send key 和
   serving source 绑定到当前进程/当前 lease；`HybridMessageCrypto` 的 send
   key 不是跨进程恢复接口。
4. Provider 的 `ProtectedRuntime` 可以用 authority 根据
   `modelManifestDigest + protectionEpoch` 恢复稳定的 content key，但该 key
   只授权 assembled ciphertext；它不能自动恢复 Core large-data 的旧 send key。

因此当前证据只证明“protected cache 命中被安全地挡住”，不证明密文、key
reference、当前 grant 和 serving owner 已经可以在重启后重新绑定。后续任何只
改 cache miss、只保留文件、只复用旧 grant 或只通过 Python fixture 的修复都必须
保持 `PARTIAL`。

### Implementation/wire — gap

  contract; `RepoEncryptedLargeDataStore::Source` therefore cannot distinguish an
  owned request object from a committed reusable object.

  has no authenticated durable key-reference/serving-recovery record.
- `ProviderArtifactKey` has protected identity fields, but the protected disk
  entry is not yet wired to a recovered key-reference and current grant. The
  existing compatibility source directory is intentionally not a production
  protected path.

## Required design closure before production edit

The next Changed gate must freeze, in public C++ contracts, all of the following:

1. `EncryptedLargeDataRangeStore` retention mode and its owner: transient source
   destruction removes only the publication owned by that request; durable commit
   returns a reference whose cleanup is explicit and cannot be triggered by a
   late transient destructor.
2. The Core crypto owner’s durable key-reference/recovery operation. Repo stores
   ciphertext bytes and manifest identity only; it must not receive plaintext,
   private keys, grant JSON, or authority to issue/accept a grant.
3. The protected identity tuple: producer/trust domain, ciphertext digest and
   full encryption/AAD manifest, key identity/version, policy epoch, model/role
   identity, and serving locator. Request ID, attempt, provider boot and old grant
   remain request/runtime bindings, not durable hit identity.
4. New-grant rebinding: a hit is allowed only after current grant verification,
   current Selection/placement checks, key-reference recovery and ciphertext/AAD
   validation. Old grant, revoked/changed key, wrong boot/KV or failed recovery is
   a typed miss/rejection, never a cache hit.
5. Serving lease/cancel/error order: durable bytes survive request completion and
   process owner replacement; active reads pin them; transient plaintext and
   request leases still drain and zeroize on cancel/complete/destruction.

## Target interface freeze

CD-09 now records the target-only retention/key-reference contract. The freeze is intentionally
not a production API change: existing source, grant, request and protected-cache behavior remains
unchanged until a new C++ static review verifies that the Core owner, Repo adapter, Provider serving
lease and negative paths agree on the same identity. The contract requires explicit
`Transient/Durable`, opaque key-reference metadata, ciphertext-only Repo storage, Core-owned serving
recovery, new-grant rebinding and typed fail-closed miss; it forbids request/attempt/boot/KV reuse.
