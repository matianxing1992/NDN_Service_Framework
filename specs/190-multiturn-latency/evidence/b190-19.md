## Architecture and production path

The applicable architecture sources were read in the required order:
`Design/highlevel-design.md`, `docs/architecture.md`,
`docs/ndnsf-core-app-boundary.md`, `docs/NDNSF-DI-runtime-workflow.md`,
`.specify/memory/design-code-convergence.md`, and the active Spec190
`spec.md`/`plan.md`/`tasks.md`/contracts/evidence. The relevant principles are:

- G3/G5: authorization, content identity, mutable policy state and references
  are distinct; cache hits retain current authorization checks.
- G4/D3: each operation, cache, lease and serving owner has an explicit
  lifetime and release owner.
- D2: authorization and Selection precede material fetch; storage readability
  is not execution permission.
- R2/R3/R6: committed objects are durable and recoverable, while references,
  locators and mutable validity remain separately checked.

The current production path is:

`NativeCanonicalArtifactPublisher::prepare/publishUncached` →
`ServiceUser::prepareServiceRequest` →
`ServiceUser::publishEncryptedLargeDataImpl` → Repo durable lookup/commit and
Core `m_largeDataFiles` serving registration → later Core Request/ACK/Selection
and DI role/placement binding → Provider material fetch/assembly/runner.

CodeGraph confirms that `PreparedServiceRequest` currently carries only
`serviceName`, `requestId` and `used`; `prepareServiceRequest()` creates only a
request id. The durable publisher therefore cannot claim that its reuse path
has already performed the later grant, Selection or placement checks. The
current `replyFromLargeDataFile()` also serves a registered range publication
by name without rechecking Controller status.

## Severity-ranked findings

### P1 — first status installation is indistinguishable from version advance

`installControllerStatus()` sets `versionChanged` true when there is no prior
per-service status. Persisted runtime-status restoration therefore calls the
same invalidation path on a valid first restore and can erase durable
references that should be reusable at the restored version. Invalidation must
be conditional on an existing status and a strictly newer Controller version;
same-version restore must remain a hit.

### P1 — publication/reference commit has no policy-epoch fence

A durable publication can start under an older status, commit ciphertext, and
write a reference after a newer status has been installed. The current code
reads `getCurrentPolicyEpoch()` while constructing the reference, so a stale
ciphertext can be recorded with the new epoch. File locking the reference file
does not serialize the Controller-state transition with Repo commit and local
serving registration. The repair needs a service-scoped lifecycle fence:
capture the authorization generation, recheck it before durable commit/reference
publication, and ensure invalidation cannot be overtaken by a late writer.

### P1 — deleting a reference does not stop active local serving

`HybridMessageCrypto::invalidateService()` and the proposed reference-store
invalidation do not remove `m_largeDataFiles`. `replyFromLargeDataFile()` can
therefore continue to answer an old encrypted name after revocation/status
change. Invalidation must retire the Core serving publication for that service
while preserving the committed Repo object; a currently executing Interest may
finish, but future lookup must not find the publication.

### P1 — invalidation I/O must fail closed without escaping status handling

Reference-store lock/read/rename failures can occur after the in-memory status
has been accepted. An exception escaping the status callback would leave an
ambiguous state, while silently continuing would leave an old hit live. The
operation needs a typed result or a durable pending-invalidated fence, explicit
logging, and tests for lock/read-only/corrupt-store failure. It must never turn
an I/O failure into a protected-hit success.

### P2 — service-scoped filtering and concurrency

One identity may have records for multiple services in one reference file.
Invalidation must rewrite only the affected service records under the existing
process mutex and file lock; deleting the whole file would revoke unrelated
services. The same lock order must be used by load, persist and invalidate.

### P2 — synchronous file work on the Face callback

`installControllerStatus()` is reached from the policy-status callback. An
unbounded file rewrite there can delay the Face event loop. The repair must use
bounded records/operations and preserve an explicit completion/failure state;
blind fire-and-forget invalidation is unsafe because it races publication and
serving.

## Changed gate and repair order

The next real Changed gate is **B190-20: policy-transition protected-serving
fence**. It must be one owner-correct C++ unit with this observable exit:

1. install a current status, publish durable service A and service B, and
   confirm both are serving/Repo-committed;
2. install a same-policy-epoch but newer Controller generation for service A;
3. service A's old Interest no longer finds a local publication and its durable
   reference fails closed, while the Repo ciphertext remains committed;
4. service B's reference remains usable;
5. a same-version persisted-status restore does not invalidate either record;
6. a publication paused across the status transition cannot write an old object
   as a reference for the new epoch; failure leaves no false hit and only its
   owned staging is rolled back.

The implementation order is: (a) distinguish first install from newer version,
(b) introduce the service-scoped lifecycle/epoch fence, (c) retire active local
serving entries, (d) implement filtered reference invalidation with typed
fail-closed handling, and (e) add the C++ concurrency/status/serving tests.
Only after this gate passes should T006 address new grant/Selection/placement
binding and real Provider/assembled reuse.
