# B190-09 Native Stable Repo Owner and Historical Stream Boundary

## T004 fixed per-node Repo owner/restart proof — 2026-09-23

T004 was closed with the existing C++ file-backed Repo implementation and a new
native selector; no production change was needed in
`FilesystemRepoStoreBackend.cpp` or `RepoNode.cpp`. The selector uses one fixed
`<deployment>/<node>`-equivalent root and one stable owner identity, then starts
three new child PIDs sequentially. Each process closes by process exit and the
next process reopens the same root.

The selector proved that committed graph/layer/later payloads remain readable,
manifest count and payload bytes remain unchanged, and a range written before a
simulated crash but never committed is not visible after restart. A second live
owner receives `repo-persistence-owned` and cannot mutate the root. Malformed
catalog metadata causes conservative recovery (committed data and uncertain
staging are retained), a root symlink is rejected, and the logical Repo quota
rejects before payload mutation. The run uses small file fixtures and never
loads a model-sized vector.

## Historical T003 stream boundary

2026-09-23, r28 used one direct MiniNDN start, the immutable Qwen candidate/cache,
normal encrypted Repo publication, the installed C++ production binaries, and
`--rounds 3 --max-new-tokens 1025 --require-multi-token`.

The run passed the startup gates, MiniNDN/NFD, Repo publication, ACK, Selection,
placement-bound material fetch, cold assembly, `RUNNER_READY`, and real ONNX CPU
execution on both Providers. Each Provider crossed the old 512-event boundary
(529 and 528 execution updates respectively) with zero
`native epoch token event admission was rejected` events.

The first terminal boundary was instead the authenticated requester timeout:
`requestTimeoutMs=900000` followed by
`NATIVE_STREAM_ORACLE_FAILED: terminal event timeout`. No EOS, terminal response,
conversation checkpoint, KV-reuse turn, or three-round result was observed. Both
Providers shut down through their normal cleanup path. The measured execution rate
was approximately 529 updates in 900 seconds per first turn, so increasing the
timeout would only make the run longer; it is not recorded as a performance fix.
