## First boundary

当前最早未证明边界不是 Repo 是否还能读到密文，而是：一个新的 OS 进程能否在
当前授权和当前 serving owner 下重新注册同一 protected publication，并让生产
Provider 继续走真实 envelope/decrypt 路径。

静态追踪得到的事实如下：

1. `RepoEncryptedLargeDataStore::lookupDurable` 会从固定 Repo 根恢复
   ciphertext range source 和 manifest metadata；它不拥有 key，也不负责授权。
2. `ServiceUser::loadDurableKeyReference` 只恢复 publication、service、digest、
   protection epoch、opaque key-reference 和 serving locator 等非秘密字段。
   `HybridMessageCrypto` 的 send key、wrapped-key cache 和 lease 仍然是进程内状态。
3. `ServiceUser::publishEncryptedLargeDataImpl` 的 durable hit 会重新创建
   `m_largeDataFiles` serving owner，但当前回归只在同一测试进程重新构造
   `ServiceUser`；没有 exec 后的新 Repo owner/Face/KeyChain 证据。
4. 冷发布产生的 `HybridMessageEnvelope` 将 wrapped message key 放入已提交密文
   envelope；`ServiceProvider::fetchAndDecryptLargeDataUntil` 在新进程中理论上可
   从该 envelope 走 inline unwrap，但这个跨进程生产路径尚未被 C++ oracle 观测。
   不能用“Repo 中有文件”或“reference 文件存在”替代该证明。
5. 当前 durable hit 入口仍是 Core large-data publish/rebind，而不是完整的
   `user.prepare(model) → publication query → ACK/Selection/placement` 生产闭环；
   新 grant、Selection、placement 和 revoke 绑定仍是未观测边界。

## Severity-ranked findings

### P1 — no real OS restart serving/decrypt oracle

`DurablePublicationReusesAfterServiceUserRestart` 共享同一个 `RepoCore`、文件
后端对象和测试进程地址空间；它证明了 metadata lookup 和本地 serving re-registration，
不能证明新的 process owner、Face、key cache 和 callback closure 能工作。

**Owner-correct repair**：在现有 Spec189 encrypted Repo target 增加一个
`fork`+`exec` 子进程 selector。父进程完成一次 durable cold publication 后只保留固定
Repo 根和 key-reference 目录；子进程重新构造 Repo backend、Face、ServiceUser，
调用同一生产 durable publish/recovery API，并从 serving prefix 读取并验证完整
envelope。子进程必须报告 `lookup → owner registered → segment served`，父进程再
核对 committed object 数量和 digest 未增长。

### P1 — provider decrypt remains unobserved after the restart gate

静态代码显示 stored envelope 可携带 inline wrapped key，Provider 有对应 fallback，
但现有 Core-only fixture 没有调用真实 `ServiceProvider::fetchAndDecryptLargeData`。
该边界应在 Core restart gate 通过后作为独立 C++ production oracle，不应先修改
key persistence 或把 secret 写进 Repo/reference store。

### P1 — current grant/Selection/placement rebinding is not represented by the Core API

`PreparedServiceRequest` 不携带 grant、Selection 或 placement binding。Core durable
hit 的成功不能被解释为 DI 当前授权成功；Provider 仍必须在 Selection 后用当前
`ProtectedRuntime` 验证 grant 和 role assignment。

### P2 — durable metadata validation is identity validation, not cryptographic key recovery

reference 中的 `keyReferenceId`、manifest digest 和 epoch 能阻止明显错配，但它们
不是 content key。任何后续修复必须继续保持 Repo ciphertext-only、reference
non-secret、旧 grant/KV/boot 不可恢复；不得通过持久化完整旧 request/grant/session key
绕过授权边界。
