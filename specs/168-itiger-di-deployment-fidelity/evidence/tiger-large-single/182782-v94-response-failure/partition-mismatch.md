# v94 reference/stage partition mismatch

The v94 response failure is not evidence of a resource shortfall.  The
96-GiB/node replacement reached `LLM_PIPELINE_QWEN_RUNTIME_READY` on all three
providers with CUDA and `cpuFallbackCount=0`, fetched all three stage packages,
and produced a complete 64-token response.  It failed only at the exact
reference-token gate, diverging at token index 40.

The frozen reference and the deployed stage manifest did not describe the same
layer boundaries:

| Source | Stage 0 | Stage 1 | Stage 2 |
|---|---:|---:|---:|
| `reference.json` `deviceMap` | `[0,18)` | `[18,42)` | `[42,64)` |
| `stage-manifest.json` | `[0,21)` | `[21,42)` | `[42,64)` |

Thus the reference token sequence was generated by a different cross-device
partition than the NDNSF-DI pipeline.  The preparation job now uses an explicit
stage-aligned device map and fails closed if the reference map differs from the
exported ranges.  v94 remains immutable and is not reclassified.

Evidence hashes:

- reference: `sha256:3ee52f5553405556d95f5e8166de88a166b2a3f4a1452c1e0b208e0cf003c1e5`
- stage manifest: `sha256:16de41986564c436a33cd6a292f17f4bd939d0a893c441441022e3b389737f6f`
- generation raw: `sha256:4504acd6e616d6e8673ad72652d9fdcd5a99ad968b8caf8f5cf10a430ab2a882`

The next validation must use a new immutable preparation/campaign identity
created by the corrected preparation code.  It must first prove that the
reference and stage manifests carry identical layer ranges, then run the same
bounded one-prompt large-model request.
