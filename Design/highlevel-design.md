# NDNSF High-Level Design

本文件是四模块共同的高层设计约束，供需求、Spec、代码审查和验收首先对照。四个模块各用约 500–1000 字说明用途、用例、当前设计和必须保持的原则；具体签名、字段及验证记录仍在 [API 参考](api/) 和各 Spec 中维护。用例说明系统应如何工作，不代表每条硬件或模型路径均已验收。当前设计摘要以 2026-09-19 的维护文档、源码及活跃 Spec 为依据。

## 共同原则

| ID | 必须保持的约束 |
| --- | --- |
| G1 | **由 Named Data 驱动跨节点协作。** 请求、选择、依赖、结果和进度以可验证的命名对象表达；Interest 用于获取 Data。定时器、调度和设备操作在本地执行，其跨节点决定通过协议对象传达。不能用共享目录、测试回调或旁路消息替代生产协议后宣称功能完成。 |
| G2 | **通用机制与领域语义分开。** Core 拥有通用调用、授权、协作及传输；UAV 拥有飞行和感知，DI 拥有模型与推理，Repo 拥有对象存储。应用复用公共机制；Core 不反向依赖应用、ONNX 或 GUI。 |
| G3 | **身份、权限、保密和业务正确性分别检查。** 签名有效不等于允许执行，获准服务不等于被本次选中，能解密不等于内容语义正确。来自原生产者、Repo 或网络缓存的对象采用相同的适用验证规则。 |
| G4 | **状态与资源有明确所有者。** 每次操作定义截止时间、取消、终态和释放责任；队列、缓存、准备及暂存有预算。局部等待超时不自动表示远端已取消，网络重传不应重复产生业务副作用。 |
| G5 | **内容身份与可变状态分开。** 内容、版本、生产者和引用绑定可核对；缓存复用必须保留当前授权检查。授权版本、目录版本、请求 attempt 和模型生成状态不得互换；发现旧对象不能让旧状态推进新操作。 |
| G6 | **结论与证据一致。** 代码存在、局部测试、跨进程链路和真实设备/模型验收分别记录。失败必须定位首个可观测边界；不能通过降低安全条件、伪造候选或复用历史结果关闭当前验收。 |

## 1. NDNSF：通用服务框架

**用途与用例。** NDNSF 让调用者通过服务名称寻找并使用当前愿意且能够执行的 Provider，而不必预先固定一台机器。例如，操作员寻找附近可拍照的无人机，应用寻找有足够内存的推理节点，或录像服务寻找有可用空间的 Repo。普通调用解决一次服务执行；多角色协作把多个参与者和命名依赖连接起来。框架可以支持移动设备、边缘或固定服务器，网络环境不限定其应用范围。

**当前设计。** User 发出 Request，Provider 返回 positive 或 negative ACK，User 按策略选择候选并发送 Selection，选中者验证后执行并发布 Response。Request 中的 discovery descriptor 用于判断是否参与；完整应用输入及其密钥按选定接收者交付。Controller 管理服务使用权限与提供权限；当前 KP-ABE 保护面向获授权 Provider 的发现信息，RequestNonce、ProviderChallenge 配合签名验证、权限状态和请求状态参与授权检查。输入及结果使用请求级保护。在线授予更新目标策略和 DKEY；撤销涉及状态更新和相应换钥，实际生效依赖节点获取并安装有效状态，不能收回已披露的数据。

协作路径在 ACK 收集关闭后固定候选快照，由应用策略确定角色、Provider 与依赖，再提交绑定本次请求的计划。Core 检查通用结构及选择上下文，应用负责计划的领域可行性。已有 Targeted、进程内调用、大对象传输和连续流入口，各自有不同前置条件；已知身份或进程内可调用不能自动扩大网络权限。当前组件和协议均有实现，完整能力与验证范围以对应入口的证据为准。

**C1：服务决定必须可验证。** 执行以有效 Selection 或相应调用模式的授权条件为前提；ACK、计划提交、执行完成和结果接受是不同阶段。**C2：框架保持通用且以原生运行时为核心。** 协作策略可替换，但不能绕过候选、权限、依赖及终态规则，也不能将模型或飞行语义下沉进 Core。**C3：数据保护跟随对象用途。** 获授权但未选中的 Provider 可以读取其权限覆盖的发现信息，不因此获得本次完整输入；密钥、名称与请求上下文必须保持绑定。

依据：[当前 Core 设计](current-content.tex)、[Core/应用边界](../docs/ndnsf-core-app-boundary.md)、[Core API](api/core-reference.md)。

## 2. NDNSF-UAV：无人机应用

**用途与用例。** UAV 应用覆盖地面站操作、飞行任务、遥测、视频、录像和感知。操作员可以向指定无人机发送飞行命令、订阅实时画面并回看保存的录像；也可以将巡逻区域分给多架无人机，只对未完成部分重新安排任务。多视角感知的典型用例是在地图上指定目标区域，寻找位置、视野和时间条件合适的无人机采集不同视角，再由具备计算能力的 Provider 分析并返回结果。发现描述提供参与判断所需条件，精确任务输入及访问材料在选定后交付。

**当前设计。** 无人机端和地面站都通过服务容器组合 User/Provider 能力。飞控后端适配 mock、UDP/串口及 MAVLink；视频与遥测使用有会话身份的命名数据流，录像可将原始已签名 packet 保存在 Repo。任务模块管理 mission、分片、attempt 和缺失部分补偿；有限识别 job 管理视图引用、算法和终端报告。多视角代码已有算法接口、确定性测试算法和真实 ONNX 工具路径；默认入口、真实飞行和识别效果的验收必须分别说明，不能把算法工具通过视为整套空中协作已经完成。

视图应使用采集者自己的命名空间和精确引用；分析者发布自己的识别或标注 Data，并引用原图。只增加标注时可复用图像字节并按授权交付解密能力；确实生成了新图像才发布新对象。GPS、姿态、拍摄时间和相机标定共同影响几何解释，单有 GPS 不能保证精确定位。固定相机的视线随机体姿态变化，姿态补偿可辅助解释画面，但不能等同于云台稳定。

**U1：设备安全在执行边界负责。** Core 服务权限、操作员控制权和飞控安全条件分别满足；GUI 按钮状态不能作为后端授权依据。当前部分检查仍在地面站，Drone handler 尚缺相同程度的独立重验，这是待收敛缺口。**U2：任务、媒体与设备状态分开。** 关闭窗口、取消请求、停止视频和停止车辆动作有不同结果；迟到报告不得覆盖新 attempt。**U3：媒体策略符合用途。** 直播可丢弃旧帧以控制延迟，录像与任务证据必须记录缺口并验证完整性。算法只解释感知内容，不接管 Core 的认证或任务终态。

依据：[当前 UAV 设计](current-content.tex)、[UAV API](api/uav-reference.md)、[UAV 文档](../docs/NDNSF-UAV/)。

## 3. NDNSF-DistributedRepo：分布式命名对象存储

**用途与用例。** Repo 保存和提供命名对象。无人机可暂存加密录像并显式归档；DI 可发布一次模型材料，供选中 Provider 按分配读取。只有完成约定的持久提交，才能依赖服务器在原应用退出后继续提供数据；临时来源不作此保证。Repo 不解释视频、模型或张量语义。

**当前设计。** RepoCore 提供对象、manifest、原始 Data packet、范围存储和目录操作；客户端与网络服务接入 NDNSF，部分编排仍在 Python。已有 SQLite、缓存和文件后端，以及 `repoMode`、`acceptsBackupReplica` 字段，但不能据此声称下述模式边界已在所有入口实现。

**已接受的模式约束。** 两种模式共享存储与读取机制，区别是生命周期和责任，而非是否使用磁盘。in-app mode 由所属应用管理，允许本地发布、应用主动读取后的缓存及对外提供已有 Data；不接受外部插入、上传或副本放置，不自动复制或修复，不计入持久副本数。应用可通过 RepoClient 显式归档到 server。server mode 独立长期运行，负责授权写入、持久提交和重启恢复；副本维护按明确策略执行。客户端选择与接收端均检查模式，不能只靠能力声明。现有不符合入口须迁移，不能仅改字段名称。

**R1：对象身份稳定。** 原始 Data 保留生产者名称、签名与 wire bytes；副本定位不改变内容身份或验证规则。ForwardingHint 只引导转发，须配套可达 locator 和原名 Interest 到 Repo 的本地路由，不能代替授权。**R2：成功由提交契约决定。** 授权和选择后获取、校验、提交，以绑定操作及对象的 receipt 计算符合保存条件的副本数；重复操作幂等、冲突拒绝、部分成功可查询，staging 不作为完整对象交付。**R3：目录和资源可恢复。** 目录快照与版本一致，缺失增量显式恢复；预算覆盖提交、暂存和预留，删除尊重活跃读取，缓存命中不证明某服务器持有副本。**R4：保持领域无关。** 应用管理模型、录像及执行语义，Repo 可读性不等于执行权限。**R5：模式约束不可旁路。** 本地应用写入与远端管理分开；所有写入、恢复和修复入口执行同一模式边界。

**R6：对象引用与副本位置分离。** 存储成功后返回可复用的对象 handle：不可变部分绑定 manifest 名称、摘要及大小/分段信息；可更新部分记录 Repo 身份、ForwardingHint、位置记录版本与有效期，并关联提交 receipt 和可选的位置更新入口。位置记录须由获授权的发布者签名并绑定对象身份；副本迁移不改变内容摘要。handle 不是授权凭证，不默认携带明文解密密钥，也不保证数据永久存在。插入时指向生产者的 hint 与读取时指向副本的 hint 分开管理。客户端验证引用和位置记录，以原始 Data 名称及选定 hint 读取，在总 deadline 内刷新位置或切换副本；仍须验证原始 Data。路由部署须同时满足 locator 可达及原名 Interest 到服务进程的转发，不默认注册 `/` 捕获无关流量。

依据：[当前 Repo 设计](current-content.tex)、[Repo API](api/repo-reference.md)、[两模式分析与协议参考](repo-two-mode-analysis-20260919.md)。模式及引用约束为用户接受的方向，具体 API 与迁移验收仍须下层设计，不表示当前/冻结目标 PDF 已同步实现。

## 4. NDNSF-DI：分布式推理

**用途与用例。** DI 将模型执行映射到当前可用的计算资源。例如，摄像头应用把图像交给一个合适的 GPU Provider；模型超过单节点资源时，由多个节点承担合法的模型分片；语言模型在多轮生成中复用匹配的 KV 状态，避免重复计算已有前缀。是否拆分及采用顺序、分支或张量并行，取决于模型适配器、运行后端和通信成本，不能假设任意 ONNX 模型都支持任意切分。

**当前设计。** 原生 Runtime/User 提供模型准备和请求入口，PreparedModel 保存可复用的模型身份与必要 lease；模型适配器负责图、输入、切分与物化语义，放置策略根据有效 ACK、设备、资源和可信驻留信息提出分配。准备阶段发布与放置无关的 canonical graph、initializer 及材料索引；普通请求携带不可变引用和本次输入，计划将角色、参与者与命名依赖绑定到本次执行。选中 Provider 经授权后读取分配材料、组装 runner 并执行，后继角色消费验证后的张量 Data，终端角色产生结果。

当前材料 consumer 已有选择性读取和局部 C++ 测试；真实 Qwen 双 Provider 的完整请求、输出及资源回收仍由活跃 Spec 验收，不能写成已经完成。不可变模型材料可缓存；KV 则是模型生成、运行时保存并再次提供给模型的可变状态，复用必须匹配模型、角色、前缀、位置、布局与安全域。模型驻留不等于 KV 有效。跨角色传递激活张量、必要的生成反馈及状态引用，具体数据由模型执行图决定，不默认每轮搬运全部权重或全部 KV。

**Repo 使用约束。** 准备阶段可由应用内 Repo 发布不可变材料，或显式提交到 server Repo；普通推理不强制部署长期 server，也不默认复制整模型。应用内来源的 owner 必须在仍需读取时保持 Data 服务及资源存活；跨应用退出的复用须先取得所需 server 提交凭据。选中 Provider 主动获取分配材料并写入自己的本地缓存，不是接受外部插入，也不自动成为持久副本。准备材料供存储服务器归档不等于允许未选中计算 Provider 预取或组装模型。激活、结果与 KV 的保留由请求/会话约束；需要归档时由 DI 显式发布受保护的不可变对象，不能让通用 Repo 自动复制可变 KV。

PreparedModel 应持有上述材料引用，将不可变材料身份与可更新来源位置分开。切换应用内源或 server 副本不改变模型/材料摘要，不绕过本次授权、Selection 和 placement 检查。临时来源的 lease 由本地 owner 管理，不能把可传递 handle 当作远端保活保证；位置更新也不延长保存期限。

**D1：原生执行只有一套权威状态。** C++ 拥有准备、规划验证、授权接线、执行和终态；Python 负责薄绑定、离线工具及实验编排，兼容入口不得成为绕过原生契约的另一套实现。**D2：先授权和选择，再为本次分配取材。** 缓存命中仍检查当前权限与 placement；未选中节点不能因能力探测而预取、组装整模型。**D3：控制成本和生命周期。** 准备、传输、runner、模型缓存及 KV 分别计量，取消和失败释放本次资源；同一内容可复用，但旧 attempt 和旧会话状态不能推进新执行。**D4：分片正确性由 DI 验证。** Core 检查通信和通用依赖，张量形状、模型语义及数值结果由 DI 与测试 oracle 负责。

依据：[当前 DI 设计](current-content.tex)、[DI API](api/di-reference.md)、[准备模型契约](../specs/185-prepared-model-runtime/contracts/public-api.md)、[活跃验证计划](../specs/189-qwen-two-provider-minindn/plan.md)。

## 编译、安装与 MiniNDN 实验约束

**B1：NDNSF 自有目标由仓库根 Waf 统一管理。** Core、UAV、Repo、DI 的原生库、应用及相应测试目标使用根目录 `waf`/`wscript` 完成配置、构建与安装，子模块通过该构建图组织依赖，不维护另一套竞争的原生构建入口。Python 打包等必要工具可按维护流程调用，但不得自行复制一套原生核心编译逻辑。构建目录保存中间产物，安装步骤负责将可运行软件交付到声明的系统安装位置。

**B2：外部依赖由各自项目的构建系统安装。** NDNSF 的 Waf 检查并使用已经安装的依赖，不把 NAC-ABE、NDN-SVS 等外部源码纳入自身目标图。应说“各自维护的构建系统”，而不是要求它们全部使用 Waf：当前维护入口中 NDN-SVS 使用其 Waf，NAC-ABE 使用其 CMake。顶层安装脚本可以编排这些项目的安装顺序、检查版本和生成回执；编译安装责任仍属于各项目，不能手工复制几份头文件或库来代替完整安装。

**B3：构建与运行使用明确且一致的已安装依赖。** 在每台机器上声明编译器、头文件、库、安装前缀及 ABI，核对真实路径和版本/摘要；不能混用 checkout、历史 staging 或临时安装目录中的同名库。修改后先构建受影响目标，再按维护流程安装并验证其运行时依赖。外部依赖只有缺失、版本不符或 ABI 改变时才需要重建，不随每次 NDNSF 修改重复编译。具体机器路径放在[依赖闭包文档](../docs/native-dependency-closure.md)，不在此固化某一台机器的版本。

**M1：所有 MiniNDN 实验运行系统级已安装的软件。** NFD、NDNSF 库、User/Provider/Controller 应用、worker、被测 Python 模块及实验调用的原生辅助程序，都必须从声明的系统安装位置解析；不能直接执行 `build-*`、源码 checkout、`/tmp` 或 `.codex-tmp` 中的被测产物，也不能用 `LD_LIBRARY_PATH`、`PYTHONPATH`、RPATH 或软链接将其暗中引入。启动前记录程序及实际加载库的真实路径、版本/摘要和安装回执；校验失败即停止。同一运行期间不更换该运行使用的安装产物。构建树单元测试可以先做，但不能作为 MiniNDN 的软件来源或替代其验收。

**M2：临时运行数据与软件安装分开。** 本次运行的配置、身份材料、日志、结果、模型输入、Repo 数据和 staging 可以保存在独立运行目录；禁止的是临时软件和库，不是实验必需的临时数据。受版本管理的拓扑/启动脚本可以从仓库执行，但只编排已安装的软件，不在启动时临时编译、补丁替换或注入另一套业务实现。采用容器时，系统安装位置指镜像内声明的 SDK/应用安装位置，同样不得借用宿主构建树产物。

**M3：新增安装要求按真实入口收敛。** 现有启动器若仍使用构建树应用或 worker，应登记为待迁移并修正安装规则；不能仅修改文档就称已经符合 M1。历史实验保留原始身份和结论，后续所有 MiniNDN 运行执行本约束。安装成功、网络启动、协议执行及最终业务结果分别验证。

## SIF 构建与复用约束

**S1：先构建并封存可复用的 base SIF。** base 包含四模块及绑定所需的全部已声明外部依赖、构建工具链、头文件、库、pkg-config 信息和 Python ABI；外部依赖仍由各自构建系统安装。NDNSF 自有库、应用和绑定不进入 base。base 必须验证实际编译、链接、加载和必要运行能力，再按摘要封存；保存依赖清单、构建输入和验证记录，不能只因 NFD 或 Python 启动成功就认定依赖齐全。模型、私钥和本次运行数据单独管理。

**S2：日常修改只重建 NDNSF 层，生成新的完整 SIF。** 固定 base 摘要和本次完整源码身份，在使用该 base 的容器构建环境内，以根 Waf 构建、安装受影响的 NDNSF 目标及必要的绑定，然后封装新的 `runtime.sif`。不得复制宿主编译的库、Python 扩展或 venv 充当容器产物，也不得在 NDNSF 阶段临时下载、安装或重编外部依赖。SIF 是只读交付物；“在 base 上加”指从它派生新镜像，不是原地修改旧 base。最终 SIF 包含已声明运行软件，运行时不依赖相邻 base 文件、外置应用包、源码树或构建缓存；模型、配置、密钥及输出可显式挂载。宿主内核、Apptainer 和 GPU 驱动兼容性仍是平台条件。

**S3：按依赖身份决定是否复用。** 仅 NDNSF 源码改变且依赖契约不变时复用 base；依赖集合、版本、编译选项、工具链或 ABI 改变时，先基于现有 base 补齐或重建受影响依赖，生成并验证新 base，旧版保留。增量对象缓存只有在 base、工具链、选项和依赖身份匹配时才可复用，否则重编受影响消费者。该方式避免反复构建稳定依赖，但最终 SIF 仍需重新封装和验证，不能保证每次仅花费源码编译时间。

流程为：`验证/封存 base.sif → 容器内 Waf 构建与安装 NDNSF → 新 runtime.sif → 最终镜像依赖检查与规定测试`。复用 [TigerCluster 维护入口](../Experiments/TigerCluster/README.md)、[base 构建说明](../Experiments/TigerCluster/docs/base-sif-build.md)和 [SIF 构建流程](../Experiments/TigerCluster/docs/sif-build.md)，不新增平行脚本；当前统一使用 Apptainer 1.5.3。按既定分工由实验机执行镜像构建和集群实验。base 验证、NDNSF 构建、MiniNDN 与集群验收分别记录；本节规定交付方式，不代表全部脚本和已有镜像已完成相应验收。

## 变更如何遵守本文件

所有四模块的功能、修复、重构、性能优化、配置和实验入口变更，先对照 G1–G6、对应模块原则及适用的 B1–B3、M1–M3、S1–S3。在 Spec 或变更记录中写清：适用原则 ID、影响的 owner/调用链、如何保持原则、验证证据和残留缺口；无行为影响的文档修改可简记“不改变原则”，无需新建 Spec。

当前摘要描述事实；“必须保持的约束”和 C/U/R/D、B/M/S 原则约束后续设计。现有实现若违反原则，应记录缺口并修复，不能把现有行为反写成原则。任何已有目标、Spec 或实现与本文件冲突时，应先显式说明冲突并收敛；原则变更必须经用户明确接受，同时记录理由、影响及迁移方式。不得为了让局部测试通过、缩小实验成本或迁就既有代码而静默放宽原则。

本文件是人工审查依据，不能自动证明每次改动都符合设计。检查应沿生产调用链验证适用原则；局部通过不能替代端到端验收。当前摘要随实际实现更新，原则则保持稳定。维护流程见 [MANAGEMENT.md](MANAGEMENT.md)；具体缺陷、临时实验和详细字段留在下层文档，避免本文件再次膨胀。
