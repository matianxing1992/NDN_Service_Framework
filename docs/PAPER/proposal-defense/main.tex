\begin{abstract}

Service-oriented applications increasingly operate across dynamic collections of edge devices, robots, cloud resources, storage systems, and users. Existing service frameworks provide useful programming abstractions but remain largely host-centric and channel-centric, requiring application developers to repeatedly address mobility, intermittent connectivity, multi-provider coordination, access control, and data authentication at the application layer.

Named Data Networking (NDN) offers a data-centric communication model based on named and authenticated data, making it well suited for dynamic and distributed environments. However, NDN currently lacks a general service framework that supports secure service invocation, provider collaboration, and dynamic service management.

This dissertation proposes the Named Data Networking Service Framework (NDNSF), a data-centric service framework for secure, collaborative, and dynamic service-oriented applications. We have developed the first version of NDNSF, which provides an intuitive service-oriented API, NDN-based service messaging, multi-provider selection, selective acknowledgment, adaptive admission control, and data-centric access control. While this initial design establishes the foundation for service-oriented communication over NDN, it does not yet fully support collaborative execution among multiple providers or application-driven service composition.

To address these limitations, this dissertation proposes three major extensions. First, NDNSF will be extended with provider-collaboration mechanisms, including targeted invocation, service composition, and large-object references. Second, a UAV networking application will be developed to evaluate NDNSF in collaborative sensing, control, and mission-execution scenarios. Third, a distributed AI inference application will be developed to evaluate NDNSF in coordinating model shards, runtime artifacts, and inference services.

The central hypothesis is that combining NDN's data-centric communication model with service-level abstractions, provider collaboration, and data-centric authorization can reduce the complexity of building distributed service-oriented applications while improving reliability and security under mobility, intermittent connectivity, provider heterogeneity, and collaborative execution. The core contribution of this dissertation is the design, implementation, and evaluation of NDNSF, while the UAV and distributed inference applications serve as validation workloads that both demonstrate and refine the framework.

\begin{keywords}
Named Data Networking, service-oriented applications, data-centric security,
UAV networks, distributed AI inference, provider collaboration
\end{keywords}

\end{abstract}

\section{Motivation}

Modern networked applications are increasingly organized around services rather
than monolithic programs. A mobile robot may expose telemetry, perception, and
flight-control services. A ground station may provide object detection,
mapping, mission planning, and storage services. Edge devices may request AI
inference services from nearby accelerators or cloud nodes. In each case, the
application developer wants to invoke named capabilities without manually
binding every operation to a fixed host address, a long-lived channel, and a
single provider.

Today's service frameworks provide valuable engineering tools, but the
underlying network model remains primarily host-centric. Remote procedure call
(RPC) systems, REST services, and microservice platforms typically identify
service endpoints by host addresses, ports, or channel endpoints. Robotics
middleware provides publish-subscribe or request-response communication, but
often assumes an operational domain where identity, trust, network reachability,
and service discovery are configured outside the service invocation itself.
When applications become mobile, intermittent, multi-provider, and
security-sensitive, developers must rebuild mechanisms for discovery, retry,
authorization, integrity verification, data retrieval, and provider selection.

Named Data Networking (NDN) offers a different foundation. NDN names data
directly, secures Data packets directly, and decouples retrieval from fixed
endpoints. These properties naturally match service-oriented applications in
which users care about a named service, a named model artifact, a named
telemetry object, or a named video segment rather than a particular IP
connection. However, NDN by itself is a networking architecture, not a complete
service framework. Application developers still need a runtime that defines how
to publish service requests, authorize users and providers, select one or more
providers, protect service data, and support higher-level collaboration.

This gap also emerged from the application-driven development in this
dissertation. Building the UAV application exposed the need for stable service
selection, command authorization, telemetry freshness, local service
composition, and large video/recording object handling. Building the
distributed inference workload exposed the need to coordinate artifact
provisioning, tensor dependencies, provider roles, and large intermediate data.
These experiences motivate treating the gap as a framework problem rather than
as isolated application glue code.

\section{NDN Background and Building Blocks}

This proposal assumes several NDN concepts, but they are used here for a
specific purpose: to explain why NDNSF is a service framework rather than
another host-centric RPC layer. NDN is data-driven: a consumer sends an
Interest packet for a named object, and the network returns a matching Data
packet from a producer, cache, or other available source~\cite{ndn}. This
simple exchange already differs from IP service invocation. The application
names what it wants, not the host that should send it; the returned Data packet
is independently named and signed; and retrieval can succeed even when the
original producer is not on the same path as the consumer.

NDN forwarders maintain three data structures that are important for NDNSF's
design. The Forwarding Information Base (FIB) forwards Interests by name
prefix. The Pending Interest Table (PIT) records unsatisfied Interests and
aggregates multiple Interests for the same name, allowing one returned Data
packet to satisfy multiple consumers. The Content Store (CS) caches Data
packets for future retrieval. Together, these structures support stateful
forwarding, in-network caching, multicast-style delivery, and adaptive
retrieval under mobility or failures~\cite{yi2013case}. For service
applications, this means that service-related data can be named and retrieved
independently of a fixed address or connection, but it does not by itself
define service invocation semantics.

NDN also adopts a data-centric security model. Each Data packet carries a
producer signature, allowing consumers to verify integrity and producer
authenticity regardless of whether the Data came from the original producer, an
in-network cache, or a repository~\cite{ndn}. This property is central to
NDNSF: service requests, ACKs, selections, responses, permissions, and large
artifacts can all be treated as named and verifiable objects. However,
signatures alone do not decide who is allowed to call a service, which provider
is authorized to offer it, or which attributes should protect each service
message. Those higher-level decisions are framework responsibilities.

Data-driven retrieval and in-network caching are useful, but service
invocation needs more than fetching a single object. Multiple providers may
need to learn that a request has been published, users may need to collect ACK
metadata before selecting providers, and long-running work may need status
diagnosis. NDNSF therefore uses NDN Sync, especially State Vector Sync as
implemented by NDN-SVS, to let users and providers discover newly published
service messages without binding the service to one fixed endpoint
~\cite{li2018brief,moll2022sok,ndnsvs-github}. In NDNSF, Sync is not the
service semantics itself; it is the dissemination substrate over which the
framework publishes Request, ACK, Selection, and Response messages as named
Data.

The implementation is built on the standard NDN software stack. NFD provides
the local forwarder and face abstraction, while \texttt{ndn-cxx} provides the
C++ application library for names, packets, faces, signing, validation, and
segmented object retrieval~\cite{ndn-cxx}. These libraries allow NDNSF to use
ordinary NDN names and packets rather than inventing a separate transport
format. They also make it possible for applications to pass large artifacts by
reference: models, video recordings, images, logs, and intermediate inference
data can be segmented into named Data packets, signed, optionally encrypted,
retrieved by name, and verified outside the small service-request payload.

For access control, NDNSF builds on NAC-ABE, which combines NDN naming with
attribute-based encryption so that service-level authorization can be expressed
over names rather than transport connections~\cite{dulal2023nacabe}. NDNSF uses this
capability together with controller-issued permissions, service-level
attributes, and per-invocation tokens. The result is that NDN supplies the
data-centric communication substrate, while NDNSF supplies the service-layer
runtime: who may call a service, who may provide it, how providers are
selected, how messages are protected, and how large named objects are attached
to service workflows.

\section{Research Gap}

The research gap is therefore between NDN communication primitives and
service-oriented application semantics. NDN provides named Data, signatures,
caching, forwarding state, segmented retrieval, and Sync-based discovery. It
does not by itself define how a user invokes a named service, how authorized
providers advertise readiness, how ACK metadata is collected, how one or more
providers are selected, how replay is prevented, or how large objects are
attached to a service workflow. NDNSF addresses this gap by treating these
functions as reusable framework mechanisms rather than application-specific
glue code.

\section{Thesis Statement}

This dissertation argues that dynamic service-oriented applications expose a
recurring mismatch with host-centric service frameworks: applications want to
operate on named services, named capabilities, named data, and verifiable
results, while the network stack usually exposes addresses, channels, and
endpoints. A data-centric service framework can close this gap by making
service invocation, authorization, provider selection, collaboration, and
large-object retrieval explicit framework-level abstractions over NDN names and
verifiable Data packets.

NDNSF v0.1 is a completed core contribution of this dissertation and
demonstrates the feasibility of this direction. The remaining dissertation work
extends this foundation into a framework for real dynamic service applications
and evaluates it through two high-pressure domains with different service
requirements:

\begin{itemize}
  \item \textbf{UAV network applications} represent mobile, command-sensitive,
  real-time service-container workloads, where intermittent connectivity,
  command authorization, telemetry, live video, recording, object detection,
  and multi-UAV missions must be coordinated across a ground station and
  multiple drones.
  \item \textbf{Distributed AI inference} represents artifact-heavy,
  multi-stage compute/data collaboration workloads, where model shards, runtime
  artifacts, intermediate tensors, large-data objects, and heterogeneous inference
  providers must be selected, verified, and coordinated.
\end{itemize}

\section{Research Questions}

The dissertation is organized around the following research questions.

\begin{enumerate}[label=RQ\arabic*., leftmargin=*]
  \item What classes of mobility, discovery, security, and data-retrieval
  problems are structural consequences of host-centric service frameworks, and
  which of them can be reduced by data-centric service naming and verifiable
  Data?
  \item How should NDNSF expose service invocation, authorization, provider
  selection, collaboration, and large-object retrieval as generic framework
  abstractions without forcing each application to design a custom NDN
  protocol?
  \item What reliability, security, and latency tradeoffs arise when NDN
  service requests are published to multiple providers and resolved through ACK
  metadata, provider selection, and collaboration, and how should supporting
  mechanisms such as Targeted invocation and compensation be used?
  \item How can UAV network applications evaluate NDNSF under mobile,
  command-sensitive, real-time service-container workloads?
  \item How can distributed AI inference evaluate NDNSF under artifact-heavy,
  multi-stage compute/data collaboration workloads?
\end{enumerate}

\subsection{Expected Answer Shape}

The dissertation is expected to answer these questions in the following form.
RQ1 should identify a set of recurring service-application problems that are
not merely implementation gaps in existing systems, but consequences of
binding services to hosts, sessions, or channels. RQ2 should show that NDNSF
can expose service invocation, authorization, provider selection, and provider
collaboration as reusable framework mechanisms, with local composition and
large-data references serving as supporting abstractions rather than
application-specific NDN protocols. RQ3 should characterize when
one-to-many request publication, ACK metadata, provider selection, and provider
collaboration improve reliability, and when supporting mechanisms such as
Targeted invocation or compensation are needed to control latency and recovery
costs without weakening security checks. RQ4 should show that UAV workloads exercise the same framework
mechanisms under mobility, command sensitivity, real-time video, and
multi-drone collaboration. RQ5 should show that distributed inference exercises
the same mechanisms under artifact provisioning, tensor dependency exchange,
provider role assignment, and long-running distributed execution.

\section{Expected Contributions}

The expected dissertation contributions are:

  \item A review and gap analysis of service-oriented application frameworks

  \item The design and implementation of NDNSF as a generic dynamic C++ service

  \item Extensions to NDNSF centered on provider collaboration, with

\section{Proposal Scope Boundary}

For clarity, this proposal treats NDNSF v0.1 as a completed core contribution
of the dissertation, not as the final complete system. NDNSF v0.1 establishes
the basic architecture and feasibility of a data-centric service framework. The
remaining dissertation work extends this foundation into an
application-validated framework. The main framework extension is provider
collaboration: how multiple authorized providers discover requests, advertise
capabilities, are selected, exchange state or artifacts, and jointly complete a
service task. Targeted invocation, trusted local invocation, and large-data
references are treated as supporting mechanisms that make this collaborative
service model practical under low-latency, same-process composition, and
large-object workloads. These mechanisms are not UAV-only or AI-only features;
they are proposed NDNSF framework mechanisms whose usefulness will be evaluated
through two demanding application classes.

The core dissertation question is therefore not whether two applications can
be built, but whether NDNSF can provide reusable data-centric service
mechanisms that remain valid across two very different workloads.

The UAV application is used to validate NDNSF as a service-container framework
for mobile, command-sensitive, real-time systems. Its design exercises typed
telemetry, mission, video, and safety information; Targeted flight-control
commands; adaptive live video; encrypted local recording; object-detection
service composition; and multi-drone patrol workflows. The DistributedInference
application is used to validate NDNSF as a framework for artifact-heavy,
multi-stage compute/data collaboration. Its design exercises automatic model
plan generation, reference-based model and activation artifacts, predictable
prefetchable object names, and dependency-driven execution over tensor DAGs.
The dissertation therefore does not present UAV and DistributedInference as
isolated demos; it uses them as two complementary stress tests for the same
data-centric service framework thesis.

These applications also contribute requirements back to NDNSF. The UAV
workload stresses low-latency command invocation, structured command status,
service-container composition, and large-data video references, while the
DistributedInference workload stresses dependency-driven collaboration,
artifact references, provider role assignment, and long-running selection
diagnosis. Thus the application work has two roles in the dissertation: it is
valuable in its own domains, and it is the primary method for validating and
refining provider collaboration as the central NDNSF extension.

\chapter{Frameworks for Service-Oriented Applications}
\label{chap:soa}

\section{Purpose of This Review}

This chapter is not intended to be a broad survey of every service framework.
Instead, it reviews what existing systems have already achieved and identifies
the open issues that motivate NDNSF. The key question is not whether systems
such as gRPC, ROS, microservices, or NDN Service Call are useful; they clearly
are. The key question is why dynamic, secure, collaborative applications still
require another framework despite the existence of those systems.

\section{Host-Centric RPC and Microservice Frameworks}

RPC systems such as gRPC~\cite{grpc}, HTTP/REST systems~\cite{fielding2000rest},
and microservice platforms have become the dominant way to build distributed
software. They provide typed APIs, transport bindings, load balancing, service
registration, and production tooling. These systems work very well when
services can be identified by stable endpoints, when channels can be
established and maintained, and when security can be expressed as channel
security plus service-side authorization.

However, the abstraction becomes less natural for applications with mobility
and intermittent connectivity. A user of a UAV video service may care about the
latest frames from drone A, not whether drone A is currently reachable through
a particular IP address. A distributed inference client may care about the
service name for a model stage, not a fixed GPU server. A mission-planning
application may need any available drone that satisfies a role, not exactly one
preconfigured endpoint. Host-centric frameworks can support these scenarios,
but the burden shifts to external discovery, retry, state tracking, and
application-specific coordination.

\subsection{What These Systems Solve}

RPC and microservice systems solve several problems that NDNSF should not
ignore. First, they give developers a familiar programming model: a service has
an interface, a request type, a response type, error handling, and often a
deadline. Second, production systems around gRPC and REST provide mature
tooling for load balancing, logging, monitoring, deployment, and versioning.
Third, channel security such as TLS gives a practical and widely deployed way
to protect client-server communication. For stable cloud services, these
features are often sufficient.

NDNSF does not attempt to replace this engineering knowledge. Instead, it asks
which assumptions break when service providers are mobile, intermittently
connected, replicated, or embedded in resource-constrained edge environments.
In these settings, a service call is not only a channel operation. It is also a
decision about which provider is currently authorized, reachable, capable, and
worth selecting. Existing host-centric frameworks can implement this behavior,
but the logic is typically distributed across service discovery systems,
load-balancers, application retries, middleware plugins, and service-specific
policy code.

\subsection{Open Issues for NDNSF}

The first issue is endpoint dependence. Even if modern service meshes hide IP
addresses behind logical service names, the underlying communication still
depends on reaching an endpoint through host-centric routing. The second issue
is data lifetime. Once a response, video chunk, model shard, or telemetry log is
stored outside the original channel, applications must add their own
verification and encryption model. The third issue is provider multiplicity.
RPC normally selects a single server before the request is sent; NDNSF instead
allows multiple providers to observe a request, decide whether to acknowledge
it, and expose metadata that helps the user choose. These differences motivate
a data-centric service framework rather than another IP endpoint wrapper.

\section{Robotics Middleware and Service Composition}

Robotics middleware, including ROS and ROS2~\cite{ros,ros2}, provides a more
application-aware model for robot components. Nodes can publish topics, call
services, and interact through standardized message types. ROS2 improves
quality-of-service control and deployment flexibility compared with earlier
ROS systems. These frameworks are important precedents for UAV applications
because they treat sensors, control, telemetry, and perception as composable
modules.

The remaining gap is that robotics middleware is not a general data-centric
network security framework. Trust anchors, certificate deployment, data-at-rest
protection, multi-provider service selection, and cross-domain service
authorization are not the main abstractions. In addition, a UAV application
deployed across a ground station, multiple drones, and intermittent wireless
links still needs naming, verification, and recovery mechanisms that are robust
outside a single local robotics domain.

\subsection{Lessons for UAV Service Containers}

ROS is particularly important for this dissertation because it shows that
robotics applications are naturally service-oriented. A UAV system is not a
single communication flow. It contains flight-control commands, telemetry
streams, camera frames, mapping, mission planning, object detection, logging,
and health monitoring. ROS-style composition validates the idea that UAV
software should be decomposed into services.

However, NDNSF targets a different layer. ROS and ROS2 are strong middleware
systems for local and distributed robot components, while NDNSF focuses on
named, secure, network-visible service invocation over NDN. In the proposed
UAV application, the drone app can still be viewed as a service container, but
external interactions such as ground-station commands, telemetry discovery,
video retrieval, and cross-drone collaboration use NDNSF service names and
data-centric verification. This distinction is important: NDNSF is not a
replacement for flight controllers or robotics middleware, but a network
service framework that can connect such components across dynamic NDN
environments.

\section{Message Queues and Event Systems}

Message queues and publish-subscribe systems decouple producers and consumers
in time~\cite{messagequeue}. They are useful for telemetry, logs,
asynchronous workflows, and elastic back-end processing. This is relevant to
NDNSF because many service applications include both request-response actions
and event streams. For example, a drone may receive a command as a service
request while publishing telemetry or video metadata asynchronously. A
distributed inference pipeline may publish intermediate results and execution
events while serving user requests.

However, many message queue deployments rely on brokers or logically
centralized infrastructure. Security is often enforced by broker access control
and channel encryption rather than by data objects that remain verifiable
wherever they are stored or forwarded. For mobile or disconnected edge
environments, broker availability and placement can become a limiting
assumption. Moreover, queues do not by themselves define how a user should
choose among multiple providers, verify that a provider is authorized to serve
a specific service, or retrieve large service artifacts as independently
verifiable data.

\section{NDN Computation and Service Frameworks}

NDN already provides useful primitives for service-oriented systems:
hierarchical names, data-driven retrieval, in-network caching, adaptive
forwarding, and data signatures~\cite{ndn}. A service framework over NDN must
bridge the gap between these primitives and application-level service
semantics. Prior NDN work explores several regions of this design space.

\subsection{Function-Centric Computation}

Named Function Networking (NFN) treats computation as a first-class named
object by embedding function expressions in names~\cite{nfn}. This model is
powerful because it allows computation and data retrieval to be composed within
the naming system itself. It also suggests a deep integration between content
names and computation names, which is attractive for in-network processing.

The trade-off is complexity. Function-centric naming can make names highly
expressive, but it also makes execution semantics, trust, caching, and
deployment more difficult to reason about. UAV control, live video, and
distributed AI inference require explicit service authorization, provider
selection, long-running state, and application-defined execution policies.
NDNSF therefore chooses a service-invocation abstraction rather than a fully
general function-expression abstraction.

\subsection{Serverless and Edge-Oriented NDN Frameworks}

NFaaS extends NDN toward serverless computing by treating functions as
deployable units that may be executed at edge locations~\cite{nfaas}. Other
edge-oriented frameworks, such as CFEC for information-centric Internet of
Vehicles, explore low-latency microservice execution and dynamic placement in
edge environments~\cite{cfec}. These systems highlight an important direction:
service execution should move closer to users, data sources, or resource-rich
edge nodes.

The open issue is that dynamic placement is only one part of service-oriented
application support. Applications also need a stable API, authorization for
both users and providers, multi-provider selection, large-object handling, and
clear deployment procedures. NDNSF focuses on these runtime service semantics.
It can coexist with future placement mechanisms; for example, a placement
algorithm could decide which drones, storage components, or inference providers
should advertise a given NDNSF service.

\subsection{Remote Invocation Frameworks}

RICE provides remote method invocation in ICN using mechanisms such as
handshakes and thunks to represent computation parameters and
results~\cite{rice}. NSC proposes Named Service Calls for NDN and offers an
RPC-like abstraction for remote execution~\cite{nsc}. These systems are close
to NDNSF's goals because they directly address service invocation rather than
only content retrieval.

The key limitation is that they do not provide the complete set of mechanisms
needed by the application classes targeted in this dissertation. NSC is
primarily one-to-one: a caller contacts an executor, and the protocol is not
designed around simultaneous provider discovery, provider ACK metadata, or
multi-provider selection. RICE provides stronger invocation semantics but
requires changes to the forwarding plane. NDNSF keeps the framework at the
application/runtime layer and uses NDN Data publication and Sync to support
one-to-many service request dissemination without modifying NFD.

\subsection{Application-Specific NDN Frameworks}

Other NDN systems focus on particular domains. DNMP builds a secure network
measurement framework using NDN synchronization and hierarchical
topics~\cite{dnmp}. MIA-NDN explores microservice-centric Interest aggregation
for NDN~\cite{miandn}. SECaaS studies security-as-a-service in multi-access
edge environments~\cite{secaas}. These projects demonstrate that NDN can be
adapted to practical service-like workloads, especially when names and
application semantics are designed together.

The limitation is generality. Application-specific frameworks often make
assumptions about a particular data type, service domain, aggregation pattern,
or deployment topology. NDNSF instead aims to provide a reusable framework
layer that can support different application services, including UAV control,
video, object detection, distributed inference, storage, and collaboration.
The proposed UAV and DistributedInference applications are intended to test
whether the framework is general enough for multiple domains rather than only
one carefully tuned application.

\subsection{Security and Access-Control Mechanisms}

NDN signs Data packets by design, but signatures alone do not answer all
service questions. A service framework must decide who may request a service,
who may provide a service, what data should be encrypted, how keys should be
distributed, and how replayed messages should be rejected. Prior work on
attribute-based encryption and NAC-ABE shows how fine-grained access control
can be integrated with NDN data names~\cite{goyal2006abe,dulal2023nacabe}. These ideas
are central to NDNSF.

The open issue is integration with the service workflow. If access control is
bolted onto individual applications, every application must separately handle
permission retrieval, encryption attributes, message verification, and replay
protection. NDNSF makes these part of the runtime: ServiceController
distributes permissions, service messages are protected according to
service-level attributes, and one-time user/provider tokens bind ACK,
selection, targeted fast-path, and response messages to the current invocation.

\section{NDN-Based Service Systems}

NDN Service Call (NSC)~\cite{nsc} and other NDN application frameworks show
that NDN can support service invocation without IP endpoint binding. NDN's
Interest/Data exchange, name-based routing, in-network caching, and data
signatures address several issues in IP-based systems. These systems are
therefore important evidence that NDN is a promising foundation for services.

The remaining gap is that existing NDN service systems have not provided a
general-purpose runtime that combines:

\begin{itemize}
  \item generic dynamic service APIs,
  \item controller-authorized user and provider permissions,
  \item one-to-many request publication,
  \item provider ACK metadata,
  \item application-defined selection strategies,
  \item adaptive admission control,
  \item large-data references,
  \item provider collaboration, and
  \item service containers that can be evaluated in realistic settings.
\end{itemize}

\section{Design Patterns and Trade-offs}

The related work suggests several recurring design patterns. First, service
frameworks must decouple service names from provider locations. Second, large
inputs and outputs should be represented as named data objects rather than
embedded directly in small request payloads. Third, service state usually
cannot rely only on NDN's Pending Interest Table because service execution may
be long-running, multi-step, or collaborative. Fourth, security must be part of
the invocation workflow rather than an afterthought.

These patterns also expose trade-offs. Function-centric names are expressive
but can be difficult to deploy. Serverless placement is flexible but requires
orchestration. RPC-style invocation is easy to understand but can favor
one-to-one execution. Broker-based systems decouple time but may introduce
infrastructure dependencies. NDNSF's design point is to combine an RPC-like
developer API with NDN's data-centric names, signed Data, Sync-based
publication, and application-visible provider selection.

\chapter{NDNSF Framework}
\label{chap:ndnsf}

\section{Design Goals}

NDNSF is designed around five goals.

\begin{enumerate}[leftmargin=*]
  \item \textbf{Application-facing simplicity.} Developers should register and
  invoke typed services without writing service-specific NDN protocols.
  \item \textbf{Data-centric security.} Service messages and permissions
  should be signed, verifiable, and encrypted where appropriate.
  \item \textbf{Dynamic provider selection.} A request should be able to reach
  multiple providers and select the best one according to strategy.
  \item \textbf{Collaboration and resilience.} The framework should support
  multiple providers, compensation after partial failure, and cross-validation.
  \item \textbf{Operational validation.} The framework should support MiniNDN
  evaluation, selected real-machine experiments, certificate management, and
  reproducible configuration.
\end{enumerate}

\section{NDNSF v0.1 Baseline}

NDNSF v0.1 includes:

\begin{itemize}
  \item a generic dynamic C++ service API;
  \item ServiceController, ServiceUser, and ServiceProvider runtimes;
  \item service request publication over NDN synchronization;
  \item Request, ACK, Selection, and Response message flow;
  \item user and provider permission distribution;
  \item NAC-ABE-based service-level access control;
  \item selective ACK and provider metadata support;
  \item built-in provider-selection strategies;
  \item adaptive admission control;
  \item MiniNDN evaluation against NSC and gRPC.
\end{itemize}

This baseline is substantial because it already connects the main pieces that a
data-centric service framework must coordinate: service naming, service-message
publication, user and provider authorization, encrypted service payloads,
provider metadata, provider selection, and response verification. In other
words, NDNSF v0.1 is not only an API sketch; it is an executable runtime that
shows how NDN names, Sync, signed Data, NAC-ABE attributes, and service-level
policy can be combined into one service-invocation workflow. This is why the
proposal can focus on extending and validating the framework rather than
starting from a blank design.

Figure~\ref{fig:ndnsf-v01-architecture} summarizes the three runtime roles
implemented in the baseline. The controller manages policies and distributes
permissions, providers subscribe for authorized requests and publish service
results, and users publish requests, collect ACK metadata, select providers,
and verify responses. This role separation is the foundation for the later UAV
and distributed-inference service-container work.

\section{Provider Collaboration as the Central Extension}

The central extension beyond NDNSF v0.1 is provider collaboration. In a
collaborative service, one logical request may involve multiple authorized
providers rather than a single endpoint. Providers may advertise ACK metadata
such as availability, queue state, location, or role capability; the user may
select one or more providers after an ACK collection interval; and the
application may issue compensation requests when only part of a logical task
is completed. Long-running selected work should also be diagnosable: after a
timeout, the user should be able to learn whether a selected provider has not
seen the selection, is queued, is executing, has failed, or has already
published a response.

This collaboration model is intentionally application-independent. Multi-UAV
patrol can use it to assign mission segments and recover from partial failure,
while distributed inference can use it to assign model roles and coordinate
intermediate artifacts. In both cases, NDNSF should provide the generic service
semantics: request publication, provider metadata, provider selection,
authorization, status diagnosis, and response verification. The application
defines the domain-specific work; the framework defines how selected providers
participate in one logical service workflow.

\section{Generic Dynamic API}

NDNSF v0.1 moved toward a generic dynamic API instead of generated,
service-specific stubs. A provider can register a typed service handler:

\begin{lstlisting}[language=C++]
provider.addHandler<RequestT, ResponseT>(
    ndn::Name("/ObjectDetection/YOLOv8"),
    handler);
\end{lstlisting}

A user can invoke a service through the generic runtime:

\begin{lstlisting}[language=C++]
user.RequestService<RequestT, ResponseT>(
    providers,
    ndn::Name("/ObjectDetection/YOLOv8"),
    request,
    onResponse,
    onTimeout,
    timeoutMs,
    strategy);
\end{lstlisting}

This API is intended to keep application data in application-defined request
and response objects while the framework handles naming, publication,
permission checks, tokens, provider selection, and response delivery.

is central to the one-to-many service design: a request can be observed by

before execution, and the user can explicitly bind the request to selected
providers.

\section{Service Invocation Workflow}

The normal NDNSF invocation workflow is:

\begin{enumerate}[leftmargin=*]
  \item The user publishes a service request under a service name.
  \item Providers with permission to serve the service receive the request.
  \item Providers decide whether to ACK based on availability, local state, and
  application-defined metadata.
  \item The user collects ACKs during an ACK window.
  \item A selection strategy chooses one or more providers.
  \item Selected providers execute the request and publish responses.
  \item The user verifies tokens, provider identity, and response data.
\end{enumerate}

This workflow supports both one-to-one and one-to-many service models. The same
request can reach multiple providers, enabling the user to select the first
available provider, randomly balance load, select all providers, or use a
custom strategy based on metadata.

\section{Security Model}

NDNSF uses a controller-authorized permission model. The ServiceController
issues encrypted permission responses to target identities. Users and providers
fetch their respective permissions, and permission Data is signed by the
controller. NAC-ABE attributes map service messages to service-level
authorization namespaces. ABE-protected challenges, validated signatures, and
invocation-state checks jointly enforce service-level authorization and reject
replayed or mismatched Request/ACK/Selection/Response messages.

Figure~\ref{fig:ndnsf-policy-example} illustrates the intended policy model:
provider permissions specify which named services an entity may offer, while
user permissions specify which named services an entity may access. This
proposal keeps that service-name-centered policy model in the UAV and
distributed-inference extensions, while adding deployment procedures that make
the trust root and publisher namespaces explicit.

The current model separates:

\begin{itemize}
  \item \textbf{user authorization}: whether the user may request a service;
  \item \textbf{provider authorization}: whether a provider may serve a
  service;
  \item \textbf{message integrity}: whether a service message is signed and
  valid;
  \item \textbf{data confidentiality}: whether the payload is encrypted for
  authorized participants;
  \item \textbf{replay protection}: whether one-time tokens have already been
  consumed.
\end{itemize}

\section{Completed Foundation and Current NDNSF Validation}

The NDNSF evaluation compares NDNSF against NSC and gRPC in MiniNDN. It covers
service latency and success under wired loss, intermittent Providers, wireless
mobility, adaptive admission, selective ACK, and Provider-selection scenarios.
The current evidence supports three bounded multi-Provider claims: NDNSF can
discover Providers through a service namespace without a pre-registered
address list, can reduce tail latency when mobility actually requires a
Provider switch, and can avoid redundant Provider execution. It does not claim
that NDNSF is universally more reliable or faster under mobility.

The strongest evidence comes from scenarios where endpoint binding or a single
provider becomes fragile. In the lossy wired Memphis--CSU--UCLA path, packet
round-trip loss is $1-(1-\ell)^4$ for per-link loss $\ell$. NDNSF completed
599 of 600 requests at 1\% link loss, where the packet round-trip loss is
3.94\%, and 598 of 600 requests at 3\% link loss, where the packet round-trip
loss is 11.47\%. At 10\% link loss, where packet round-trip loss rises to
34.39\%, the best measured NDNSF result was 539 of 600 requests. This
identifies the bounded-time delivery limit of SVS-based service invocation
under heavy loss, rather than a failure of the NDNSF service model. In a wired multi-provider
experiment with intermittent provider rejection, NDNSF maintained 99.46\%
success at 20\% provider-failure probability and 96.70\% success at 30\%,
whereas the single-provider baselines dropped to roughly two-thirds success or
lower. The wireless rows below remain historical diagnostics because their
single-Provider baselines and timing provenance were not matched. The current
fair campaign uses byte-identical traces, four Providers per system, common
publication times, and matched deadlines. Its unconditional 50/100/150\,m
controls show that coverage dominates all-request success. In the registered
ten-seed 100\,m, 2\,m/s holdout, the 1,312 requests unanimously classified as
requiring a Provider switch show an NDNSF seed-p95 latency reduction of
597\,ms versus gRPC-SEQ-4 (95\% CI $[-992,-200]$\,ms) and 2,618\,ms versus
NSC-4 (95\% CI $[-2916,-2315]$\,ms). The success comparison does not establish
superiority. In a separate transition test, NDNSF completes 357/357 requests
with zero pre-registered Provider endpoints after a new Provider becomes solely
reachable; static gRPC/NSC complete 0/357, whereas their pre-registered variants
complete 357/357. This establishes native service-namespace discovery while
recognizing that an external resolver can supply equivalent endpoint updates
to gRPC or NSC. The adaptive-admission and Selective ACK
experiments further show why the framework needs runtime metadata: admission
control kept P95 latency below 270\,ms under overload, and Selective ACK raised
success from 1.82\% to 100\% when the nearest provider was overloaded.
Together with the capacity-matched six-seed repeat (NDNSF: 1,798/1,800
successes and 1,800 provider executions; gRPC-PAR-4: 1,800/1,800 successes and
7,180 server executions; seed-level bootstrap 95\% interval $[-0.22,0.00]$ pp),
the evidence also supports a Provider-work-efficiency mechanism claim. These
results jointly support native discovery, conditional switching latency, and
execution efficiency, with explicit limits on general mobility claims.

\section{Limitations of NDNSF v0.1}

NDNSF v0.1 establishes feasibility, but it does not yet fully address the
requirements of dynamic service applications beyond controlled framework
tests. The main limitations
that motivate the remaining dissertation work are:

\begin{itemize}
  \item \textbf{Low-latency known-provider control}: the normal
  Request/ACK/Selection/Response workflow is appropriate for provider
  discovery, but control commands to a known drone or device need a faster
  Targeted path while preserving authorization and replay protection.
  \item \textbf{Provider collaboration}: v0.1 supports selecting providers, but
  larger tasks need collaboration among multiple providers, partial failure
  handling, and compensation requests.
  \item \textbf{Service-container composition}: real applications often contain
  multiple services in one trusted process. Those services need efficient local
  composition without exposing a network bypass to remote callers.
  \item \textbf{Large artifacts}: v0.1 service payloads are not intended to
  carry models, recordings, images, or intermediate tensors. Applications need
  typed references to named Data objects plus native NDN segmented retrieval
  for large signed and encrypted objects.
  \item \textbf{Operational validation}: v0.1 demonstrates the security
  model, but broader validation needs clearer certificate bootstrapping,
  trust-schema guidance, configuration procedures, and reproducible
  experiments.
  \item \textbf{Application-level validation}: v0.1 evaluation shows the core
  framework works in MiniNDN, but the dissertation must evaluate whether the
  design supports demanding UAV and distributed-inference workflows.
\end{itemize}

\section{Supporting Mechanisms for Provider Collaboration}

The following mechanisms support provider collaboration in specific operating
conditions. They are motivated by the UAV and distributed-inference workloads,
but they are not separate dissertation threads and should remain generic
framework mechanisms rather than application-specific shortcuts.

\subsection{Targeted Invocation}

Some services, such as UAV flight-control commands, are directed at a known
provider and must minimize latency. The proposed Targeted invocation path keeps
NDNSF permissions, one-time user/provider tokens, and replay protection, but
avoids repeated ACK/Selection rounds after a token batch has been bootstrapped
through the normal flow. This gives known-provider commands a fast path while
keeping the security semantics of normal NDNSF invocation.

\subsection{Trusted Local Invocation}

A service-container application may contain several services in the same
trusted process. A local call from one internal service component to another
should not need to publish an NDN request. The proposed local invocation path
therefore provides synchronous and asynchronous in-process invocation for
explicitly registered local services. It is not a wire-protocol mode: remote
callers cannot request it, and it bypasses NDNSF network security only inside
the trusted local container boundary.

\subsection{Large-Data Reference Abstraction}

Models, video, images, activations, and logs should not be placed in small
request payloads. The proposed pattern is to let the producer segment the
object as named NDN Data and place only a typed object reference in the NDNSF
request or response. The reference can include the object name, object type,
version or session id, expected digest, expected size, final segment
information, source type, and optional encryption metadata. The receiver then
uses normal NDN segmented fetching, such as ndn-cxx segment fetch logic, to
retrieve the object by name.

This abstraction is intended to be a generic NDNSF mechanism, not an API for a
particular storage service. Small request and response payloads remain useful
for control messages and compact typed objects. When the payload becomes a
large artifact, the same logical service invocation should carry a
\emph{reference} rather than the artifact bytes. The application or helper can
turn a payload into named Data segments, sign and optionally encrypt those
segments, and then pass a typed reference through NDNSF. This keeps service
selection, authorization, token checks, and timeout diagnosis in the normal
NDNSF path, while large bytes move through NDN's native named-data retrieval
path.

The same reference format should be usable across UAV recordings, camera
artifacts, model shards, runtime artifacts, intermediate activations, and logs.
As a result, UAV-APP and DistributedInference can share one framework-level
large-data vocabulary: object type, object name, producer, session or version,
size, digest, final segment hint, and optional encryption metadata. This avoids
embedding application-specific conventions such as raw Data-name strings inside
service payloads and makes large-object behavior inspectable by applications
that do not understand NDN packet details.

This design can optionally use persistent storage, but storage is an
implementation support component rather than a separate research direction in
this proposal. If persistent storage is used, it stores opaque NDN Data
segments that have already been named, signed, and optionally encrypted by the
application or by a framework helper. Security is not handled by a storage-
specific path: NDNSF's normal hybrid encryption, signatures, tokens,
permissions, and trust-schema validation protect the service message and the
referenced Data. Discovery metadata can still accelerate validation, but large-
object transfer itself is based on typed object references and native NDN
segmented retrieval.

This chapter supports RQ2 by previewing the reusable NDNSF mechanisms that the
dissertation will refine: secure invocation, provider authorization,
provider collaboration, and its supporting mechanisms. It supports RQ3 by
identifying where collaboration introduces reliability, security, and latency
tradeoffs, and where supporting mechanisms are needed to control overhead
without weakening the core service semantics.

\chapter{UAV Network Application over NDNSF}
\label{chap:uav}

\section{Why UAV Networks Need a Service Framework}

UAV applications are a strong test case for NDNSF because they combine
mobility, real-time control, video streaming, distributed sensing, multi-agent
coordination, and safety constraints. A UAV network may include a ground
station, several drones, cameras, flight controllers, object-detection
services, storage capabilities, and mission-planning components. Each component exposes
capabilities that naturally look like services.

For the dissertation, the UAV workload is specifically used to stress provider
collaboration under mobile and command-sensitive conditions. A ground station
may need to discover multiple drones, select one or more providers for a
mission, issue targeted commands to known drones, compensate for a failed
mission segment, and retrieve video or recording objects without treating
large data as RPC payload. This makes UAV-APP a validation workload for the
NDNSF framework: it asks whether provider collaboration, authorization,
selection status, and supporting low-latency or large-data mechanisms can work
together in an operator-facing service container.

Developing such an application over IP creates several recurring problems:

\begin{itemize}
  \item \textbf{Address binding.} A drone's identity and its IP address may
  change as it moves, reconnects, or switches networks.
  \item \textbf{NAT and mobility.} Direct connectivity to drones is not always
  available, especially in ad hoc or field deployments.
  \item \textbf{Service discovery.} A ground station needs to know which drones
  offer camera, telemetry, flight-control, and mission services.
  \item \textbf{Command authorization.} Flight-control commands must be
  restricted to authorized users and protected against replay.
  \item \textbf{Data verification.} Telemetry, images, videos, and mission
  results should be verifiable independently of the channel.
  \item \textbf{Failure recovery.} If one drone disconnects or fails a task,
  the mission should compensate using other drones when possible.
  \item \textbf{Large data.} Live video and recorded video should use streaming
  and segmented data retrieval instead of small RPC payloads.
\end{itemize}

\section{Architecture}

The UAV application contains two main roles:

\begin{itemize}
  \item \textbf{Ground station role}: operator interaction, map-based mission
  planning, telemetry and video observation, object-detection service
  composition, and NDNSF user behavior.
  \item \textbf{Drone role}: flight-control adaptation, telemetry publication,
  camera and video publication, encrypted recording support, mission execution,
  and NDNSF provider behavior.
\end{itemize}

The application is explicitly service-oriented. A drone does not expose one
monolithic endpoint. Instead, it exposes independently named services for
flight control, telemetry, video control, camera frames, recording discovery,
and mission assignment. The ground station uses structured runtime state to
represent telemetry freshness, mission progress, video availability, and
safety readiness, so that operator-visible status and command decisions remain
consistent across independently named services. Known-drone commands use
Targeted invocation, while collaborative workflows such as patrol assignment
use normal NDNSF selection.

\section{Operator Workflow and State Discipline}

The UAV application is not intended as a replacement for an existing ground
control station. Its purpose is to validate whether NDNSF can support a real
UAV service workload. For that validation to be meaningful, the GS must still
answer the operator questions that matter in practice: which vehicle is
selected, whether it is ready and safe to control, which command or mission is
active, whether telemetry and video are fresh, and what will happen if a link
or device fails. The proposed UAV work therefore treats the GS as a
state-driven operator console, not only as a collection of service invocations.

\section{Live Video and Recording}

Live video is initiated by a GS command to a drone-specific video-control
service. The drone negotiates the accepted bitrate and frame size, encodes
camera frames as a streaming codec, and publishes stream Data under names that
include a stream identifier and monotonically increasing packet sequence. Each
packet also carries stream metadata so the receiver can reject stale packets
from a previous stream. The GS fetches and decodes video with an adaptive
low-latency policy that uses observed RTT, bitrate, timeout pressure, decoder
backlog, and published/decoded gap to tune the prefetch window and stale-frame
skipping policy.

Recording is intentionally different from live control. The drone may keep its
camera active and record locally even when live streaming is off. The recorded
object is represented as a large-data reference to signed and encrypted Data
segments. The ground station discovers available recordings through an
authorized service invocation, then fetches the referenced segments by name and
decrypts locally. Thus storage does not need to understand service
authorization; authorization and key material are handled by NDNSF service
messages, while replay or stale-data problems are handled by session
identifiers, stream identifiers, and signed Data names.

\section{Flight Control and Safety}

Flight-control commands are naturally targeted at a specific drone. The
proposed work uses Targeted NDNSF invocation for commands such as arm, takeoff,
land, goto, emergency stop, and manual control. The drone-side adapter supports
mock mode for MiniNDN tests and MAVLink/PX4 mode for SITL or real flight
controllers~\cite{mavlink-survey,px4}. Manual-control commands are continuous control messages rather
than mission services; their responses can carry telemetry so the GS can update
altitude, battery, GPS, speed, controller state, and flight-safety indicators while the
operator is flying.

Safety mechanisms include:

\begin{itemize}
  \item readiness gates based on heartbeat, GPS/EKF, battery, mode, and arming
  checks;
  \item command acknowledgments from the flight controller;
  \item manual-control timeouts that stop sending stale control values;
  \item emergency stop or hold/land behavior after communication failure;
  \item explicit warnings that real propeller tests require a validated safety
  procedure.
\end{itemize}

\section{Multi-UAV Patrol}

The proposed patrol service demonstrates provider collaboration. A ground
station creates a waypoint mission and partitions it among two or more drones.
The design clusters waypoints according to the number and position of
available drones so each drone receives a compact region and returns to its
own departure point after completing its segment. Each drone receives a mission
segment, executes it through MAVLink, and returns status. If a drone fails or
returns an incomplete result, the GS can issue a compensation request for the
missing segment rather than restarting the entire mission.

This design illustrates a key NDNSF principle: compensation requests are
application-level parts of the same logical mission, while NDNSF provides the
secure service invocation, provider selection, and message verification
substrate.

The current UAV-APP is a research prototype, not yet a field-ready or
safety-certified ground-control system. This distinction is important for the
proposal: practical use, SITL, and selected real-machine testing may expose new
requirements or changes in command handling, telemetry freshness, video
behavior, safety policy, deployment, or operator workflow. Those discoveries
are part of the research value because they can feed back into NDNSF's
framework mechanisms.

\section{Evaluation Plan}

The UAV application will be evaluated in three stages:

\begin{enumerate}[leftmargin=*]
  \item \textbf{MiniNDN regression tests}: controller, one or more
  drones, operator console behavior, video start/stop, encrypted recording playback, and patrol
  service execution.
  \item \textbf{SITL tests}: PX4/jMAVSim control for arm, takeoff, land,
  manual control, and mission execution.
  \item \textbf{Real-machine validation}: one PC and one or more drones with
  NFD routes, certificates, camera devices, and MAVLink connections.
\end{enumerate}

Metrics will include command latency, video startup time, decoded frame rate,
recording retrieval time, mission completion rate, compensation overhead,
telemetry freshness, and failure recovery time.

This chapter supports RQ4 by defining UAV as the command-sensitive,
real-time, mobile workload used to validate NDNSF beyond core framework tests.
It also feeds back into RQ2 and RQ3 by using UAV behavior to stress Targeted
invocation, provider collaboration, timeout diagnosis, and large-data
references.

\chapter{Distributed AI Inference over NDNSF}
\label{chap:ai}

\section{Motivation}

Distributed AI inference is another strong test case for NDNSF. AI models are
large, runtime artifacts are sensitive, intermediate tensors can be large, and
inference providers may be heterogeneous. A model may be split across edge
devices, drones, ground stations, GPUs, and cloud resources. The user wants to
invoke an inference service by model or task name, while the system determines
where model shards and stages should run.

For the dissertation, distributed inference stresses provider collaboration in
a different way from UAV workloads. Providers are not collaborating because
they are vehicles in a shared physical mission; they collaborate because a
single inference task may require multiple model chunks, runtime artifacts,
activation exchanges, and dependency-ordered execution steps. This workload
therefore tests whether NDNSF can keep collaboration generic: the framework
should coordinate authorized providers, large-data references, status
diagnosis, and result verification, while the inference layer supplies the
model-specific dependency graph and execution plan.

In IP-based systems, distributed inference often relies on custom orchestration:
host addresses for model stages, separate object stores for model artifacts,
custom integrity checks, ad hoc retry behavior, and manual placement policies.
This makes it hard to build applications that remain correct when providers
join, leave, fail, or move.

\section{Approaches to Distributed AI Inference}

The dissertation will review the main distributed inference approaches:

\begin{itemize}
  \item \textbf{Replication/data parallel inference}: multiple providers hold
  the same model and serve independent requests.
  \item \textbf{Pipeline partitioning}: model stages execute sequentially on
  different providers, following split-computing ideas such as DNN
  partitioning across mobile, edge, and cloud resources~\cite{neurosurgeon,ddnn}.
  \item \textbf{Layer or operator partitioning}: the model graph is split at
  finer granularity according to compute and memory constraints.
  \item \textbf{Early-exit inference}: computation can stop early when a
  confidence threshold is reached~\cite{branchynet}.
  \item \textbf{Collaborative inference}: multiple providers cross-check,
  aggregate, or vote on results.
  \item \textbf{Edge-cloud split inference}: lightweight preprocessing happens
  at the edge while heavier stages run on ground-station or cloud nodes.
\end{itemize}

This proposal uses unambiguous partition terminology. A
\emph{pipeline/layer-range partition} assigns contiguous model-layer ranges to
sequential stages. An \emph{intra-layer/tensor partition} shards the work of one
stage across multiple tensor ranks. A heterogeneous hybrid layout is written as
$N\times\{M_i\}$, where $N$ is the number of pipeline stages and $M_i$ is the
number of tensor ranks used by stage $i$. The values of $M_i$ need not be equal.
Tensor partitioning is allowed only when the model adapter certifies the
required collective and redistribution semantics; aggregate memory across
unrelated devices must not be treated as capacity for an unsplittable role.

\section{NDNSF-Based Inference Architecture}

The public application call identifies the model, task, input, options, and
deadline. It does not provide a pre-split deployment layout or a list of
Provider roles. NDNSF Core remains a model-neutral carrier for
Request/ACK/Selection/Response and named large-data references. NDNSF-DI owns
model-graph interpretation, pipeline and tensor semantics, placement, assembly
specifications, device bindings, and execution dependencies. The Repo stores
immutable manifests and canonical layer bytes, not request-specific role
shards.

The design distinguishes three identities that must never be collapsed:

\begin{itemize}
  \item \textbf{canonical layer identity}, which names reusable model-layer
  bytes and their immutable manifest;
  \item \textbf{assembled fragment identity}, which records the ordered layers,
  adapter, assembly options, and logical role produced locally by one Provider;
  \item \textbf{loaded runtime identity}, which additionally binds the assembled
  fragment to a runtime, visible device set, and load configuration.
\end{itemize}

Planning occurs only after the immutable ACK collection closes. Signed ACK
offers expose Provider load, network observations, canonical-layer cache state,
and explicit per-device memory/topology information. Zero visible accelerators
is a valid CPU-only offer. ACK collection and queue acceptance do not reserve
accelerators; device feasibility is revalidated immediately before loading.

layers, assembles its assigned fragment locally, revalidates the selected
CPU/SINGLE\_DEVICE/DEVICE\_SET binding, loads the runtime, and becomes locally
ready. Execution is then driven by named dependency and collective edges; it
does not require a global all-Providers-ready barrier.

\section{Automatic Collaboration Plan Generation}

A major proposed contribution is automatic generation of collaboration plans
from AI model structure and resource information. The input includes:

\begin{itemize}
  \item the model graph, canonical-layer catalog, tensor dependencies,
  adapter-certified partition capabilities, and estimated activation or
  collective sizes;
  \item an immutable ACK-closed set of signed Provider offers containing
  explicit CPU and per-device memory/topology state;
  \item network latency, RTT, throughput, and relevant topology observations;
  \item canonical-layer, assembled-fragment, and loaded-runtime cache state;
  \item authorization, naming, dependency-edge, and key-scope constraints.
\end{itemize}

The output is a sealed collaboration plan containing logical roles and ranks,
Provider-specific assignments, \texttt{RoleAssemblySpec}s, explicit
\texttt{DeviceBinding}s, named dependency/collective edges, and the evidence
used by the decision. A reuse-aware strategy may prefer Providers that already
hold required canonical layers, but reuse never overrides model compatibility,
per-device feasibility, topology, authorization, or deadline constraints.

\section{Dependency-Driven Execution}

The planned runtime should hide dependency management from AI application
developers. A Provider should not contain YOLO-specific or fully-connected
network-specific communication code. It receives a Provider-local role bundle,
assembles and loads the specified fragment, consumes declared input edges,
executes its pipeline stage or tensor rank, performs certified collectives or
redistributions, and publishes only the outputs authorized by its edges. This
executor model is intended to support chains, fan-in/fan-out graphs, and
heterogeneous $N\times\{M_i\}$ layouts. Direct and cached Data must pass the
same producer, name, dependency-edge, and key-scope checks.

\section{Current Prototype Status and Evidence Boundary}

The available measured evidence predates the V3 reusable-layer architecture.
The NativeTracer campaign uses a small Qwen-style ONNX artifact and an earlier
Backbone/Head/Merge role/chunk workflow over the full MiniNDN network harness.
It exercises real model execution, Repo-backed artifact fetching, service
manifests, NDNSF large-data references, and named intermediate tensor objects.
It does not validate canonical-layer reuse, Provider-local assembly identity,
tensor/hybrid execution, multi-accelerator placement, or just-in-time device
admission.

In ten successful runs per layout, the shared-backbone layout had mean latency
259.4\,ms, p50 267.7\,ms, p95 283.9\,ms, and standard deviation 22.1\,ms. The
single-provider layout had mean latency 186.8\,ms, p50 191.7\,ms, p95
206.3\,ms, and standard deviation 20.0\,ms. For this small model,
single-provider execution is faster because it avoids the fixed cost of
cross-provider dependency exchange. This is a useful negative result: the
planner must compare compute, intermediate-data, network, device, and artifact
reuse costs rather than split merely because multiple Providers are available.

Earlier YOLO-style and small fully connected examples remain useful regression
cases for dependency-driven execution. The V3 architecture described above is
therefore presented as a design and implementation target whose evidence gates
remain open, not as a capability established by this campaign.

\section{Prototype and Evaluation Plan}

The evaluation will proceed from deterministic integration tests to MiniNDN and
sealed real-model/container qualification. Planned cases include:

\begin{itemize}
  \item exact canonical-layer, assembled-fragment, and loaded-runtime identity
  derivation, including cold, warm, restart, and cache-corruption cases;
  \item CPU-only, zero-visible-accelerator, single-device, and multi-device
  Provider offers with per-device feasibility and topology revalidation;
  \item proof that ACK collection and queue acceptance do not reserve devices,
  followed by just-in-time admission success and failure cases;
  \item pipeline-only, adapter-certified tensor, and heterogeneous
  $N\times\{M_i\}$ hybrid layouts, including collective and redistribution
  dependencies;
  \item direct versus cached Data with positive and negative producer, name,
  dependency-edge, assignment, and key-scope checks;
  \item local baseline versus NDNSF execution, cold versus reused artifacts,
  Provider failure/replanning, and output consistency;
  \item integration-harness qualification followed by MiniNDN and sealed
  container/Tiger runs for representative real models.
\end{itemize}

Metrics will include end-to-end latency, canonical-layer retrieval and local
assembly time, load/admission time, cache reuse, peak per-device memory,
activation and collective bytes, Provider utilization, success and recovery
rates, output consistency, p50/p95 latency, variance, and planner prediction
error.

This chapter supports RQ5 by defining distributed inference as the
artifact-heavy, dependency-driven workload used to validate NDNSF under
multi-stage compute/data collaboration. It also feeds back into RQ2 by testing
whether large-data references, ACK-closed planning, Provider-local bundles,
named dependency edges, and long-running status can remain generic rather than
model-specific.

\section{Risks and Mitigation}

\begin{itemize}
  \item \textbf{Dependency risk}: UAV and AI applications depend on many
  libraries. Mitigation: controlled dependency environments and container-based
  tests.
  \item \textbf{Real flight risk}: physical UAV testing is safety-critical.
  Mitigation: start with MiniNDN and SITL, then use controlled real-machine
  tests without propellers before flight.
  \item \textbf{Performance risk}: security and sync overhead may affect
  latency. Mitigation: use Targeted invocation, local invocation, and
  large-data references as supporting mechanisms where the collaborative path
  would otherwise add avoidable overhead, together with sampled logging and
  careful benchmark profiles.
  \item \textbf{Scope risk}: UAV and AI inference are both large applications.
  Mitigation: implement minimal convincing prototypes first, then extend only
  the features needed to demonstrate the framework.
\end{itemize}

This chapter connects the research questions to the dissertation execution
plan. It shows that each RQ has a corresponding evidence path, while leaving
room for application-driven findings from UAV and DistributedInference to
refine the final NDNSF design.

\chapter{Conclusion}
\label{chap:conclusion}

This proposal presents NDNSF as a data-centric service framework for dynamic,
secure, and collaborative networked applications. NDNSF v0.1 demonstrates that
NDN can support a generic service abstraction with authorization, provider
selection, and adaptive behavior. The proposed work centers the next framework
step on provider collaboration, supported by Targeted invocation, trusted local
composition, and large-data references, and validates this direction through
two demanding application domains: UAV networks and distributed AI inference.

The expected outcome is not merely another application implementation, but a
framework and design methodology for building service-oriented systems where
services, data, permissions, and collaboration plans are named and verifiable.
UAV-APP and DistributedInference are important because they stress NDNSF in
different ways and reveal what the framework must provide, but the dissertation
contribution remains the NDNSF framework, its mechanisms, and the evidence that
those mechanisms generalize beyond a single application.
