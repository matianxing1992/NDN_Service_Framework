\chapter{引言}
\label{chap:introduction}
\section{服务发现与获准调用}
命名数据网络（NDN）支持按名获取 Data 和以数据为中心的安全机制~\cite{ndn,ndnpacket}。应用可用 trust schema 规定哪些签名密钥有权签署哪些 Data，并指导 Data 验证~\cite{trustschema}。Sync 通告数据集变化以辅助获取~\cite{li2018brief,moll2022sok}。这些机制不自动选择执行者或保证按时完成；调用授权需应用定义规则与检查。

请求者知道服务，却未必知道哪些获准 Provider 可达、有能力且愿意执行。NFN、NFaaS、RICE 和 NSC 支持命名计算或调用~\cite{nfn,nfaas,rice,nsc}。Distributed Network Measurement Protocol（DNMP）提供 Trust Schema 命令授权实例~\cite{dnmp}；gRPC 支持可扩展名字解析~\cite{grpcresolver}。研究参照这些先例评价 NDNSF 的发现、授权与调用成本，不假定已有工作缺少相应机制。

\section{初版 NDNSF 的调用基础}
初版 NDNSF 从多个候选中选定一个 Provider。User 发布 Request Data、收集应答（ACK）Data，再发布 Selection Data；选定 Provider 执行并发布 Response Data。候选是同一次调用的替代执行者，不承担不同的相互依赖角色。

发现与授权不以协作为前提。发现描述提供期限和资源需求，应用输入提供执行材料。被评估设计以属性基加密（ABE）保护描述，以受保护 challenge 核验、信任规则下的签名验证和请求状态检查实施授权。获准但未选中的候选仍可读描述。输入／结果保护、撤销和管理成本同样属于评价范围。

\section{从单 Provider 调用扩展到多 Provider 协作}
部分任务需要不同 Provider 提供互补服务。分别调用各服务，并不会自动规定哪个 Provider 担任哪个角色，以及依赖服务可以接受哪些中间对象。本 Proposal 研究在保留调用基础的同时，通过扩展明确这些分工与依赖。

例如，附近无人机（UAV）从不同角度采集地面区域图像，交给计算 Provider 分析。扩展分配采集和处理角色，并按声明依赖检查每张图像。判断可行性所需的区域与期限可能要在 ACK 前提供；处理图像可通过 Selection 披露。descriptor 加密限制读取者为获准候选，但不隐藏名称或流量模式。此例说明扩展需求；识别算法仍由应用选择。

\section{论点与研究问题}
拟验证的论点是：命名且可验证的对象能够支持运行时服务发现和获准的单 Provider 调用，而明确的角色与依赖规则能够将这一基础扩展到多 Provider 任务。研究分别评估发现／授权设计和协作扩展。收益必须在所测条件下足以说明发现、验证、通信与密钥管理成本的合理性。
\begin{enumerate}[label=RQ\arabic*.,leftmargin=*]
\item NDNSF 如何发现愿意参与的 Provider，同时避免未获准者读取发现描述，并在执行前检查服务权限？相对完整替代设计，其成本是什么？
\item 如何扩展单 Provider 调用基础，让运行时选定的多个 Provider 按任务角色和命名依赖执行，而不依赖中间 Data 来自生产者还是缓存？
\item 在何种任务和网络条件下，这些机制改善完成率、时延或执行效率？何时成本超过收益？
\end{enumerate}
RQ1 评价调用基础，包括适配到 NDNSF 流程的 DNMP-inspired 角色授权加内容加密对照；RQ2 通过 UAV／DI 依赖检验协作扩展；RQ3 分别测量两者及其失败行为。

\section{贡献与证据边界}
预期贡献是经评价的发现／授权设计、通过命名依赖检查落实运行时分工的协作协议，以及收益和成本证据；研究基于已有 NDN、加密与计算机制。

已有调用实验不验证多角色计划。扩展新增角色与依赖规则，不替代已有 request ID 隔离。后续实现不归为初版能力；协作端到端评价仍未完成。“已有证据与待完成评价”章区分现有结论和待补证据。

\chapter{相关工作与完整替代方案}
\section{命名计算、调用与服务组合}
NFN 研究命名计算与表达式求值，NFaaS 研究命名函数执行放置~\cite{nfn,nfaas}。RICE 握手支持认证与安全信息交换~\cite{rice}。NSC 使用应用提供的 Trust Schema 验证签名调用 Interest，并讨论输入和结果保护~\cite{nsc}。实验中的简化 harness 不等同于完整 NSC 设计。

协作扩展关注如何先收集当前意愿与可行性，再分配执行角色，并约束中间对象的使用。长期服务权限并不确定本次哪个 Provider 是指定前驱；request ID 和单独的合法签名也不表达该分工。拟议贡献是运行时分工与对象使用之间被执行检查落实的联系，而非 manifest 格式本身。CaSCON~\cite{cascon} 等服务组合研究是相关对照；研究将比较分配时机、依赖验证和恢复语义，并纳入工作流安全与 capability 方案。超出这一拟议范围的创新性仍需上述比较确认。

\section{在相同需求下比较授权设计}
\subsection{DNMP：Trust Schema 授权的具体实例}
DNMP 通过角色约束的签名授权测量
命令~\cite{dnmp}。Network Key 是角色密钥、设备密钥及所分发 Schema 签名层级的
信任锚。客户端根据 \texttt{target}、\texttt{probeType}、\texttt{probeArgs} 和用户的
\texttt{roleType}，从用户已有的密钥中查找 Schema 允许的签名密钥；无匹配时拒绝，
多个匹配时选择权限最小的密钥。接收方 Network Observer Daemon（NOD）仅在
publication 通过 Schema 规定的验证后才调度探测操作。因此，这是真正的命令
授权，不是接受任意合法签名。DNMP 还限制 publication 的生命周期并保留近期
publication 状态以防重放，其假设包括设备时钟大致同步。

\subsection{将对照方案适配到 NDNSF}
\label{sec:dnmp-alternative-ch}
本比较提出保留 NDNSF 的 Request--ACK--Selection--Response 流程，将 ABE-backed
调用检查替换为角色约束签名规则。该方案需分别检查 User 的调用权限与 Provider
的参与权限，将消息关联到活动请求，并仅允许被 Selection 选中的 Provider 执行。
这些是对照设计的适配要求，不归属于 DNMP 原有功能。两种方案都需满足选择前的
发现描述保密、选择后的接收者专属输入／结果保护，以及撤销后的授权检查。

选定后的交换使用接收者专属加密。保密发现还需要在选出本次参与者之前分发解密能力，例如组密钥管理或 ABE；这些并非穷尽全部选择。Trust Schema 单独不提供保密性，但与适当加密结合后可以满足这一要求。

证书式撤销需要验证者获取足够新的撤销状态，或者等待证书过期。删除仓库中的证书不能使已缓存副本自动失效。这是公平替代方案的生命周期要求，不是声称 DNMP 原论文实现了 NDNSF 的运行时撤销流程。

\section{受保护发现与权限管理}
NDNSF 使用 ABE 保护 Provider 选择前的发现描述，并让服务权限与身份签名凭证分离管理。User 发布可共享获取的描述密文，Controller 签发定义解密范围的策略密钥。增强 NAC-ABE 库提供 KP-ABE 支持~\cite{dulal2023nacabe}。NDNSF 通过受保护的 challenge 值、信任规则下的消息签名及当前授权／请求状态检查，将这些权限连接到调用。内容加密提供保密性，组合检查约束参与和执行。第~\ref{sec:abe-rationale-ch} 节解释权限管理的复用及其额外成本。

小而稳定的接收组可能适合普通组密钥；已知 Provider 且权限简单时，签名调用加接收者加密可能更直接。ABE 适合先按服务权限描述接收者、再发现具体身份，以及将多项服务权限与身份签名凭证解耦的需求。策略规模、成员变化、加密成本和 authority 可用性构成限制。

\chapter{系统模型与协议}
本章先描述被评估的调用与授权设计，再介绍拟议协作扩展。后续保密性与生命周期改进不被归为所有初版路径已有的行为。基本调用选择一个 Provider；角色分配与命名依赖边属于扩展。

\section{参与者、信任与不保证的性质}
这些是协议角色，不是必须分开的硬件；一个节点可以同时担任 User 和 Provider。管理组织登记身份并批准服务权限，Controller 管理这些策略。参与者预先配置可信锚及身份凭证／Controller 材料验证规则。不知道本次哪些候选会回复，不等于授权机构从未登记它们。计费、任意业务事务、全局最优调度和抵抗所有拒绝服务流量不在本研究主张范围内。
User 请求服务并选择 Provider；在协作扩展中还协调角色分配。Provider 提供并执行服务；Controller 管理授权材料与签名状态。转发器和缓存可交付对象，但不负责应用执行授权。模型信任 Controller 和 User 的规划决定，不引入抵抗恶意协调者的共识协议。攻击者可能观察可见名字／流量、注入非法对象、重放合法旧消息或在缺少权限时尝试调用。凭证泄露及获准实体主动共享密钥不由 ABE 单独解决。

认证通过信任规则下的签名和证书链验证识别签名身份，授权决定是否允许操作，保密性限制谁能恢复 Content。合法凭证不保证负载报告真实、推理正确或图像内容可信。签名状态只有被获取和验证后才影响本地授权；断连节点不可能被假定立即获知撤销。期限判断必须明确时钟及容许偏差。

\section{授权与保密性}
\input{\proposalroot/ch/chapters/authorization-rationale}
发现 descriptor 的保密范围是缺少相应 ABE 解密能力的实体，不排除其他获准候选，也不隐藏流量。在请求级保护设计中，User 用对称密钥加密应用输入，并通过 Selection 交付所需密钥材料；这些材料加密给经过认证的选定 Provider 公钥。响应密钥由请求方 User 和选定 Provider 共享。其他 User 在密钥未泄露的假设下不能解密结果；生成结果的 Provider 必然知道明文。这里定义被评估设计的保护要求，而非所有历史实现路径的行为。

\section{拟议扩展：从 ACK 集合到协作计划}
扩展将选择问题从挑选一个执行者变为分配互补任务角色。应用提供角色／依赖模板、所需服务、约束和期限。模板可以手工编写，不要求新发明自动规划算法。ACK 窗口关闭后，可替换策略从合格 positive ACK 中分配 Provider。冻结的是本次已观察到的候选，不是全网所有可能参与者；执行时仍需重新检查资源。

在拟议设计中，User 签名的 Plan Manifest 包含请求标识、候选快照、角色分配、命名依赖边、授权／密钥范围与执行身份。摘要来自不含自身 digest 字段的规范化计划正文。Provider 验证签名计划后才导出本地依赖检查；长期证书不指定本次分工。User 必须记录已提交计划并拒绝同一执行身份下的不同计划。这是受信 User 模型下的本地状态机规则，不是签名本身的性质，也不抵抗 User 故意签署冲突计划。

\section{命名对象准入与恢复}
按拟议准入规则，下游 Provider 接受依赖前先检查执行仍然活动且未超出截止时间，再验证信任规则下的 Data 签名、当前请求／计划／执行身份、指定前驱生产者，以及声明边允许的名字／数据格式／密钥范围。所需分段须全部通过验证；不完整或格式错误的对象不能满足依赖。生产者、缓存和仓库获取执行相同检查。计划引用实际生产者授权命名空间中的对象，而不以其他生产者身份重新发布。

\section{有条件的正确性论证}
假定签名密钥安全、信任／授权检查正确、Provider 遵守状态机：全部启动路径须核验活动 Selection 及未使用的一次性授权状态；全部输入路径（含缓存）须核验指定生产者和声明边。重分配须隔离旧 worker 和迟到回调。重启须保留相关状态或使其安全失效；签名和 FreshnessPeriod 不能替代这些检查。

这些是有条件的不变量和实现论证义务，不是完整系统的密码学证明。反例应包括同请求错误角色、合法签名生产者提供未声明边、重分配后迟到回调，分别检验 request ID 本身不表达的性质。应用结果语义及物理副作用仍不属于该论证。

\chapter{应用验证}
\section{UAV：多视角采集、处理与返回}
主案例是地图上的地面位置请求，而非完整自主任务系统。发现时只提供判断覆盖、视角、传感器及时间可行性所需的受服务权限保护的信息。候选返回 ACK，计划选择互补采集角色和处理角色，Selection 交付执行细节及密钥。

在拟议 UAV 流程中，采集 UAV 签名包含加密图像内容的 ViewImage Data，在自己的授权命名空间发布，并附观察时间及可用姿态／标定元数据；内容加密不隐藏外层 Data 名称。GPS 不足以独立确定视线、相机方向、深度或跨视角对应；应用需规定采集容差、视角质量和失败处理。处理 Provider 按授权边获取图像，执行规定分析并发布 Annotation Data，返回原图引用并在给请求方的加密结果中提供获准分享的图像密钥。User 获取原图和标注后绘制叠加结果，不要求重新发布同一原图。

框架主指标是截止时间内完成授权的采集—处理—返回。只有声称提高识别／定位精度时，才另外要求 ground truth、单视角对照与确定的融合算法。MiniNDN~\cite{minindn} 和 PX4 SITL~\cite{px4} 可分别检验网络及应用／飞控接口，但不等同实飞安全认证。控制、直播、录制与巡逻功能是支持工程，不全部变成毕业验收项。

\section{DI：计算、数据与状态依赖}
pipeline 切分分配连续层或层组；tensor 切分分割算子／张量并需要相应 collective。ONNX~\cite{onnx} 表示计算图，导出模型本身不会完成跨节点 collective 或证明数值正确。模型切分已有相关工作~\cite{neurosurgeon,ddnn}；NDNSF 的候选增量是运行时分配和命名依赖检查。

规划器结合支持的模型／切分说明与 ACK 能力，Provider 准备授权模型片段，通过声明边交换 activation 或 collective 输入。Repo 是受管理的存储；Content Store 是机会缓存。模型文件复用与请求级 activation／状态复用必须区分。

使用 KV cache 时，模型计算 key/value（K/V）张量，运行时代码保留相关状态供后续解码复用。复用可以采用共享缓冲区，不要求每一步复制整个 cache~\cite{ortkvcache}。权重驻留不替代该请求特定状态。自回归生成还需将生成的 token 用于下一步输入，这是时间上的依赖，不同于逐层前向计算。若保留 LLM 流式主张，需另报 prefill、首 token、后续 token 和 KV 驻留／传输成本；结论限定于实际验证的模型与切分配置。

截至本次 2026 年 9 月修订，原生实现已有定向测试证据，但声明的进程、设备和恢复配置尚未全部完成端到端验证。仅限单进程的测试不能证明跨进程行为。较早小模型实测不验证较新的模型片段复用、tensor/hybrid、多加速器或大语言模型恢复路径。最终固定模型、精度、切分、显存、网络、冷热状态和输出容差；单设备能运行则保留基线，不能运行则只论证分布式可行性。

\chapter{结论}
本研究以初版 NDNSF 从多个候选中选定一个 Provider 完成调用的能力为基础，评价发现／授权设计，并研究面向互补角色和命名依赖的协作扩展。候选贡献是经评价的服务协议及有证据支持的机制选择，不是新密码学原语或首次命名计算。RQ1 比较 ABE-backed 授权与 DNMP-inspired 角色规则配合内容加密，纳入管理和撤销成本；RQ2 把运行时分工变成本地命名依赖准入规则；RQ3 分别评价调用与协作的收益和成本。已有实验支持有限调用结论；协作与跨应用主张仍需其声明的端到端证据。本 Proposal 据此给出可核查的 dissertation 完成路径。
