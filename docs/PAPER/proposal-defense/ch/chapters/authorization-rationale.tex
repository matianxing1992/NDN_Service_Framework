\subsection{采用 ABE-backed 服务授权的理由}
\label{sec:abe-rationale-ch}

NDNSF 使用 ABE 保护发现描述，并在调用检查中复用基于属性的服务权限。
前者解决具体参与者尚未确定时的内容保密问题；后者让服务权限与身份签名凭证
分离管理。这不意味着 ABE 总优于角色授权配合适当加密；撤销和换钥仍是需要
评估的生命周期成本。执行授权决定 User 是否可以调用服务，
Provider 授权决定实体是否可以提供该服务；内容机密性限制谁能读取受保护内容。
Controller 管理服务权限，User 和 Provider 在调用过程中检查这些权限，并执行
信任规则下的签名验证与调用状态检查。获准提供服务不等于被选中执行某一次任务。

\paragraph{理由一：选择 Provider 之前的保密发现。}
在选择 Provider 之前，User 发布 discovery descriptor（发现描述），其中
包含 Provider 决定是否返回 positive ACK 所需的位置、截止时间和资源要求。
例如，附近 UAV 需要知道观察区域和到达时限才能决定是否参与，但此时不需要
完整应用输入。User 使用 ABE 和所请求服务的属性加密发现描述，无需逐一列出
Provider 身份。这里的保密对象是缺少相应解密能力的外部
观察者；获准但最终未被选中的 Providers 仍可读取。内容加密不隐藏外层 Data
名称或流量模式。在请求级机密性路径中，应用输入使用请求级密钥加密，Selection
将该密钥保护给选中的 Provider，请求方 User 仍保留访问能力。Trust Schema
本身不加密内容；角色授权方案也可以配合 ABE 或
服务组加密来实现发现阶段的保密性。

节点可以获取或缓存加密的 Request Data，而不获得解密权限。
交付与披露的分离也适用于其他内容加密方案，并非 ABE 独有。

\paragraph{理由二：在服务调用中复用基于属性的权限。}
保密发现本身不足以论证 ABE-backed 执行授权：ABE 加密也可以配合基于角色的
调用检查。NDNSF 选择通过已有的属性授权机构管理 Provider 和 User 两类服务
权限，并将这些权限与身份签名凭证分离。

Provider 权限决定其能否获取 Requester Challenge，User 权限决定其能否获取
Provider Challenge。NDNSF 将返回的 challenge 值与签名、当前权限及请求状态
一起检查（第~\ref{sec:authorization-withdrawal-ch} 节）。因此，解密能力只是
调用检查的一部分，不代表可以执行任意请求。

DNMP 则通过角色签名密钥与 Trust Schema 约束命令目标和动作~\cite{dnmp}。
在第~\ref{sec:dnmp-alternative-ch} 节的 DNMP-inspired 对照方案中，若保留
ABE 保护发现描述，就需要同时管理解密权限和基于角色的调用权限。NDNSF 在
两类服务级检查中复用属性授权机构，无需仅为表示服务成员资格而增加角色签名
凭证；验证 Data 签名所需的信任规则仍须保留。

这是复用管理机制的理由，并非已证明的成本优势。Provider 与 User 权限仍然
不同；发现加密并不已经提供 User 权限解密密钥或 challenge 处理。若策略
需要限制命令参数，DNMP 的 Schema 检查可能比 NDNSF 的服务级检查更合适。评价应
在相同策略粒度下比较凭证更新和调用开销。

\paragraph{理由三：权限聚合作为额外的管理便利。}
KP-ABE 将属性关联到密文，将访问策略编码到解密密钥（DKEY）
中~\cite{dulal2023nacabe}。NDNSF 使用 \texttt{/SERVICE/<service>} 表示
Provider 访问权限，使用 \texttt{/PERMISSION/<service>} 表示 User 访问权限。
在同一授权机构和参数代际内，一个实体的多项服务权限可以合并到为其单独签发
的 DKEY 中。例如，一个 User 的策略允许检测 OR 地图服务，另一个仅允许检测
服务；这些不同的服务集合不需要通过改变身份签名凭证来表示，各服务的密文仍
使用各自的服务属性。

这种聚合补充了理由二：在复用的授权管理设施中，将多项服务权限与签名凭证
分离组织。它并非 ABE 独有的能力，DNMP 的角色和签名凭证也可以覆盖多项
权限~\cite{dnmp}。一份 DKEY 不代表固定大小或固定成本，策略复杂度、密钥
分发、更新与撤销仍需考虑。其好处是便于组织服务权限，而不是证明总成本低于
基于 Trust Schema 的授权方案。

\subsection{授权机制、生命周期与成本}
\label{sec:authorization-withdrawal-ch}

\paragraph{将解密能力关联到调用授权。}
在 ABE-backed 调用路径中，User 将 Requester Challenge（\texttt{UserToken}）
放入受保护的 Request 内容。Provider 恢复该值后在 ACK 中返回，User 将其与
活动请求中的值比较。Provider 将自己的 Challenge（\texttt{ProviderToken}）
放入受保护的 ACK 内容，并在执行前检查 Selection 中对应的 challenge response。

这些检查表明参与者能够获得受保护的 challenge 值，不会创建新权限，也不是
密钥独占持有的形式化证明。双方还需按信任规则验证消息签名和证书链，检查当前
服务权限，并匹配请求及其状态。一次性状态只有被保留或在重启时安全失效，才能
防止重复消息授权另一次执行；获准实体主动共享密钥或 challenge 不在所声称的
防护范围内。这沿用了属性化权限管理，而不是另设一套基于角色的调用规则，但
并非没有额外成本：保密发现已需要 Provider DKEY，而 User 的调用权限 DKEY
和 challenge 处理仍是额外授权成本。ABE 保密配合 DNMP-inspired 角色授权同样是有效的
替代方案。

\paragraph{运行时权限撤销与评估。}

当前运行时通过 Controller 签名的授权状态以及调用处理点上的检查实现权限
撤销。参与者需要获取并验证更新后的状态，才能执行新公布的权限撤销。
ABE 参数轮换和 DKEY 更新保护随后使用新代际加密的交换。目前轮换作用于整个
Controller 的 ABE 参数代际，其他仍获授权的成员也可能需要刷新 DKEY；
这不是无需更新其他成员的撤销方案。

DNMP 规定了有效期约束与防重放状态处理~\cite{dnmp}；这些机制本身不等于立即
撤销尚未过期的角色密钥。作为对照设计，DNMP-inspired 方案可以撤销相关凭证，
并要求执行节点检查签名的撤销状态或拒绝过期证书。这是在验证方取消凭证
所代表的权限，而不是物理取回已分发的证书。两类方案都需要传播更新信息，
也都无法收回已披露的密钥或明文。

定向集成测试已检验 NDNSF 的运行时撤销检查，包括身份级、证书级和服务级
撤销。这些测试支持已覆盖运行时边界上的行为，不代表整个网络中的瞬时撤销，
也不能证明其成本低于证书方案。后续评估应测量状态传播延迟、拒绝生效延迟、
重新分发密钥的流量，以及对未撤销成员的影响。因此，运行时状态验证和密钥
轮换使 NDNSF 支持权限撤销，同时带来明确的状态传播和重新分发密钥的成本。
