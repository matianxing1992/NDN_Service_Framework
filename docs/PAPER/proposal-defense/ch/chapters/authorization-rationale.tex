\subsection{采用 ABE-backed 服务授权的理由}
\label{sec:abe-rationale-ch}

NDNSF 使用 ABE 保护发现描述，并在调用检查中复用基于属性的服务权限。
前者解决具体参与者尚未确定时的内容保密问题；后者让服务权限与身份签名凭证
分离管理。这不意味着 ABE 总优于角色授权配合适当加密；撤销和换钥仍是需要
评估的生命周期成本。执行授权决定 User 是否可以调用服务，
Provider 授权决定实体是否可以提供该服务；内容机密性限制谁能读取受保护内容。
Controller 管理服务权限，User 和 Provider 在调用过程中检查这些权限，并执行
信任规则下的签名验证与调用状态检查。获准提供服务不等于被选中执行某一次任务。

该设计面向三个要求：参与 Provider 尚未确定时不公开发现描述；认证参与者身份、
验证服务权限并拒绝重放调用消息；运行时授予和撤销服务权限。权限聚合是额外的
管理便利，而不是第四项安全保证。

\paragraph{理由一：选择 Provider 之前的保密发现。}
在选择 Provider 之前，User 发布 discovery descriptor（发现描述），其中
包含 Provider 决定是否返回 positive ACK 所需的位置、截止时间和资源要求。
例如，附近 UAV 需要知道观察区域和到达时限才能决定是否参与，但此时不需要
完整应用输入。User 使用 ABE 和所请求服务的属性加密发现描述，无需逐一列出
Provider 身份。这里的保密对象是缺少相应解密能力的外部
观察者；获准但最终未被选中的 Providers 仍可读取。内容加密不隐藏外层 Data
名称或流量模式。在请求级机密性路径中，应用输入使用请求级密钥加密，Selection
将该密钥保护给选中的 Provider，请求方 User 仍保留访问能力。Trust Schema
本身不加密内容；角色授权方案也可以配合 ABE 或
服务组加密（使用共享组密钥加密）来实现发现阶段的保密性。

节点可以获取或缓存加密的 Request Data，而不获得解密权限。
交付与披露的分离也适用于其他内容加密方案，并非 ABE 独有。

\paragraph{理由二：在服务调用中复用基于属性的权限。}
保密发现本身不足以论证 ABE-backed 执行授权：ABE 加密也可以配合基于角色的
调用检查。NDNSF 选择通过已有的属性授权机构管理 Provider 和 User 两类服务
权限，并将这些权限与身份签名凭证分离。

Provider 权限决定其能否获取 RequestNonce，User 权限决定其能否获取
ProviderChallenge。NDNSF 检查 ACK Data 中的 RequestNonce，并使用保存的
ProviderChallenge 验证 Selection Data。签名、当前权限和请求状态检查仍是
独立要求（第~\ref{sec:authorization-withdrawal-ch} 节）。因此，解密能力只是
调用检查的一部分，不代表可以执行任意请求。

DNMP 则通过角色签名密钥与 Trust Schema 约束命令目标和动作~\cite{dnmp}。
在第~\ref{sec:dnmp-alternative-ch} 节的 DNMP-inspired 对照方案中，若保留
ABE 保护发现描述，就需要同时管理解密权限和基于角色的调用权限。NDNSF 在
两类服务级检查中复用属性授权机构，无需仅为表示服务成员资格而增加角色签名
凭证；验证 Data 签名所需的信任规则仍须保留。

评价将测量共用管理基础设施的成本与收益。Provider 与 User 权限仍然
不同；User 权限解密密钥及 challenge 处理会增加描述加密以外的成本。若策略
需要限制命令参数，DNMP 的 Schema 检查可能比 NDNSF 的服务级检查更合适。评价应
在相同策略粒度下比较凭证更新和调用开销。

\paragraph{理由三：权限聚合作为额外的管理便利。}
KP-ABE 将属性关联到密文，将访问策略编码到解密密钥（DKEY）
中~\cite{goyal2006abe,dulal2023nacabe}。NDNSF 使用 \texttt{/SERVICE/<service>} 表示
Provider 访问权限，使用 \texttt{/PERMISSION/<service>} 表示 User 访问权限。
在同一授权机构和参数代际内，一个实体的多项服务权限可以合并到为其单独签发
的 DKEY 中。例如，一个 User 的策略允许检测 OR 地图服务，另一个仅允许检测
服务；这些不同的服务集合不需要通过改变身份签名凭证来表示，各服务的密文仍
使用各自的服务属性。

相比 DNMP 基于角色密钥的授权~\cite{dnmp}，NDNSF 在 DKEY 中表示服务权限，
而非增加角色专用签名凭证。如果等价权限需要多个不同角色凭证，这避免了签发和
维护这些额外签名凭证。比较取决于角色粒度：一个 DNMP 角色可以允许多种命令，
Trust Schema 也可以支持其他凭证安排。因此，评价将同时测量需独立管理的凭证数、
DKEY 大小、策略复杂度、分发、换钥及运行成本。

\subsection{授权机制、生命周期与成本}
\label{sec:authorization-withdrawal-ch}

\paragraph{身份认证。}
User 和 Provider 按适用的信任规则验证 Data 签名与证书链。这确定了被接受的
签名身份，但单独不能确定该身份是否有权提供或调用所请求的服务。

\paragraph{服务权限验证。}
在 ABE-backed 调用路径中，User 为请求生成新的随机值 \emph{RequestNonce}，
并将其放入 ABE 保护的 Request 内容。这是 NDNSF 应用层的值，
不是用于转发重复／环路处理的 NDN Interest Nonce。Provider 恢复该值后在 ACK Data 中返回，
User 将返回值与活动请求中保存的值比较。因此，RequestNonce 既用于请求绑定，
也用于检查对方能否获取该服务保护的值。Provider 生成 \emph{ProviderChallenge}，
并将其放入 ABE 保护的 ACK 内容。User 使用恢复出的 ProviderChallenge 构造
Selection Data。执行前，Provider 使用为该请求保存的 ProviderChallenge 验证
Selection Data。这些检查结合当前服务权限检查，确定 Provider 能否提供该服务，
以及 User 能否调用该服务。

这些检查表明参与者能够获得受保护的 challenge 值，不会创建新权限，也不是
密钥独占持有的形式化证明。获准实体主动共享密钥或 challenge 不在所声称的
防护范围内。这沿用了属性化权限管理，而不是另设一套基于角色的调用规则，但
并非没有额外成本：保密发现已需要 Provider DKEY，而 User 的调用权限 DKEY
和 challenge 处理仍是额外授权成本。ABE 保密配合 DNMP-inspired 角色授权同样是有效的
替代方案。

\paragraph{防重放。}
参与者将消息匹配到活动请求及其协议状态。Provider 记录 ProviderChallenge
是否已用于接受 Selection Data 并启动执行；再次收到相同 Selection 不得启动
另一次执行。这要求适当保留和失效请求状态，包括重启时的处理。加密或持有
challenge 值本身都不能防止重放。这些准入检查也不保证跨崩溃的应用副作用恰好
发生一次。

\paragraph{运行时授予与撤销权限。}

\texttt{PolicyStatusData} 指 Controller 签名的命名 Data 状态载荷，本身不是
授予权限的操作。它标识服务、当前 ControllerVersion、有效期、策略摘要、可选的
ABE 公共参数名称／摘要、Controller 证书和撤销目标。参与者先验证外层 Data 签名及
状态内容，再更新本地权限或 DKEY；它用于传播和认证策略状态，不单独授予权限。

Controller 为两种操作更新权限状态。普通授予更新目标实体的完整权限策略，
该实体获取替换 DKEY，ABE 公共参数保持不变。撤销还会轮换 Controller 的
ABE 主密钥与公共参数；仍有权限的实体获取编码其剩余权限的替换 DKEY。
主密钥保留在 Controller，轮换范围是整个 Controller，而非仅被撤销的服务。

在拟议的更新发现路径中（目前尚未完成端到端验证），Controller 将更新后的公共参数发布为签名的 Named Data，
并通过 Sync 宣告其可获取。参与者获取并验证公共参数与 Controller 签名的
\texttt{PolicyStatusData}，按需刷新 DKEY。普通授予虽不更换公共参数，仍要求
参与者发现并获取更新后的权限状态。Sync 用于发现更新，不是授予权限的依据。
本机实现支持状态获取与参数轮换；专用 Sync 宣告路径仍需端到端验证。

当前权限检查在获取并验证新状态后执行撤销；参数轮换限制使用新代际加密的交换。
断连节点不能立即应用更新，也不能收回已披露的密钥或明文。

\paragraph{生命周期对比与评估。}

DNMP 规定了有效期约束与防重放状态处理~\cite{dnmp}；这些机制本身不等于立即
撤销尚未过期的角色密钥。作为对照设计，DNMP-inspired 方案可以撤销相关凭证，
并要求执行节点检查签名的撤销状态或拒绝过期证书。这是在验证方取消凭证
所代表的权限，而不是物理取回已分发的证书。两类方案都需要传播更新信息，
也都无法收回已披露的密钥或明文。

定向集成测试已检验 NDNSF 的运行时撤销检查，包括身份级、证书级和服务级
撤销。这些测试支持已覆盖运行时边界上的行为，不代表整个网络中的瞬时撤销，
也不能证明其成本低于证书方案。后续评估应测量状态传播延迟、拒绝生效延迟、
重新分发密钥的流量，以及对未撤销成员的影响。因此，运行时状态验证和密钥
轮换支持运行时权限变更，同时带来明确的状态传播和重新分发密钥的成本。
这些并非 ABE 独有能力。NDNSF 为保密发现引入 ABE，并复用其服务权限管理
进行调用检查和权限更新；签名验证与请求状态检查仍是独立且必要的设计组成。
