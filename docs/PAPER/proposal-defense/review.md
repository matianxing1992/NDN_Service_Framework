## 1. 结论先说

老师最主要的意见成立：目前的 slides 是“介绍 NDNSF 有哪些功能、用了哪些机制”，还不是足够清楚的“研究哪些问题、为什么值得研究、为什么选择这些机制、怎样判断研究成功”。

这不是把标题全部改成问句就能解决的。需要补出真实的推导链：

**应用任务 → 具体困难与后果 → NDN/已有工作已解决什么、还剩什么 → 可检验的研究问题 → 候选方案与选择依据 → 验证。**

目前最明显的结构问题是：

- P4、P13、P14 已声称框架和贡献，但需求从何而来尚未展示。
- P15 的 RQ 混合了需求调查、已选机制的评价、应用开发和研究问题。
- P17–27 连续介绍实体、消息、策略和配置；听众还不知道为什么需要这些步骤。
- 具体 UAV 和 DI 需求直到 P36–41 才出现，晚于相关机制和不少实验。
- “NDNSF is the dissertation contribution” 表达的是一个系统名称，不是可以被评价的研究贡献。

建议重构主讲部分，而不是继续在现有 62 页上逐条加页。系统原理和已有实现可以保留，但要改变其在论证中的作用。

## 3. 先从一个任务中真正导出问题

建议开场用已经讨论过的 UAV 协作场景，而不是“IP 有哪些问题”。这是场景化需求说明，不声称当前版本已经完成全部流程。

操作者在地图上指定一个观察目标区域，希望在指定时间内得到多个角度的图像和识别结果。附近可能有多架 UAV，但并非每架都能在该时限内到达、获得合适视角或提供所需传感器；一架较大 UAV 或 edge node 承担图像识别。操作者希望选择合适的拍摄者和处理者，并获得能对应到各个视角的结果。

这里要主动说明：GPS 位置和可达性不等于可用视角；ACK 是 Provider 对当前条件的报告，不是对未来成功的保证。应用负责估计视角/到达可行性，框架负责交换、选择和约束执行。

| 案例中的具体困难 | 应导出的框架问题 | 不应偷换成的结论 |
|---|---|---|
| 有权限或能联网的 UAV，不一定现在能按要求拍摄 | 如何发现本次愿意且具备条件的 Provider，并在执行前选定它们？ | NDN 路由找到节点就完成了服务发现。 |
| 判断是否参加需要知道区域、时限和设备需求，但这些内容不宜向公众公开 | 如何让获准 Provider 读取足够的发现信息，而无需事先枚举它们？ | 必须使用 ABE；或所有有权限的人都应看不到 Request。 |
| 多个拍摄者和一个处理者承担不同工作 | 如何表达并执行角色分工与数据依赖？ | 同时选中多个 Provider 就已经实现协作。 |
| 图像可能从拍摄者、Repo 或缓存取得 | 如何确认它是本任务允许的角色产生、供这条依赖使用的数据？ | 缓存不可信；或现有 requestId 完全不起作用。 |
| 拍摄完成后某节点失联，处理者可能仍能获取已发布图像 | 哪些工作应重试、哪些对象可复用、何时重新选择或终止？ | 网络重传会自动完成整个服务任务。 |

然后用 DI 说明哪些问题可以推广：Provider 具有不同可用内存、加速器和已存模型对象；执行依赖变成模型分片间的数据依赖。不要把“写一个 DI 应用”本身作为研究问题。模型分片算法、物体识别算法和飞行控制也不自动都是 NDNSF 的贡献。

对于“需求是否完整”，建议明确限制研究范围为：有管理的信任域内、Provider 运行时条件变化、需要远程调用或多角色协作的网络应用。用案例和已有工作交叉核对需求，不宣称覆盖任意服务平台；计费、业务事务、全局最优调度等未研究内容应明确排除。

## 4. 建议把五个 RQ 收敛为三个候选研究问题

这是待确认的建议，不是通过改名就成立的新颖性结论。每个问题都需要相关工作边界和评价设计。

### RQ1：运行时服务发现与授权

**How can a requester discover and authorize providers based on their current willingness and capabilities, without exposing non-public discovery information to unauthorized parties?**

关注“有权限”和“本次能服务”不是同一件事。ACK、Selection 和 ABE 是候选回答，不应先写进问题作为必然选择。

验证：候选选择是否符合约束，信息披露给谁，越权请求是否拒绝，发现延迟/消息量/密码学及凭证更新成本。比较完整替代方案，不能只与一个不带加密的 Trust Schema 方案比保密性。

### RQ2：运行时选定 Provider 的多角色协作

**How can multiple providers selected at runtime execute a task according to its role and data dependencies, when intermediate Data may be retrieved from producers or caches?**

关注真实缺口：同一个 requestId 内，也可能有多个有合法签名的 Provider；需要明确谁承担哪个角色，谁的哪个输出可以驱动哪个后续步骤。不能再把已有 requestId 已排除的跨请求混用当作新问题。

应用可以手工给出工作流模板或依赖图；运行时分配策略根据候选条件填入 Provider。图的来源、选择策略和框架的检查职责应分开，不必假定 NDNSF 发明通用自动规划算法。

验证：正确前驱被接受、错误角色/依赖被拒绝、直接和缓存获取执行同样规则；比较静态分配、集中转发、分布式消费等设计的条件与成本。

### RQ3：变化中的执行恢复与数据复用

**When providers or connectivity change during execution, which work and named Data can be safely reused, and when should the framework retry, reassign, or terminate the task?**

这不是研究“NDN 如何转发到移动节点”。它研究请求/任务语义：何时认为执行失败，已有结果是否仍符合本任务授权和时效要求，重做是否有副作用，以及截止时间内何时应终止。网络连通性仍是必要条件，不能承诺无连接也能完成服务。

验证：截止时间内任务完成率、恢复时延、重复执行/副作用、重复传输量、对象复用量和失败边界。若没有相对现有框架的独立机制和证据，这一项应降为 RQ1/RQ2 的评价维度，不要硬凑第三项贡献。

原 RQ1 的“有哪些服务层功能”作为需求分析方法；原 RQ3 的性能取舍分配到上述各问题；原 RQ4/RQ5 的 UAV/DI 作为需求来源和验证场景。这样既不把 NDNSF 缩成仅协作框架，也不把应用名称当研究问题。

## 5. 每个机制都需要回答“为什么不选另一种”

| 机制选择 | 要解决的问题 | 主讲必须说明的理由与边界 |
|---|---|---|
| 使用命名、签名的 Data 表示协议对象 | 请求、状态和结果可能异步取得并经缓存/存储转交 | 对象可独立命名和验证；仍需信任锚、检索和应用状态。应承认 signed Interest 调用也是可行设计，说明为何本工作需要较丰富的发现/协作对象。 |
| Request–ACK–Selection | 多个有权限的 Provider 中，谁本次可以且愿意执行？ | 将条件询问、当前状态报告与执行选择分开；代价是额外交互、窗口等待和状态管理。 |
| positive/negative ACK | 用户需要区分“没有回复”和“明确暂不能服务” | 区分业务不可用与消息未到；ACK 不等于资源预留，收集窗口也不是全网候选的完备快照。 |
| ABE 保护 discovery descriptor | 接收者身份尚未由 User 选定，但读取权限可按服务定义 | 保护内容免于缺少解密能力者读取；服务组密钥等也是替代方案。授权但未选中的 Provider 仍能读，外层名称仍可能泄露信息。 |
| ABE-backed challenge | 如何在调用中使用机构授予的 ABE 权限？ | 复用服务权限管理，配合签名与请求状态作检查；不是所有执行授权方案都需要它，User DKEY 和 challenge 处理仍有成本。 |
| Selection 后使用接收者专属的输入/结果保护 | 完整应用输入只应交给选定执行者，结果应按请求范围保护 | 区分发现信息与实际输入；准确标注对应实现版本/请求路径，不能回填为所有历史路径默认具备。 |
| 角色分配与命名依赖检查 | 有合法签名的数据也未必是本步骤需要的前驱输出 | 用角色、依赖和任务状态决定使用对象；不夸称现有签名或 requestId 没有保护作用，也不把这等同分布式原子事务。 |
| 有界重试/重新选择和对象复用 | Provider 失效时可能只需重做部分工作 | 区分重取数据与重新执行；说明副作用、取消和时限语义，评估控制开销而不是保证无条件恢复。 |

每张机制页推荐同一结构：**Problem / Alternatives / Choice / Tradeoff / Evidence**。主讲可压缩到其中三四项，但讲稿必须能解释全部五项。

## 6. 如何准确回应老师对 Trust Schema 和 token 的意见

### 应接受的批评

原 P21/P22/P57 把 challenge、请求匹配、重放拒绝和授权混在一起，而且把“普通验证”作为过弱的对照。它没有回答为什么不直接用角色签名和规则控制命令执行。

Trust Schema 不是只有“签名数学上正确”的检查。它描述允许的数据/密钥关系，验证链需要落到已建立的信任锚；因此不能说 NDN 有签名就不用信任配置。[Schematizing Trust in NDN](https://named-data.net/wp-content/uploads/2015/11/schematizing_trust_ndn.pdf)

DNMP 确实依据命令目标、probe 类型/参数和角色约束选择签名密钥，并由接收方验证命令；这是实际命令授权的先例。[DNMP 原论文](https://named-data.net/wp-content/uploads/2019/10/kathleen.pdf)

NSC 也明确区分保护执行资源和保护敏感数据，使用初始 signed Interest 和应用定义的 Trust Schema 检查调用来源。因此不能暗示其他 NDN 调用框架只会验证结果，完全没有执行前检查。[NSC technical report，§4.2](https://named-data.net/wp-content/uploads/2021/05/ndn-tr-0074-1-nsc.pdf)

### 不应据此推出的结论

不能从“Trust Schema 可以授权”推出“NDN 禁止 challenge”，也不能从“Trust Schema 本身不加密”推出“ABE 是唯一合理设计”。需要比较完整方案：

1. DNMP-inspired 角色签名授权，加独立内容保护和请求状态。
2. NDNSF 的 ABE 权限管理、challenge、身份签名和请求状态组合。

建议口头回答：

> The Controller grants service permissions before invocation. The challenges do not create those permissions; they let the invocation protocol check access to the required ABE decryption capability. Signatures and request-state checks remain necessary. We retain this design to reuse service-permission management for protected discovery and invocation, and compare its credential, rekeying, and runtime costs with DNMP-inspired authorization supplemented by content encryption.

这解释了设计依据，但没有声称 challenge 在理论上不可替代。权限由策略机构授予；是否愿意服务由 Provider 报告；选择由 User 作出；challenge 是检查机制。需要将这几个动作拆开画清楚。

“运行时撤销”可以作为完整生命周期能力，必须同时披露状态传播和换钥成本；它不是 ABE 独有优势。本轮没有重新验收撤销代码，最新实现事实仍应以对应源码与测试记录为准。

## 13. Final Defense 审查结论：需要完成的是证据链，不只是措辞

不能只把 proposed / expected / will 改成 completed / demonstrates。若结论依赖尚未完成的验证，应完成验证，或缩小最终贡献范围。当前 Spec 的所有工程任务也不自动都是毕业前必须完成的研究任务；应由实际 dissertation 核心主张决定证据要求。

| 运行时发现与 ABE-backed 授权 | 在何种信任/部署假设下，以何种成本发现并授权本次可参与 Provider？相对完整替代方案有何取舍？ | 完整调用流程、威胁/策略边界、授权反例、匹配调用对照；若声称管理收益则加生命周期成本 | 仅介绍 ABE 算法；只有一张成功截图；仅证明 Trust Schema 不加密 |
| 多角色协作与数据依赖检查 | 哪些运行时分配和对象使用错误被机制排除？为何仅有请求 ID 或长期角色规则不足以表达本任务分工？ | 任务级状态机、合法/非法角色和边实例、端到端依赖执行、直接/缓存同规则检验、机制开销 | 选择多个相同服务 Provider；只验证 Data 签名；老原型的推理延迟 |
| 恢复/复用（仅在具有独立研究增量时） | 何时重取、重做、重分配或终止；能复用哪些工作/对象；代价和适用条件是什么？ | 明確故障注入、重复/副作用观察、恢复轨迹、截止时间内完成率、字节/执行量分解 | 普通网络重传成功；一份恢复设计文档；单一成功路径 |

每张卡必须能填出一句有限定条件的结果，例如“在 X 配置/负载/攻击模型下，机制 A 相比 B 改变了指标 Y；代价是 Z，条件 W 下无优势”。没有数据时保留空项或标未测，不编造数值，也不通过挑选有利场景填满卡。

如果最终只证明了前两项，则形成两项扎实贡献；不要为了维持三条 RQ 把常规恢复功能包装成独立创新。

## 16. 验证应该如何加强，而不是无边界增加实验

以下是由 NDNSF 的具体安全、正确性和性能主张推导的验证建议，不是从学校表格照抄的毕业门槛。最终保留什么主张，才决定哪些验证不可缺少；不要求把全部协议模式、模型类型或 Spec182 工程任务都做完。

### 16.1 先把正确性从性能里分离

最低需要将以下性质逐项写成可检查条件，只有进入最终主张的机制才必须执行对应验收：

- 未授权 User 不能触发所声称受保护的服务处理；不仅返回 error，还应观察是否启动了处理/副作用。
- positive ACK 不自动启动任务；未选中/已取消的执行者不因迟到消息重新开始。
- 同一活动请求中，错误的角色生产者或未声明依赖被拒绝；合法前驱通过直接或缓存获取均可使用。
- 重复 Request/ACK/Selection 的语义明确；“缓存再次交付”和“业务再次执行”不能混为一谈。
- 重新分配之后，先前结果何时可用由任务语义与授权规则决定；不默认所有旧对象都作废，也不默认所有签名正确的旧结果均可复用。
- 权限撤销的状态获取、拒绝生效和后续密钥更新分别记录；不承诺收回历史明文。

不一定都要给出形式化定理，但应有明确假设、不变量、状态迁移论证和针对性反例。若声称“保证唯一/绝不混用/防止所有重放”，分析与测试覆盖必须足以支持该强度，否则缩小表述。

### 16.2 对照应隔离机制，而不是隔离一个不完善的对手

- **发现/选择**：比较相同候选数、负载与 deadline；如果一方有动态发现而另一方只用固定名单，则该实验仅回答该配置差异，不能证明对方框架无法动态发现。
- **授权**：角色证书方案也带所需加密和新鲜度/重放检查；ABE 方案计入 User/Provider DKEY、签名凭证、政策/状态分发和更新成本。
- **协作**：在同一任务图上比较静态/动态分配或不同执行检查策略。撤去某项检查的消融主要回答安全性质，不把不安全变体当推荐部署方案。
- **分布式推理**：单机能容纳模型时报告单机基线；不能容纳时可以证明可行性，但不能宣称相对无法运行的单机有可量化加速比。分清增加设备容量与协议优化的贡献。
- **恢复**：按失败时刻、已完成工作和副作用语义比较；网络不可达、Provider 拒绝、计算失败和结果未收到应分开。

### 16.3 统计与指标至少补清这些内容

1. 区分独立实验单位（如 seed/run）与同一运行中的多条请求，不能把相关请求全部当独立重复。
2. 报告所有预定运行及失败，不只报告最佳运行或成功运行的时延。
3. 明确 latency 的起止点、是否包含发现、排队、密钥获取、组装/加载和重试。
4. 成功请求的 p95 应与总体完成率/超时率并列；否则丢弃慢失败请求可能让系统“看起来更快”。
5. 条件性切换子集需有独立于比较结果、可复现的筛选规则，并报告总体及被排除部分。
6. 如果只观察到相近成功率，写 comparable observed completion；未做等价性/非劣分析时，不写已证明相同。
7. work initiations、处理时长、消息包数、应用对象数、网络字节和能耗分别定义，不能互相代替。
8. 小样本尾时延应报告不确定性；10 次成功运行不足以单独支撑一般化的尾延迟/可靠性优势。
9. 用消融或 profiling 支持因果解释；否则把“因为某机制”降为“与该解释一致”。
10. 保存源码/依赖/模型/参数/拓扑/随机种子和分析脚本身份。单纯列一个仓库 URL 不能复现冻结的图表。

扩展性测试应围绕实际主张选择变量：候选 Provider 数、并发请求数、服务/权限规模、任务图边数或对象大小。无需做所有维度的笛卡尔积，但不能用单个小规模场景证明“通用可扩展”。

### 16.4 UAV 与 DI 的边界

UAV 若只用于验证框架协作，可以把“正确完成多视角采集—处理—返回”作为主任务；只有声称提高识别/定位精度，才需要相应 ground truth、单视角对照、相同目标条件和精度指标。SITL 不等于实飞；有限硬件验证不等于安全认证。是否必须实飞取决于最终主张，不应为形式完整而扩大范围。

DI 应明确模型版本/精度、层或 tensor 切分、每设备可用内存、网络配置、cold/warm cache，以及输出比较准则。浮点分布式执行通常应给出约定容差及任务输出检查，不无条件要求所有平台逐 bit 相等。若最终包含 LLM/KV-cache/流式生成，则另报 prefill、首 token、后续 token、KV 驻留/迁移成本；若不在最终贡献范围内，移至未来工作，不加重当前主线。

## 17. Final dissertation 和 Final-defense slides 的组织方式

### 17.1 论文：按论证组织，不按开发目录组织

可以采用以下章节职责，具体章数可合并：

1. **Introduction**：一个真实任务、研究范围、统一 RQ、最终贡献与结果摘要。
2. **Background and Related Work**：只保留理解问题所需的 NDN/安全基础；按 RQ 比较最近工作。不要长篇网络教程后才出现研究问题。
3. **System Model and Protocol Overview**：参与者、信任边界、请求/对象生命周期、主要不变量、应用与框架的职责。
4. **Discovery and Authorization**：候选方案、NDNSF 的选择、实现边界及针对该选择的证据。
5. **Collaboration and Recovery**：角色/依赖、执行/恢复规则、正确性分析及证据；未形成独立恢复贡献时作为本章一部分。
6. **Application Validation and Cross-Case Findings**：UAV/DI 的精简端到端案例，共性需求、复用机制、应用专属部分及实测边界。
7. **Synthesis and Limitations**：综合权衡、什么条件下无收益、威胁/部署限制、外部有效性。
8. **Conclusion**：逐个回答 RQ，区分已建立结论与未来扩展。

大段配置、所有 API、GUI 状态清单、完整设备支持列表和部署步骤放附录/开发文档。保留一两个必要配置实例解释机制，但不再让“manual/spec”占据研究主线。

每个研究章尾部用同样四句结构：本章回答哪个问题；建立了什么结论；什么证据支持；什么条件下不适用。这比在末尾集中重复“NDNSF 是贡献”更有说服力。另在引言或贡献说明中区分本人完成的研究与合作者/既有库的工作；若采用期刊文章分章形式，还须满足第 20.1 节 M3 所列的作者贡献和篇章整合要求。

### 17.2 Slides：结果与解释成为主体

第 7 节约 28 页是 **Proposal** 结构。Final defense 应调整为更短背景、更多实际结果，不能原样保留“将来怎么评价”。一种约 26–30 页的主讲组织是：

| 区段 | 作用 | 与 Proposal 的差别 |
|---|---|---|
| 开场 4–6 页 | 场景、问题、范围、RQ、核心结论预告 | 提前说研究最终发现了什么，不只说打算做什么 |
| 总体模型 2–3 页 | 端到端流程与信任/失败边界 | 听众先理解完整系统，再看局部机制 |
| 每项核心贡献约 4–5 页 | 问题、替代方案、选择、关键结果、解释/代价 | 每个机制紧跟其证据，不把所有设计与所有实验分隔成两个大块 |
| 交叉案例 2–3 页 | UAV/DI 如何验证同一抽象与其限制 | 不现场罗列两套应用的全部功能 |
| 收束 3–4 页 | RQ 答案、局限、可推广经验、结论 | 研究计划/开发清单移备份；核心未验证内容不能藏到 future work 冒充闭环 |

普通结果页建议包含：**一句结论式标题 + 一张主图/表 + 必要实验条件 + 一条解释/限制**。讲稿能指出分母、样本、比较对象和为何能支持该结论。26–30 页不是学校要求；应先与导师确认主讲时长，再实测讲述与问答时间，不应为压页牺牲证据。外校的 45 分钟主讲示例不自动适用于孟菲斯。

## 18. 答辩前应能回答的十个问题

1. 去掉 NDNSF 这个系统名称，你的两三项研究贡献分别是什么？
2. 哪个实际任务暴露了每个问题？为什么只是 NDN 的名字、签名和缓存还不够？
3. 最接近的服务框架已经能做到什么？你增加的具体机制是什么，而非增加了哪些文件/API？
4. 为什么要等待 ACK 再 Selection？何时固定 Provider 或普通 signed invocation 更合适？
5. 为什么选择 ABE-backed，而不是角色证书加内容加密？什么情况下你的方案没有优势？
6. requestId 已有的保护是什么？在同一请求中，新增角色/依赖规则究竟排除什么错误？
7. 正确性依赖哪些信任、时钟、连接和状态条件？合法但恶意的 Provider 能造成什么？
8. 图中的优势是机制本身、更多候选、不同重试策略，还是额外资源造成的？怎样区分？
9. 哪些失败/负面结果改变了你的设计？为什么单机/单 Provider 有时更好？
10. 离开 UAV 和 DI 后，哪些原则可复用，哪些结论只适用于本次模型、拓扑和负载？

建议为每题准备一个 30–60 秒回答和一张对应备份证据页，而不是只背术语。

### 20.4 对上一版若干建议的明确修正

1. **不把三项贡献当作硬指标。** 第 4、15 节的三项划分只是组织候选；本轮核对的材料不支持“恰好三个 RQ/贡献才够毕业”。贡献范围和深度由导师与委员会判断。
2. **不把顶会论文审稿要求直接变成学位规则。** 正式模型、安全反例、消融和匹配基线可以对特定主张非常必要，但不是本校评价表列出的固定实验包。允许用适当论证支持有限主张，不能要求每个工程模块都完成全面 benchmark。
3. **不因使用现有机制就否定研究，也不因搭建框架就认定创新。** ABE-backed 的选择理由属于需要解释的研究决策；是否成为独立贡献，取决于其增量和证据，不靠更换名称。
4. **不把页数、章节数或主讲时间写成统一标准。** 第 17 节的八章、26–30 页是建议；孟菲斯本次查到的文件没有规定这些数字。先确认时间再排练。
5. **不能仅通过文件检查宣布“达到 final defense 标准”。** 论文/实验审查只能判断材料；现场表达与答问、最终学术判断和程序审批仍由委员会负责。
6. **Proposal 仍可以呈现未完成工作。** 用终期标准倒推准备，不等于现在就删掉 honest planned 标签。最终保留的核心主张需要完成相应论证；非核心扩展仍可列未来工作。

### 20.5 本次校准后的整体判断与下一步
