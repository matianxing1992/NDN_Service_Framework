\section{Application Experiments and Interpretation}
Individual invocations or application sessions supply observations. Comparative uncertainty is estimated across independently repeated runs, with shared seeds or traces paired across systems; requests within one run are not assumed independent.

\begin{samepage}
Before each comparative campaign, the workload definition will specify the primary outcome, completion deadline, and criteria for a practically useful improvement. Pilot runs will inform repetition counts; these choices will be fixed before the comparison and reported alongside effect estimates and uncertainty.
\end{samepage}

To operationalize RQ1, the study defines the following authorization cost model before selecting comparison configurations.

The first RQ1 comparison will retain ABE-encrypted discovery in both designs and change the invocation-authorization mechanism: protected challenges versus DNMP-inspired role-constrained signing. Both retain signature validation, Selection, request-state checks, current service-permission checks, and recipient-scoped input/result protection. This isolates authorization choice from discovery encryption; it does not measure the original DNMP implementation. Service-group encryption is a separate sensitivity comparison. Initial authorization tests use one User, four candidate Providers, and one permitted and one unpermitted service before scaling the configuration.

For UAV orchestration, the control relays the same signed, encrypted image objects through the User without changing their producer identity; direct exchange uses the assigned producer names. Both use equivalent protection and the same processing code. Image inputs are held fixed for this comparison, so it does not test a recognition benefit from additional views. Numerical tolerances for DI will be declared for the chosen precision before runs, not adjusted to fit the observed errors.

Each run records its workload, software revision, and network configuration. Report submitted, admitted, selected, completed, rejected, timed-out, and cancelled work separately where observable, with explicit denominators and deadlines.

Latency distributions identify the included requests and are reported alongside failure rates. A single exploratory run is labeled as such and does not supply a between-run uncertainty estimate.

For UAV sessions, record command completion latency, video start delay, useful frame delivery, recording retrieval completion, and status age at the operator. For multi-view work, additionally record the number of usable views, processing completion, and the analysis metric against labeled observations. The framework experiment first holds the recognition algorithm fixed. A separate application study is needed before attributing higher recognition accuracy to additional views.

For DI, report model preparation, prefill, time to first token, subsequent output rate, total completion, peak device memory, and bytes transferred between Providers. Compare cold and warm conditions separately. Evaluate a feasible single-Provider case alongside a supported partitioned case. If the distributed deployment exists because the model cannot fit one device, report that capacity benefit directly rather than inventing a speedup over an infeasible execution. Profile communication, serialization, cryptography, and model computation to locate the limiting cost.

Authorization evaluation should exercise both directions of service permission, not only successful decryption. Negative cases include an unpermitted caller, an unpermitted Provider, a validly signed message with the wrong protected value, and reuse after request state is closed. Grant experiments measure how an enrolled entity learns and applies a new permission. Withdrawal experiments measure update propagation, status validation, parameter/DKEY refresh, and rejection after the update is applied. Disconnected nodes and old ciphertext are separate cases with the limitations stated in Section~\ref{sec:abe-rationale}.

The collaboration ablations retain request-ID isolation and signature validation. Removing assigned-producer checks tests a wrong-role object within the same request; removing edge checks tests an undeclared input from an otherwise authorized participant. Replacement tests inject old work after reassignment. Outcomes record the check responsible for rejection and whether prohibited execution occurred. If another retained check rejects the object, that experiment does not establish the removed check's independent necessity. Valid-input controls prevent rejection of all work from being mistaken for correct enforcement.

Framework reuse can be assessed by documenting which invocation, authorization, object-transfer, and lifecycle components are shared by UAV and DI, and which adapters remain application-specific. Source size alone is not a sufficient maintainability metric. Record the changes needed to add a service type and the contracts that must be supplied. This supports the framework's engineering rationale while leaving protocol correctness and performance to their own evidence.

For the boundary study in Table~\ref{tab:framework-boundary}, both applications will exercise the same NDNSF runtime paths for wrong-producer rejection, undeclared dependencies, and late work after cancellation. Separate inputs will pass cryptographic and dependency checks but violate an application contract: an out-of-window image or a tensor with an incompatible declared model/shape. Record which layer rejects each case and verify that rejected input cannot start dependent application work. Valid controls must still complete. A correctly shaped tensor with incorrect values illustrates the remaining limit: numerical validation against a reference, not a signature, is needed. Record the adapters and runtime changes needed for each workload; duplicated checks or new application-specific branches in the runtime would indicate that the proposed division of responsibilities needs revision. These observations support a reusable contract for the tested workloads, not universal applicability to all services.

Deployment records should include dependency versions, model hashes, topology, link parameters, clocks, retry policies, cache configuration, and key-management settings without publishing secrets. Separate application failures from startup, configuration, and collection failures. A failed setup is not evidence of a protocol's inability to complete a request. These records allow the final dissertation to distinguish supported claims, useful negative results, and configurations that remain untested.
