\subsection{Rationale for ABE-Backed Service Authorization}
\label{sec:abe-rationale}

NDNSF uses ABE to protect discovery descriptors and reuses attribute-based
service permissions in its invocation checks. The first choice addresses
confidentiality before the participating Providers are known; the second
keeps service entitlements independent of identity-signing credentials.
Neither implies that ABE is always preferable to role-based authorization
with suitable encryption. Withdrawal and rekeying are lifecycle costs to evaluate.
Execution authorization determines whether a User may invoke a service;
Provider authorization determines whether an entity may offer that service.
Content confidentiality limits who can read protected content. The Controller
administers these service permissions; the User and Provider check them during
invocation. Signature validation under trust rules and invocation-state checks
remain necessary. Permission to offer a service is distinct from selection for
one particular task.

The design addresses three requirements: keep discovery descriptors non-public
before participating Providers are identified; authenticate participants, verify
their service permissions, and reject replayed invocation messages; and support
permission grants and withdrawals during operation. Permission aggregation is
an additional management benefit, not a fourth security guarantee.

\paragraph{Reason 1: confidential discovery before Provider selection.}
Before Provider selection, the User publishes a discovery descriptor containing
the location, deadline, and resource requirements needed for a Provider's
positive-ACK decision. For example, nearby UAVs need an observation area and
arrival deadline to decide whether to participate, but do not yet need the full
application input. The User encrypts this descriptor using ABE and the requested
service's attribute, without enumerating Provider identities. Confidentiality is against parties
lacking the required decryption capability: authorized but unselected Providers
can still read the descriptor. Content encryption does not hide outer Data names
or traffic patterns. In the request-scoped confidentiality path, the full
application input is encrypted with a request-scoped key; Selection protects
that key for the selected Provider. The requesting User retains access. A Trust Schema alone does
not encrypt content; a role-authorized design can also use ABE or service-group
encryption (encryption under a shared group key) to provide discovery confidentiality.

Encrypted Request Data can be retrieved or cached without granting decryption
access. This separation of delivery from disclosure also holds for other
content-encryption schemes; it is not unique to ABE.

\paragraph{Reason 2: reusing attribute-based permissions for service invocation.}
Confidential discovery alone does not justify ABE-backed execution authorization:
ABE encryption could instead be combined with role-based invocation checks.
NDNSF chooses to administer both Provider and User service permissions through
the existing attribute-authority infrastructure, separately from identity-signing
credentials.

Provider permissions determine access to RequestNonce; User permissions
determine access to ProviderChallenge. NDNSF checks RequestNonce in ACK Data
and validates Selection Data using the stored ProviderChallenge. Signature,
current-permission, and request-state checks remain separate requirements
(Section~\ref{sec:authorization-withdrawal}). Decryption is therefore one part of
the invocation check, not permission to execute any request.

DNMP instead uses role signing keys and a Trust Schema to constrain command
targets and actions~\cite{dnmp}. In the DNMP-inspired alternative
(Section~\ref{sec:dnmp-alternative}), retaining ABE for discovery would require
managing both decryption permissions and role-based invocation permissions.
NDNSF uses the attribute-authority infrastructure for both service-level checks,
without adding role signing credentials solely to represent service membership.
Trust rules for validating Data signatures remain necessary.

The evaluation will measure the costs and benefits of this shared management
infrastructure. Provider and User permissions remain distinct; User permission
decryption keys and challenge processing add costs beyond descriptor encryption.
For policies requiring command-argument restrictions, DNMP's schema-based checks may be a better fit than
NDNSF's service-level checks. The evaluation must compare both designs at the
same policy granularity, including credential updates and invocation overhead.

\paragraph{Reason 3: service-permission aggregation as an additional management benefit.}
KP-ABE associates attributes with ciphertext and an access policy with each
decryption key (DKEY)~\cite{goyal2006abe,dulal2023nacabe}. NDNSF uses
\texttt{/SERVICE/<service>} for Provider access and
\texttt{/PERMISSION/<service>} for User access. Within one authority and parameter
generation, an entity's service permissions can be combined in one individually
issued DKEY. For example, one User's policy can allow detection OR mapping,
while another allows detection only. Their identity-signing credentials need
not change to represent these different service sets; each service retains its
own ciphertext attribute.

Compared with DNMP's role-key-based authorization~\cite{dnmp}, NDNSF represents
service entitlements in the DKEY rather than in additional role-specific signing
credentials. Where equivalent entitlements require several distinct role
credentials, this avoids issuing and maintaining those additional signing
credentials. The comparison depends on role granularity: one DNMP role can
permit several commands, and Trust Schemas can support other credential
arrangements. The evaluation will therefore measure independently managed
credentials alongside DKEY size, policy complexity, distribution, rekeying,
and runtime costs.

\subsection{Authorization Mechanisms, Lifecycle, and Costs}
\label{sec:authorization-withdrawal}

\paragraph{Identity authentication.}
The User and Provider validate Data signatures and certificate chains under
the applicable trust rules. This identifies an accepted signer; it does not
alone establish that signer's permission to offer or invoke the requested service.

\paragraph{Service-permission verification.}
In the ABE-backed invocation path, the User generates a fresh random value,
\emph{RequestNonce}, and includes it in ABE-protected Request content.
This is an NDNSF application-level value, not the NDN Interest Nonce used for
forwarding duplicate and loop handling.
A Provider that recovers it returns it in ACK Data; the User compares the
returned value with the one stored for the active request. Thus RequestNonce
supports both request binding and a check of access to the service-protected value.
The Provider generates \emph{ProviderChallenge} and includes it in ABE-protected
ACK content. The User uses the recovered ProviderChallenge to construct
Selection Data. Before execution, the Provider validates Selection Data using
ProviderChallenge stored for that request. Together with current service-permission
checks, these checks determine whether the Provider may offer the service and
whether the User may invoke it.

These checks demonstrate access to protected challenge values, not the creation
of new permissions or a formal proof of exclusive key possession. Authorized
key or challenge sharing is outside the claimed threat protection. This reuses
attribute-based permission management rather
than a separate set of role-based invocation rules. It is not cost-free: confidential
discovery already needs Provider DKEYs, whereas User permission DKEYs and
challenge processing are additional authorization costs. ABE confidentiality
combined with DNMP-inspired role authorization remains a valid alternative.

\paragraph{Replay protection.}
Participants match messages to an active request and its protocol state. The
Provider records whether ProviderChallenge has already been used to accept
Selection Data for execution; receiving the same Selection again must not start
another execution. This requires appropriate retention and invalidation of
request state, including across restart. Neither encryption nor possession of
a challenge value alone prevents replay. These admission checks do not establish
exactly-once application side effects across crashes.

\paragraph{Runtime permission grants and withdrawals.}

\texttt{PolicyStatusData} denotes a Controller-signed named Data payload,
not a grant by itself. It identifies the service and current ControllerVersion,
validity interval, policy digest, optional ABE public-parameter name and digest,
the Controller certificate, and revocation targets. Participants validate the
enclosing Data signature and this status before updating local permission or
DKEY state; the status distributes and authenticates policy state but does not
independently grant permission.

The Controller updates permission status for both operations. An ordinary grant
updates the target entity's complete permission policy; that entity retrieves
a replacement DKEY without changing the ABE public parameters. Withdrawal
additionally rotates the Controller's ABE master key and public parameters.
Entities retaining permissions obtain replacement DKEYs encoding their remaining
permissions. The master key stays with the Controller. Rotation is Controller-wide,
not confined to the withdrawn service.

In the proposed update-discovery path, which is not yet fully verified end to end,
the Controller publishes updated public parameters as signed named Data and uses
Sync to announce their availability.
Participants retrieve and validate the parameters and Controller-signed
\texttt{PolicyStatusData}, then refresh their DKEYs as required. Ordinary grants
also require participants to discover and retrieve updated permission status,
even though the public parameters have not changed. Sync is an update-discovery
mechanism, not the authority for granting permission. The local implementation
supports status retrieval and parameter rotation; the dedicated Sync announcement
path remains to be verified end to end.

Current-permission checks enforce withdrawal after the updated status has been
retrieved and validated. Parameter rotation restricts exchanges encrypted under
the new generation. Disconnected nodes cannot apply updates immediately, and
previously disclosed keys or plaintext cannot be taken back.

\paragraph{Lifecycle comparison and evaluation.}

DNMP specifies validity bounds and replay-state handling~\cite{dnmp}; these
do not by themselves provide immediate withdrawal of an unexpired role key.
For the comparison, a DNMP-inspired design can revoke
the relevant credential and require execution nodes to check signed revocation
status or reject expired certificates. The execution node then rejects the
revoked or expired credential; distributed certificate copies need not be retrieved.
Both approaches require update propagation, and neither retracts previously
disclosed keys or plaintext.

Focused integration tests exercise NDNSF's runtime revocation checks, including
identity-, certificate-, and service-scoped withdrawal. These tests establish
behavior at the exercised runtime boundaries, not network-wide instantaneous
revocation or lower cost than certificate-based alternatives. The remaining
evaluation should measure status-propagation delay, rejection delay, rekeying
traffic, and effects on unaffected members. Runtime status validation and key
rotation support runtime permission changes, with explicit propagation and
rekeying costs. They are not ABE-exclusive capabilities. NDNSF introduces ABE
for confidential discovery and reuses its service-permission management for
invocation checks and permission updates; signatures and request-state checks
remain necessary, separate parts of the design.
