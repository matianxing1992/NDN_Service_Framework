\slideentry{2}{Why Service-Level Mechanisms Are Needed}{
Networked applications need mechanisms for service discovery, invocation authorization, and application-data exchange. Some operations discover a currently willing Provider; others must retain an already selected Provider. Applications must associate permissions, execution state and exchanged data with the requested operation. Changes in service availability, resources and connectivity add further challenges. Research goal: a reusable service protocol. UAV and inference applications provide validation cases, not limits on the framework’s intended scope.
}
\slideentry{3}{From Invocation to Collaboration: Two Research Scopes}{
Foundation: evaluate discovery and authorization The initial prototype discovers candidates and selects one Provider whose positive ACK passes validation. Discovery confidentiality, service permissions and management costs matter even without collaboration. Extension: coordinate complementary roles Some tasks need several Providers with different responsibilities. Separate calls do not define a shared role assignment or enforce dependencies between them. Invocation and initial plan-commit mechanisms exist. [28] The proposed research evaluates authorization choices, completes dependency/recovery rules, and tests their reuse and cost.
}
\slideentry{4}{NDN Primitives and Service-Level Decisions}{
NDN building block Remaining application responsibility Named Data and signatures [1] Apply Trust Schema [16] rules to validate signing authority Interest retrieval and caching [1,26] Check task identity, dependencies and deadlines; caches do not guarantee storage Dataset synchronization / SVS [2,3] Discover names; define service-message transitions NAC [4] / enhanced NAC-ABE [19] Encrypt Content for read access; check invocation permission separately NDN: Named Data Networking [1]; NAC: Name-based Access Control; ABE: attribute-based encryption; SVS: State Vector Sync. NDNSF adds service authorization and invocation-state rules.

\slideentry{6}{Three Research Questions}{
RQ1: When does ABE permission reuse offer a better cost--protection tradeoff than complete role-authorized alternatives, as permission scale, overlap, membership and withdrawals change? RQ2: How can single-Provider invocation be extended to roles and named dependencies across Providers, whether Data comes from producers or caches? RQ3: When do these mechanisms improve completion, latency, or execution efficiency, and when do their costs outweigh the benefits? RQ1 studies invocation; RQ2 studies collaboration. RQ3 evaluates their benefits and costs, not another protocol.

\slideentry{9}{Participants and Trust Bootstrap}{
User: requests a service and selects a Provider; the extension also assigns collaboration roles. Provider: offers and executes a service. A node may play both roles. Controller: administers identities and service permissions approved by the organization. Participants use provisioned trust anchors and validation rules for certificates and Controller material. Enrollment establishes identities and service permissions. The User then discovers which authorized Providers are currently willing and selects participants for the task.

\slideentry{11}{Single-Provider Invocation: Four Named Data Types}{
Data Logical purpose Request Describe required service and participation constraints; include protected discovery information and RequestNonce ACK Report positive or negative participation; positive ACK supplies selection information and ProviderChallenge Selection Assign selected execution; provide input/references and protected request-scoped keys; constructed using ProviderChallenge Response Return status, results or result references; the User still validates them before use Sync helps discover names; Interests retrieve Data. The Provider checks Selection before execution; a positive ACK alone does not start the task.
}
\slideentry{12}{Request: Discovery Descriptor; Selection: Task Input}{
Discovery descriptor Needed to decide whether to participate: area, deadline, sensor/model and resource requirements. Application input Needed to execute the selected task: images, detailed processing parameters, or protected input references. Input and results use request-scoped symmetric keys. Selection delivers key material encrypted for the selected Provider; the requesting User retains the keys. The boundary follows necessity. A location needed to assess coverage belongs in the protected descriptor; an image needed only for processing can wait.
}
\slideentry{13}{Three Security Requirements; One Additional Benefit}{
1. Keep discovery descriptors confidential from unauthorized readers before selecting a Provider. 2. Authenticate participants, verify service permissions, and reject replayed invocation messages. 3. Grant and withdraw service permissions during operation. Additional benefit: aggregate service permissions in a decryption key (DKEY) while retaining identity-signing credentials. This is a management property, not another security guarantee.
}
\slideentry{14}{Reason 1: Confidential Discovery Before Selection}{
The User knows the service, but not yet the currently willing Provider identities. An observation area and deadline can reveal intended activity even without the full application input. The User encrypts the descriptor using ABE and the service attribute, without listing Provider identities. [19] Confidential from parties lacking the required decryption capability. Authorized but unselected Providers can read it; names and traffic patterns remain visible.
}
\slideentry{15}{Reason 2: Reuse Service-Permission Management}{
ABE was introduced to keep discovery descriptors non-public. [19] NDNSF reuses the attribute authority to manage Provider and User service permissions. [28] RequestNonce and ProviderChallenge checks use these permissions during invocation. ABE discovery plus role-based invocation is also possible. NDNSF avoids adding role signing credentials solely for service membership; signature validation and request-state checks remain necessary. User DKEYs and challenge processing still add cost.
}
\slideentry{16}{How NDNSF Checks Service Permissions}{
1. Provider permission: recover RequestNonce from ABE-protected Request content and return it in ACK Data. The User compares it with RequestNonce stored for this request. 2. User permission: recover ProviderChallenge from ABE-protected ACK content and construct Selection Data. The Provider validates Selection using its stored ProviderChallenge. Participants also check current service permissions. Challenge checks establish access to protected values, not exclusive key possession. RequestNonce is an application value, distinct from the Interest Nonce.
}
\slideentry{17}{Identity and Replay Checks Have Different Jobs}{
Identity authentication Validate Data signatures and certificate chains under trust rules. An accepted signing identity alone does not establish service permission. Replay protection Match messages to an active request and its state. Record whether ProviderChallenge has already been used to accept Selection for execution; duplicate Selection must not start another execution. Retain or safely invalidate request state, including across restart. Encryption or a challenge value alone does not prevent replay.
}
\slideentry{18}{DNMP: Trust-Schema Command Authorization}{
Distributed Network Measurement Protocol (DNMP) [12] authorizes measurement commands: 1. The Network Key anchors role keys, device keys, and the schema. 2. The client uses target, probe type, arguments, and user role to find an allowed signing key; among matching keys, it chooses the least privileged. 3. The receiving Network Observer Daemon validates the publication under the schema before dispatching the probe. DNMP also uses publication lifetimes and retained state against replay, assuming loosely synchronized clocks. These are concrete command-authorization mechanisms, not just identity checks.
}
\slideentry{19}{DNMP-inspired Authorization versus NDNSF}{
Design Execution authorization Discovery confidentiality DNMP-inspired [12] Check role-constrained signatures and NDNSF invocation state Retain ABE for the first controlled comparison NDNSF ABE-backed Check signatures, RequestNonce, ProviderChallenge, current permissions and request state User encrypts descriptor content with service-level ABE Hold discovery encryption constant to isolate authorization cost. Both retain Selection, current permissions and replay checks. This adapts DNMP, not its original implementation. Group encryption is a separate comparison.
}
\slideentry{20}{RQ1: Evaluate Authorization Design Tradeoffs}{
For n Users and k service permissions per User, on average: Additional authorization credentials Logical objects One role certificate per service nk: O(nk) certificates One policy DKEY per User n: O(n), but policy size grows Both retain identity certificates. Shared roles can also use n certificates. Fixed k: both grow linearly with n. Fewer credentials need not cost less. Measure CPU time and bytes for setup, calls, permission updates and background checks.

\slideentry{22}{Runtime Permission Grants and Withdrawals}{
Both operations update Controller-signed permission status. [28] Ordinary grant: update the target’s complete policy; it retrieves a replacement DKEY. Public parameters stay unchanged. Withdrawal: rotate the Controller’s ABE master key and public parameters; remaining members obtain DKEYs for their remaining permissions. The master key stays with the Controller. Rotation is Controller-wide. Participants must retrieve and validate updates before applying them; disconnected nodes cannot do so immediately.
}
\slideentry{23}{Permission Updates: Discovery, Validation and Application}{
1. Revised design: the Controller publishes new public parameters as signed Data; Sync announces availability. 2. Participants retrieve and validate parameters and permission status, then refresh DKEYs as required. 3. Grants also require status discovery, even when public parameters do not change. Status retrieval and rotation are implemented; Sync announcements are planned for end-to-end validation. Evaluation will measure propagation, rejection delay and rekeying traffic. Previously disclosed keys and plaintext remain accessible to their holders.
}
\slideentry{24}{Threat Model: What Is Trusted?}{
Trusted: Controller authorization and the User’s planning decision. Untrusted delivery: an object may arrive through a producer, forwarder, cache, or repository and still requires validation. Adversarial cases to test: wrong identities, permissions, challenges, request state, roles, dependencies, or execution identities. Not established by signatures/ABE: honest resource reports, correct inference, truthful images, or resistance to authorized key sharing. Scope: trusted Controller and User, Content confidentiality, and withdrawal after validated updates. Malicious-coordinator agreement and traffic-analysis resistance are outside this scope.
}
\slideentry{25}{RQ2 Extension: From Positive ACKs to a Role Plan}{
1. Application supplies roles, dependencies, constraints and deadline. 2. The User closes ACK collection and freezes eligible, validated positive ACKs. 3. A replaceable policy assigns Providers; the User signs the plan. 4. Providers validate assignments, permitted inputs and resource readiness. The template precedes discovery; concrete signer/name constraints follow ACKs. Core commit checks exist. [28] Dependency and recovery contracts remain research to validate.

\slideentry{26}{A Plan Is More Than a Request ID}{
Proposed task: User assigns UAV A to view 1, UAV B to view 2, and Provider C to analysis. UAV A signed ViewImage UAV B signed ViewImage C validates producer and edge C analyzes after both inputs pass Arrows show object dependencies; Interests retrieve the images from producers or caches. }
\slideentry{27}{Plan-to-Data Enforcement: Check Before Advancing}{
1. Validate the Data signature using the appropriate trust rules. 2. Check active execution and deadline; identify the permitted dependency. 3. For new Data, match request/plan/execution and assigned producer; for historical Data, check explicit reuse permission. 4. Check that the object matches the declared edge, permitted name, data format and key scope. 5. Require complete validated input before the dependent computation starts. The proposed rules apply equally to Data retrieved from producers, caches and repositories. End-to-end tests will check valid inputs and rejection of wrong-role, wrong-edge and outdated-execution objects.
}
\slideentry{28}{Collaboration Recovery Needs Explicit State}{
Event Required behavior Late ACK Do not silently change the committed plan Duplicate Selection Check whether execution was already authorized; do not repeat a side effect Incomplete dependency Wait within policy/deadline, recover, or fail; do not execute on partial data Provider replacement Authorize a new assignment; reject old execution actions and specify permitted result reuse Cancellation Prevent late messages from reauthorizing cancelled work A new plan may permit a specific old artifact with its original name and signature. This does not reactivate the old execution. Application checks still decide whether it is usable.

\slideentry{46}{Backup: Aggregate Service Permissions}{
Within one Controller domain, combine several service permissions in one entity’s DKEY; retain identity-signing credentials. [19,28] DNMP represents command authority through role keys and schema rules. One role can permit several commands. [12] Where equivalent permissions require distinct role credentials, NDNSF avoids maintaining those extra signing credentials. Fewer independently managed credentials does not imply fixed DKEY size or lower total cost. Policy size, key distribution and updates still matter.
}
\slideentry{47}{Backup: When Another Authorization Design May Be Better}{
Known Providers and simple rules: signed invocation plus recipient encryption may be sufficient. A small, stable receiver group: ordinary group-key management may be attractive. Rich command-argument restrictions: DNMP-style rules make those constraints explicit. [12] Many changing entitlements: measure both policy/key updates and credential/rule updates before claiming a management advantage. Compare complete combinations of authorization and encryption. ABE-backed authorization is one design choice, not a universally superior solution.
}
