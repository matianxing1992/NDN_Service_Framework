\section{Supplementary Evaluations}

\subsection{Targeted Invocation}
\label{sec:targeted-invocation-evaluation}

For a known provider, we compare NDNSF's four-message flow and targeted requests with gRPC and NSC using a 64-byte echo command and a 5\,ms handler wait. Success requires validation of the returned command and executor identity within 5\,s. For each condition, we rotate the configuration order across five matched blocks. After setup and 10\,s warm-up, each configuration runs for 60\,s with at most one call outstanding. Two 1\,Gbps links have 1, 10 or 50\,ms one-way delay without loss, or 10\,ms with 1\% loss. NDNSF uses a 4096~B publication budget within a 6144~B Sync Interest Application Parameters budget, distinct from the application payload size. NDNSF uses authorization and encryption, gRPC uses mutual TLS, and NSC validates signed packets without payload encryption; the comparison does not isolate protection overhead. Eligible targeted calls use a prepared challenge to carry input in Request and omit ACK and Selection; the four-message flow carries input in Selection. Latencies average the five block means equally. First-call observations start after readiness, before warm-up, and exclude setup.

Without loss, targeted reduces successful mean latency by 38.3--48.7\% relative to the four-message flow, with all attempts completed. All 60 sampled first calls without loss succeed, but targeted has no mean-latency advantage over the four-message flow on those first calls; four of the 20 first calls with loss time out. At 1\% loss, targeted completes 212/269 attempts, versus 309/355 for the four-message flow, 390/440 for NSC and 3179/3179 for gRPC. With one outstanding call per configuration, these rates do not compare reliability at a matched offered load. Some successful targeted calls include bootstrap recovery. The experiment does not localize loss-related failures to a protocol stage or establish a flight-control deadline.

\subsection{Permission Management: Methods and Detailed Results}
\label{app:measured-permission-cost}

We compare three C++ measurement configurations with identical initial permissions: eight RSA-2048 identities, each authorized for 1, 4 or 16 services. Aggregated ABE issues one DKEY containing all of an identity's permissions. Per-permission ABE uses the same NAC-ABE/OpenABE implementation but issues separate DKEYs. A batching alternative distributes AES-256 service keys in one RSA-protected bundle per identity and supports incremental grants. All three reuse signing credentials, sign their management objects, encrypt application data with AES-256 and cache unchanged material. A grant adds one permission to one identity; revocation removes all of that identity's permissions and rotates keys for the seven remaining authorized identities. Five matched repetitions rotate their order. Functional checks verify authorized access, rejection of unauthorized or tampered data, rejection of new-generation ciphertext by a revoked identity retaining old keys, and restored access for all seven remaining authorized identities.

Application data and wrapped content-key objects are excluded from this byte count. Both ABE configurations publish content-key objects separately, whereas batched RSA/AES includes service keys in its management bundles. Aggregation reduces initial and rotation costs relative to separate ABE DKEYs at sixteen permissions (Table~\ref{tab:permission-component-cost}); at one permission, their initial costs are nearly identical. A grant has higher local management costs with aggregated ABE because it replaces the key encoding the full permission policy, while the alternatives distribute only the newly granted key. Identity-wide revocation replaces all remaining authorized identities' DKEYs in a new ABE generation. Batched RSA/AES rotates only service keys held by the revoked identity and updates affected remaining authorized identities; all seven are affected here because the identities initially share the same permissions.

The batched RSA/AES alternative has lower local management costs than aggregated ABE at every measured permission scale and phase. The component results therefore support aggregation within ABE, without establishing a general advantage over batched key distribution.

The network comparison distributes original signed management Data from an authority-side server to eight C++ recipients, each holding only its own private keys, with the same permissions and retained-old-key rejection checks. Three links have 10\,ms one-way delay, 1\,Gbps capacity and no configured loss. Each recipient uses at most eight outstanding exact-name Interests, a 1\,s Interest lifetime, no retry and a 10\,s phase deadline. Fresh processes and NFD receive 10\,s routing warm-up. Five repetitions cover each combination of configuration, permission scale and certificate-cache policy; all runs satisfy the access-control checks.

Management windows cover certificate and key retrieval, validation and installation; access probes run afterward. Network CPU sums recipient process time and excludes generation. Recipient processing is included in both the local management CPU totals and the network-experiment CPU totals, so these measurements overlap. IP bytes count both directions on each of the three links. NFD may cache immutable public parameters and certificates.

Table~\ref{tab:permission-network-cost} shows lower initial and rotation traffic for aggregated ABE than for separate ABE keys at sixteen permissions. Initial ABE retrieval counts exceed DKEY counts because of segmentation and public parameters. The paired rotation-traffic reduction is 171.30\,KiB (95\% $t_4$ CI: 170.70--171.91); initial mean recipient management completion time is lower by 135.96\,ms (129.17--142.75). At four permissions, initial traffic is lower, but the completion-time difference remains unresolved. At one permission, initial traffic is nearly identical, leaving little aggregation benefit.

A grant reverses the traffic comparison because aggregated ABE replaces the full permission policy, whereas separate ABE delivers only the additional key. Cumulative costs across repeated updates remain unmeasured. Batched RSA/AES uses fewer link bytes than aggregated ABE at every measured scale and phase. This experiment distributes pre-generated signed material; it does not establish recovery through the NDNSF Authority API or equivalence of every security property of the constructions.

All alternatives reuse signing identities. The certificate ablation either retains the initially validated authority certificate in the application or drops that reference between phases; NFD caching stays enabled. Reuse saves 0.82--1.05\,ms of recipient CPU time during grants, with all paired confidence intervals above zero. Grant traffic is identical in every pair, and revocation traffic differences remain unresolved. Application reuse therefore saves processing here, without demonstrated link-traffic savings.

A separate MiniNDN experiment exercises the NDNSF Controller, Provider and User update APIs with eight identities and one or sixteen initial permissions per identity. Measurement timeouts are 10\,s for grant recovery and 20\,s for revocation recovery. Identity private keys are not shared between actors. Status polling is every 500\,ms, status validity is 24\,h and the configured grace interval is zero. All five runs at each scale recover protected access after the grant and restore access for the seven remaining authorized identities after revocation and key rotation. At one permission, grant recovery takes 0.644--2.569\,s and revocation recovery takes 2.691--2.819\,s. At sixteen permissions, grant recovery takes 0.664--2.713\,s and revocation recovery takes 3.348--7.022\,s. The Provider installs updated revocation state for all configured services.

Across these ten runs, 102 successful calls using the pre-revocation permission state complete after the revocation update and 18 requests have no terminal result by the end of the observation window. Completion timestamps alone do not establish when an execution was authorized. We observe no execution by a revoked user starting after the updated state is installed for the exercised service; other services have no post-installation execution samples. These measurements show access recovery in this configuration, but do not establish immediate revocation or uninterrupted service. They do not compare management costs through the framework APIs across the three cryptographic alternatives.

\subsection{Invocation with Preconfigured Providers}
\label{sec:matched-provider-availability}

We compare completion and invocation costs when NDNSF, NSC and gRPC can use the same two preconfigured providers. Their identities are supplied before invocation; the costs of obtaining and updating these candidate lists are outside this comparison. The testbed uses three 1\,Gbps links with 10\,ms one-way delay and no random packet loss; the offline conditions additionally apply the scheduled disconnections. Five paired MiniNDN runs per condition use the same scheduled arrivals, provider-state trace, 64-byte input, simulated 5\,ms handler and 2\,s deadline from scheduled arrival. Each 60\,s run schedules 13 tasks at 4.7\,s intervals. The conditions are stable availability, slow or fast link disconnection, and fast online busy rejection. In the offline conditions, complementary link states leave exactly one provider reachable, with each reachable half the time. State intervals average 5\,s (slow) or 0.5\,s (fast); online busy rejection uses the fast trace to alternate which provider rejects all tasks.

NDNSF uses Request--ACK--Selection--Response; NSC and gRPC retry with another provider after a failed attempt. gRPC also prioritizes candidates using periodic health probes. NDNSF permits at most three invocation attempts per task; NSC and gRPC try each provider at most once (two attempts). After a timeout with possible execution, the NDNSF client keeps the attempt open until the task deadline; it retries only when non-execution is established. NDNSF allows 250\,ms for ACK collection and sets an initial 600\,ms attempt timeout, while NSC and gRPC use 250\,ms per attempt. Their security mechanisms also differ, so this comparison does not isolate cryptographic overhead. Here, correct completion requires a validated result before the task deadline, with no duplicate execution or execution finishing at or after that deadline among handlers that passed the provider availability and task-capacity checks. The completion rate includes all planned tasks in its denominator. We assess completion from task plans, handler records and terminal states. Traffic measurements include health probes, failed attempts and retries during the measurement window.

Across the four conditions in Table~\ref{tab:matched-provider-availability}, NDNSF shows no consistent completion advantage and has higher mean latency and gross relay traffic. Under slow disconnection, its completion rate exceeds gRPC's by 12.3 percentage points (paired block-bootstrap 95\% interval 7.7--18.5). Under fast disconnection, its paired difference from NSC is $-12.3$ points (interval $-26.2$ to 1.5). NDNSF has no observed duplicate or late eligible execution. NSC and gRPC each have one duplicate execution under slow disconnection; gRPC has three under fast disconnection. Different retry policies, per-attempt timeouts and transport paths prevent attributing these cross-system results to feedback alone.

We then vary task-specific capacity in five paired blocks with both providers reachable, using the same fast trace. A constrained provider rejects tasks affected by its compute or memory limit, while the other remains eligible. Task classes repeat in a compute--compute--memory--memory cycle, with the starting position determined by the run's seed. The NSC and gRPC clients rotate their default provider order across tasks. In this experiment, the gRPC health probe reports general availability without evaluating task-specific capacity; the NSC client discovers task rejection after input delivery, while NDNSF obtains task-specific participation feedback through ACKs. With the same 2\,s deadline, all three arms correctly complete 65/65 tasks without duplicate or late execution. NDNSF makes 71 attempts, versus 80 for NSC and 78 for gRPC, but its mean latency is 218.0\,ms versus 180.4 and 94.7\,ms, and relay IP traffic is 78.6 versus 7.8 and 40.9\,KiB per planned task. All tasks finish within 521\,ms under this 64-byte, 5-ms-handler workload, leaving ample deadline slack. NDNSF uses fewer attempts in this workload, without improving deadline completion, mean latency or relay traffic.

\subsection{Task Solicitation Versus Coarse Service Advertisements}
\label{sec:dynamic-selection-cost}

We compare task solicitation with preselection from long-term service advertisements followed by protected targeted requests. The advertisement arm queries status after a failed call; its change-driven publications model service capabilities, not an unmodified NDNSD implementation. In five paired blocks, two providers receive one synthetic task per second with a 2\,s deadline and an 80\,ms simulated handler. Both arms use the same eligibility checks and at most three attempts. The solicitation arm waits until the task deadline if an unanswered attempt may have executed; the advertisement client can retry a targeted call after its attempt timeout. These simulated conditions do not represent measured inference or flight workloads.

During temporary busy periods, both arms correctly complete 300/300 tasks; solicitation uses fewer submissions (313 versus 408) but more relay traffic (74.2 versus 56.5\,KiB per task). Mean latencies are 272.2 and 247.7\,ms, with no established paired difference. When provider links alternate so only one is reachable, solicitation completes 259/300 versus 270/300 tasks within 2\,s (paired difference $-3.7$ percentage points; 95\% interval $-5.3$ to $-1.7$). Its mean latency including the 2\,s failure penalty is lower (642.6 versus 732.3\,ms), but it uses more relay traffic (50.1 versus 42.1\,KiB per task). The solicitation arm has no observed duplicate or late eligible execution; one duplicate execution with advertisements is excluded from correct completion. The comparison also changes invocation paths, retry behavior and advertisement visibility, so it does not isolate feedback alone.
