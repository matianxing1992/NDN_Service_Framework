NDNSF was implemented using \texttt{ndn-cxx}~\cite{ndn-cxx}, NDN-SVS~\cite{ndnsvs-github}, and NAC-ABE~\cite{dulal2023nac-abe}. The optional NDNSD integration exposes discovered service information to applications for provider preselection~\cite{dulal2022ndnsd}. The application passes its chosen provider to the targeted-request API; this API does not automatically select a provider from NDNSD advertisements. During development, we found that the baseline NAC-ABE and NDN-SVS implementations did not meet performance requirements, motivating several optimizations.

For NAC-ABE, we introduced key caching so cache hits avoid fetching and decrypting the same key again. For NDN-SVS, messages smaller than 512~bytes are embedded directly in Sync Interest Application Parameters, reducing publication-to-reception delay by one RTT. We also added regular-expression-based subscriptions to NDN-SVS so users and providers receive only relevant messages. For example, a user requesting \path{/ImageProc/YOLO12} subscribes only to matching ACK and Response messages, while a provider subscribes only to matching Request and Selection messages.

Finally, under high-frequency NDNSF workloads, the original blocking APIs and heavily single-threaded design of NDN-SVS became a bottleneck because most synchronization and processing logic executed on the main Face event loop. To address this issue, we redesigned Sync Interest handling and publication as an asynchronous pipeline. CPU-intensive tasks, including state-vector processing, decoding, comparison, and metadata preparation, are offloaded to a bounded worker pool, while all Face and \texttt{io\_context} operations remain on the main NDN thread for thread safety. We further introduced a nonblocking asynchronous publish path that prevents application-level request handling from stalling the Face event loop. These optimizations target event-loop blocking under high-frequency workloads; the evaluation does not isolate their individual contributions.
