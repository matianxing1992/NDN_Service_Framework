Table~\ref{table:Comparison} summarizes supported mechanisms and the provider-selection configurations used in this evaluation. Both NDNSF and NSC use NDN, while gRPC uses IP. NDNSF validates Data signatures under trust rules and uses NAC-ABE to restrict access to encrypted content, including cached copies. gRPC supports TLS and configurable authentication~\cite{grpc-auth}; applications can add object encryption for stored content. NSC also specifies signed invocation Interests, application-defined trust schemas, and encrypted inputs/results. The listed security capabilities are not measurements of security overhead or evidence that all capabilities were enabled in every experiment.

NDNSF also provides a more flexible communication model. Whereas the evaluated gRPC and NSC configurations use one fixed provider, NDNSF supports both one-to-one and one-to-many service invocation by publishing requests as NDN data objects through Sync. This enables collection of current provider feedback, application-defined selection, and cross-validation of results. Loss recovery depends on retransmission and timeout configuration and should not be inferred from the network architecture alone.

In NDNSF's basic invocation flow, ACK collection and Selection introduce exchanges before execution. Their latency depends on dissemination, collection timeouts, and network conditions, rather than a universal RTT count. The experiments use the configurations described below; their authorization and recovery mechanisms are not identical.

\subsection{Performance Metrics}

We use the following metrics in our evaluation:

\begin{enumerate}
\item \textbf{Service Latency}: the time interval from initiating a service request to receiving the service result.

\item \textbf{Success Rate}: the proportion of measured service requests for which the user receives the result within the configured timeout. A request counts once, regardless of message retrieval retries. A timeout does not establish whether the provider executed the request.
\end{enumerate}

The reported results describe the evaluated configurations. This manuscript does not provide the original per-run logs, repetition counts, or random seeds needed to reconstruct confidence intervals; the point estimates should not be interpreted as statistically established differences. The comparisons also do not isolate authorization costs.

\subsection{ACK Strategy Evaluation}
\label{sec:selective-ack}

This experiment evaluates NDNSF's Selective ACK mechanism in a multi-provider environment. Memphis acts as the service user with a request rate of 50~RPS, while CSU, UCLA, and WUSTL provide identical services. CSU is the closest provider but is intentionally overloaded: although it continues receiving requests, it delays responses by 30~seconds. Since the request timeout is 5~seconds, requests handled by CSU are expected to fail.  We compare two ACK mechanisms. Under \emph{ACK-all}, every provider always returns an ACK, even when they cannot complete requests before timeout. Under \emph{Selective ACK}, providers suppress ACKs when overloaded, preventing themselves from being selected.

Table~\ref{tab:selective-ack} shows that ACK-all performs poorly because the first-responding strategy selects CSU for 2209 out of 2250 requests, all of which fail to return a response before the timeout, resulting in only a 1.82\% success rate. In contrast, Selective ACK prevents CSU from being selected while overloaded, allowing requests to be handled by UCLA and WUSTL and achieving a 100\% success rate. These results demonstrate that Selective ACK improves provider selection by preventing overloaded providers from advertising themselves as available.

\subsection{Provider-Selection Strategy Evaluation}
\label{sec:custom-selection}

This experiment evaluates NDNSF's customizable provider-selection mechanism. Memphis acts as the service user, while UIUC, UCLA, and WUSTL provide the same service. To create heterogeneous provider conditions, UIUC, the closest provider, is configured with the slowest service-processing delay (100\,ms), while UCLA and WUSTL use delays of 20\,ms and 5\,ms, respectively. Each provider returns ACKs carrying metadata containing current queue size. We compare two provider-selection strategies. \emph{First-Responding} selects the first provider returning a valid ACK, minimizing ACK waiting time but favoring nearby providers even when they have slower service execution. In contrast, \emph{Shortest-Queue-First}  selects the provider with the smallest reported queue.

Despite the additional ACK collection delay, Shortest-Queue-First reduces end-to-end latency by avoiding provider selection based solely on ACK arrival order.

These results illustrate how ACK metadata supports application-defined selection in the tested heterogeneous provider configuration.
