\label{sec:eval}

We first analyze credential-management costs, then evaluate service invocation against NSC~\cite{meirovitch2021nsc}, an NDN remote code execution framework, and gRPC, an IP-based remote procedure call framework. The invocation experiments examine reliability under loss and provider unavailability, followed by the effects of ACK and provider-selection strategies.

\input{sections/credential-cost}

To measure permission-management costs, we compare three C++ configurations for eight identities, each with 1, 4 or 16 service permissions: one aggregated NAC-ABE DKEY per identity, one separate NAC-ABE DKEY for each permission, and one RSA-protected bundle of AES service keys per identity (batched RSA/AES). A grant adds one permission to one identity; revocation removes all of that identity's permissions and rotates keys for the seven remaining authorized identities. Each configuration is measured in five matched repetitions.

At 16 permissions, initial local management CPU time, including key generation and recipient processing, is 303.10\,ms for aggregated ABE, 704.58\,ms for separate ABE keys and 6.15\,ms for batched RSA/AES. Aggregation lowers this cost relative to separate ABE keys, but the batched alternative has the lowest local cost in every measured phase.

A separate network comparison distributes pre-generated signed objects and excludes online generation. At 16 permissions, aggregation reduces initial management traffic from 281.72 to 86.74\,KiB relative to separate ABE keys (paired reduction 194.98\,KiB; 95\% interval 193.87--196.10), and revocation traffic from 247.11 to 75.80\,KiB. Eight aggregated DKEYs replace 128 separate DKEYs. At one permission, both ABE configurations use about 21.96\,KiB initially; granting one additional permission updates only the affected identity's DKEY, but costs more than delivering one separate ABE key because it replaces the full policy. At 16 permissions, the batched RSA/AES alternative uses only 27.25\,KiB initially and less traffic in every measured phase. Thus, aggregation helps relative to per-permission ABE when permissions are numerous, but is neither generally cheaper than batching nor free of update costs.

A separate MiniNDN~\cite{MININDN} experiment through the NDNSF Controller, Provider and User APIs restores authorized access after grants and revocation-related key rotation in all runs. These observations do not establish immediate revocation or uninterrupted service. This experiment does not compare management costs through the framework APIs across the three alternatives. Appendix~\ref{app:measured-permission-cost} gives the cost breakdown, functional checks, reuse comparison and recovery details.

\subsection{Experimental Setup}

In the multi-provider comparisons with fixed-provider baselines, NSC and gRPC call one fixed provider, while NDNSF solicits several candidates and selects from their ACKs. NSC and NDNSF use signed NDN packets; NDNSF additionally uses NAC-ABE to protect service content. Appendix~\ref{sec:matched-provider-availability} also compares invocation with the same preconfigured candidates and failover enabled in NSC and gRPC. These cross-framework comparisons do not isolate security overhead.

The original single-provider loss, fixed-provider, ACK-strategy, provider-selection, mobility and real-machine measurements used pre-provisioned certificates and excluded online certificate-chain retrieval and validation. They describe that implementation and do not quantify the current validation path. The NDNSF configurations in the no-loss single-provider and matched invocation studies validate certificate chains against fixed trust anchors.

\subsection{Performance Metrics}

We use the following metrics in our evaluation:

\begin{enumerate}
\item \textbf{Service Latency}: the time interval from initiating a service request to receiving the service result. Unless stated otherwise, means exclude failed requests; deadline-penalized means assign failures the stated task deadline.

\item \textbf{Success Rate}: the proportion of measured service requests for which the user accepts a result under the invocation's configured timeout handling. A request counts once, regardless of message retrieval retries. A timeout does not establish whether the provider executed the request.
\end{enumerate}

The single-provider, fixed-provider, ACK-strategy, provider-selection, mobility and real-machine comparisons report point estimates without repetition-based uncertainty estimates. They do not establish statistical differences or isolate authorization costs. The matched studies report repetitions and uncertainty.

\subsection{Task-Feedback Ablation}
\label{sec:task-feedback-ablation}

To isolate task feedback from access to alternative providers, we used an internal NDNSF ablation in five paired MiniNDN blocks of 13 planned tasks each. Both arms used the same two candidates, protected Request--ACK--Selection--Response path, fixed-root validation, task-state trace, 64-byte input, simulated 5-ms handler, and modeled 2-s target-recognition deadline. In both arms, the user selected the provider whose name came first in a fixed ordering among those returning valid positive ACKs. Only the Provider's participation decision differed: a current-task capacity check versus ACK-all.

Each 60\,s block schedules tasks every 4.7\,s, with at most three invocation attempts per task; an attempt is a new invocation, not a message-retrieval retry. Three 1\,Gbps links have 10\,ms one-way delay and no random loss. Both providers remain reachable. Their complementary capacity states alternate at intervals of 0.3--0.7\,s (mean 0.5\,s), with each provider constrained half the time. A constrained provider cannot accept the task class affected by its resource limit, either compute or memory, while the other remains eligible.

Task feedback produced 65/65 timely correct completions versus 57/65 for ACK-all (paired gain 12.3 percentage points; block-bootstrap 95\% interval 7.7--18.5). It required 65 versus 89 attempts; 32 ACK-all attempts were rejected for insufficient capacity, versus none with feedback. Neither arm had duplicate execution or execution that finished at or after the task deadline among handlers that passed the provider availability and task-capacity checks. Mean per-attempt submission-to-Selection time was 83.9 versus 50.1\,ms; total IP traffic measured across the relay's interfaces, including background traffic, was 71.9 versus 99.2\,KiB per planned task. Feedback improved completion and reduced failed attempts in these traces at about 34\,ms additional selection delay. The result does not establish the same gain for other loads or deadlines.

In a separate cross-framework comparison with the same preconfigured candidates and failover, NDNSF shows no consistent completion advantage and incurs higher invocation latency and relay traffic (Appendix~\ref{sec:matched-provider-availability}). The cost of obtaining and updating candidate lists is excluded, while NDNSF's Request--ACK exchange is included.

Compared with advertisement-based preselection, NDNSF's four-message flow makes fewer submissions under busy conditions, but incurs higher traffic in both conditions and completes fewer tasks on time under link changes (Appendix~\ref{sec:dynamic-selection-cost}). Both supplementary comparisons change invocation paths, retry behavior and available state information, so they do not isolate feedback.

\subsection{ACK Strategy Evaluation}
\label{sec:selective-ack}

This experiment evaluates NDNSF's Selective ACK mechanism in a multi-provider environment. Memphis acts as the service user with a request rate of 50~RPS, while CSU, UCLA, and WUSTL provide identical services. CSU is the closest provider but is intentionally overloaded: although it continues receiving requests, it delays responses by 30~seconds. Since the request timeout is 5~seconds, requests handled by CSU are expected to fail.  We compare two ACK mechanisms. Under \emph{ACK-all}, every provider always returns an ACK, even when they cannot complete requests before timeout. Under \emph{Selective ACK}, providers suppress ACKs when overloaded, preventing themselves from being selected.

Table~\ref{tab:selective-ack} shows that ACK-all performs poorly because the first-responding strategy selects CSU for 2209 out of 2250 requests, all of which fail to return a response before the timeout, resulting in only a 1.82\% success rate. In contrast, Selective ACK prevents CSU from being selected while overloaded, allowing requests to be handled by UCLA and WUSTL and achieving a 100\% success rate. Under this forced-overload configuration, suppressing CSU's ACK prevents the first-responding strategy from choosing it.

\subsection{Provider-Selection Strategy Evaluation}
\label{sec:custom-selection}

This experiment evaluates NDNSF's customizable provider-selection mechanism. Memphis acts as the service user, while UIUC, UCLA, and WUSTL provide the same service. To create heterogeneous provider conditions, UIUC, the closest provider, is configured with the slowest service-processing delay (100\,ms), while UCLA and WUSTL use delays of 20\,ms and 5\,ms, respectively. Each provider returns ACKs carrying metadata containing current queue size. We compare two provider-selection strategies. \emph{First-Responding} selects the first provider returning a valid ACK, minimizing ACK waiting time but favoring nearby providers even when they have slower service execution. In contrast, \emph{Shortest-Queue-First}  selects the provider with the smallest reported queue.
